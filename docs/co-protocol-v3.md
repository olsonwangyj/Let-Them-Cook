# CO application protocol version 3

This is the specification of the Communications application protocol: the BLE sensor packet, when a glove sends, the source statistics, the JSON messages between the laptop, the Ultra96 service and the phone, the Ultra96's ingest connections, the result rules, the read-only board monitor on the gateway port, the board-side model interface, the phone's per-result function, the BLE control channel and file transfer. The transport underneath (BLE GATT, SSH, TLS) and the reasons for the design are in `communications-handoff.md` (section 4 for the transport, section 5 for the reasons) and its detail chapters. Where this document and the code disagree, the code wins.

## Version 3, and the opt-in sensor versions 4 and 5

Version 3 is the default of every component (the Ultra96 service runs sensor version 4 since 2026-10-28, and by Wen Ree's message of 2026-10-29 the gloves run version 5; results, which the phone apps read, stay at `v` 3 in all three). From 2026-10-14 to 2026-10-26 it was the only version (the owner's rule of 2026-10-14: only the newest version is supported). Since the merge of the team main `5e3f78e` into the fork on 2026-10-27, a **sensor version 4** for the three-flex gloves exists beside it, selected explicitly at each end and described in the next section, and since team pull request #40 (2026-10-29) a **sensor version 5**, version 4 with the gyro at a tenth of the resolution and ten times the range (the section after it). A run uses one version end to end: ends of different versions refuse each other's packets and messages, and nothing negotiates or mixes them. Everything below that names 38 bytes, 11 values or `LCS3` is version 3. Within version 3 there is no compatibility mode. An upgrade means reflashing both boards, redeploying the Ultra96 service and reinstalling the phone app together. What version 3 removed is listed under "History" at the end.

Unchanged by version 3: the BLE service and its UUIDs, the BLE security, the `B7` control framing (control version 1), the network framing, the `SUBSCRIBE` and `SUBSCRIBED` envelopes (`v` 1), the session ID and the ports. The board monitor's envelopes, added within version 3 on 2026-10-18, are at `v` 1 too and use the existing gateway port 9999, so the ports are still 8888 and 9999 (see "Board monitor on the gateway port").

## Sensor version 4 (opt-in, the three-flex gloves)

Added by Wen Ree in the team pull requests #32 to #36 (team main `5e3f78e`; the transport is `c74abab`, described in `docs/HAND_V4_TRANSPORT.md`) and merged into the fork on 2026-10-27 (`97db189`). The Communications launch options that select it were added the same day. Version 3 stays the default everywhere; version 4 is chosen with:

- **Firmware:** `-DCOMMS_FLEX3_GLOVE=1` (`comms_packet.h`): `kPacketVersion` 4, `kChannelCount` 12, `kPacketSize` 40. The environments `firebeetle32-left-glove-flex3` and `firebeetle32-right-glove-flex3` build the real three-flex gloves (Siqiang's module, always-send, 50 Hz from boot); `firebeetle32-left-flex3` and `firebeetle32-right-flex3` (2026-10-27) build the dummy module in the same format for bare boards, with `flex3` always 0, 50 Hz from boot. `python flash.py --flex3` (with or without `--glove`) flashes them.
- **Laptop:** `BridgeConfig(sensor_version=4)`, `python -m laptop.bridge --sensor-version 4`, `python -m laptop.dual_bridge --sensor-version 4`, `python demo.py start|run|live --sensor-version 4` and `python -m tools.check_board ... --sensor-version 4`.
- **Ultra96:** `python -m ultra96.server --sensor-version 4`, deployed with `python -m tools.deploy_service --sensor-version 4`; `demo.py service --start` restarts a deployment with the version it was deployed with.

What changes in version 4, and nothing else:

| Part | Version 3 | Version 4 |
|---|---|---|
| Sensor packet | 38 bytes, `<2sBBIII11h>`, version byte 3 | 40 bytes, `<2sBBIII12h>`, version byte 4; the same 16-byte header |
| Channels | 11: `ax ay az gx gy gz yaw pitch roll flex1 flex2` | 12: the same 11, then `flex3` (index 11; the thumb, GPIO39; index GPIO34, middle GPIO35), scale 10000. Wen Ree's firmware comment: the flex values are the raw 12-bit ADC reading / 4095, not a calibrated bend fraction |
| Constants | `common/sensor.py` | `common/sensor_v4.py`: `VERSION` 4, `PACKET_SIZE` 40, `SENSOR_MTU_FLOOR` 43, `MAX_PACKETS_PER_NOTIFICATION` 6 (240 bytes, still one 251-byte link-layer packet), separate synthetic fixtures `DUMMY_FIXTURES` |
| Source statistics | 36 bytes, marker `LCS3` | the same 36-byte layout, marker `LCS4` (`parse_source_stats(..., sensor_version=4)`) |
| Control commands | the command's embedded packet is version 3 | version 4 (`common/control.py`, `sensor_version=4`); the `B7` framing stays control version 1 |
| `SENSOR_BATCH`, `INGEST_ACK` | `v` 3, 11 values | `v` 4, 12 values (`ultra96.protocol.validate_message(..., sensor_version=4)`) |
| `GESTURE_RESULT` | `v` 3 | **`v` 3** (2026-10-27, the owner's decision: both phone apps refuse `v` 4; `ultra96.protocol.RESULT_VERSION`). Until that change Wen Ree's transport published results at `v` 4 |
| Model interface | `values` 11 floats | `values` 12 floats; the runner bridge's hello names the 12 channels |

Unchanged: the BLE service, its UUIDs and its security, the network framing, the ports, the session, the subscription and board-monitor envelopes (`v` 1), the result rules and the result fields. ## Sensor version 5 (opt-in, the three-flex gloves with the wide gyro range)

Added by Wen Ree in team pull request #40 (team main `ec200b9`, 2026-10-29; codec `common/sensor_v5.py`, firmware `-DCOMMS_WIDE_GYRO=1`; his `docs/HAND_AI_HANDOFF_20261029.md`, `docs/HAND_WIDE_GYRO_DIAGNOSTIC.md`), for his trained hand12 models (`fpga/models/hand12_v5_20261029`, whose `config.json` per hand names `sensor_packet_version` 5). By his message of 2026-10-29 both of Siqiang's gloves run it. The Communications launch path carries it since 2026-10-29 (not yet run on hardware). Version 5 is version 4 with one difference: the gyro channels travel at **10 counts per deg/s instead of 100**, so the int16 range covers ±3276.7 deg/s instead of ±327.67; the real gloves' sensor runs at ±1000 deg/s (`-DGLOVE_GYRO_RANGE_DPS=1000`, register `0x10`, 32.8 LSB per deg/s, read back at `gloveBegin()`). It is chosen with:

## Sensor packet

Each sample is one 38-byte packet, little-endian, Python format `<2sBBIII11h`. Packets travel as BLE notifications on characteristic `6e1c0005-7a45-4dc4-b678-3f2d5a9c1001`, 1 to 6 whole packets per notification (see "Sensor notifications" below; one packet per notification until 2026-10-19).

| Offset | Size | Field | Value |
|---|---|---|---|
| 0 | 2 | Marker | ASCII `LC` (`4C 43`), the only marker accepted |
| 2 | 1 | Version | 3, the only value accepted |
| 3 | 1 | `device_id` | 1 = left, 2 = right (fixed at build time) |
| 4 | 4 | `boot_id` | uint32, drawn at random once per power-up |
| 8 | 4 | `seq` | uint32, from 0 at each power-up, +1 per sample sent. Only a sample that leaves the board's send queue takes one: in a notification the BLE stack accepted, or as the oldest sample dropped from a full queue, which leaves a gap (see "Sensor notifications" and "When a glove sends") |
| 12 | 4 | `uptime_ms` | uint32, this board's `millis()` just after the sample was read. The two boards are not synchronised |
| 16 | 22 | `values` | 11 × int16, in the channel order below |

Channels (physical value = int16 / scale):

| Index | Name | Unit delivered by the sensor module | Scale | int16 range in physical units |
|---|---|---|---|---|
| 0, 1, 2 | `ax`, `ay`, `az` | g, gravity removed | 10000 | ±3.2767 g |
| 3, 4, 5 | `gx`, `gy`, `gz` | °/s, bias removed | 100 | ±327.67 °/s |
| 6, 7, 8 | `yaw`, `pitch`, `roll` | degrees | 100 | ±327.67° |
| 9, 10 | `flex1`, `flex2` | 0.0 to 1.0 | 10000 | at most 3.2767 |

The constants are `VERSION`, `CHANNELS`, `SCALES`, `PACKET_SIZE` (38), `SENSOR_MTU_FLOOR` (41) and `MAX_PACKETS_PER_NOTIFICATION` (6) in `common/sensor.py`, and `kPacketVersion`, `kChannelCount` and `kPacketSize` in `firmware/esp32/include/comms_packet.h:11-15`, `kMaxPacketsPerNotification` in `firmware/esp32/include/comms_send_queue.h`. A notification of one packet needs a negotiated ATT MTU of at least 41 (firmware `sensorFitsMtu`, `comms_security.h:22`; the laptop refuses a smaller MTU before subscribing); a notification carries at most (MTU - 3) / 38 packets. The measured MTU is 517. The application-layer rate at 50 Hz is 38 × 8 × 50 = 15.2 kbps per board.

### Sensor notifications

Since 2026-10-19 a sensor notification carries 1 to 6 whole 38-byte packets back to back, oldest first, so its length is 38, 76, 114, 152, 190 or 228 bytes. Each packet is unchanged and carries its own `seq` and `uptime_ms`. Six packets (228 bytes) plus the ATT (3) and L2CAP (4) headers fit one 251-byte link-layer packet when the link uses the LE data length extension.

Why: with both gloves connected, the laptop's Bluetooth controller (Intel, Windows 11) sometimes serves each glove's link only every second 15 ms connection event, with one notification per served event, about 33 notifications/s per glove. With one sample per notification at 50 Hz, Bluedroid's L2CAP queue for the ATT channel on the glove filled (ESP-IDF v4.4.7: congested above 20 queued packets, clear again at 10), `esp_ble_gatts_send_indicate` refused notifications, and each refused sample lost its `seq`: bursts of about 15 lost samples about every 0.9 s, about a third of each glove's samples, and 0.6 to 0.9 s of queueing delay (the open issue of 2026-10-19, hand-off section 13).

How the board sends (`firmware/esp32/include/comms_send_queue.h`, `sendQueuedSamples` in `firmware/esp32/src/main.cpp`):

- A send tick puts its sample in a queue of 32 samples (0.64 s at 50 Hz). A queued sample has no `seq` yet.
- On every main-loop pass the board estimates the notifications still below the application (Bluedroid's task queues, its L2CAP queue and the controller), from `esp_ble_get_cur_sendable_packets_num` and `esp_ble_get_sendable_packets_num` against the largest values seen (nothing pending then). When fewer than 2 are pending, it sends every queued sample, up to 6 and up to (MTU - 3) / 38, as one notification. So the backlog waits on the board, where it is coalesced, and the L2CAP queue never nears its congestion threshold; the board's ATT replies (the notification-off write, the source-statistics read, control responses) are neither delayed behind it nor discarded.
- `seq` is taken when the stack accepts the notification. A notification the stack refuses takes no `seq`; its samples stay queued and are sent later.
- When the queue is full, its oldest sample is dropped: it takes the next `seq` and counts as a failure, so the laptop sees the gap.
- Samples still queued when the laptop turns sensor notifications off are discarded without a `seq`, in the same locked step as the notification-off write, like the ticks that follow, so the laptop's two shutdown reads agree. Samples still queued when the link drops were lost while the laptop listened: each takes a `seq` and counts as a failure, so the laptop sees the gap after it reconnects. Either way `next_seq` = `submitted` + `failures` at every read.
- When the link keeps up, every notification carries one packet, as before. When it falls behind, each notification carries the samples of one service period; at 50 Hz with one notification per 30 ms that is mostly 1 or 2, and 3 or 4 after the laptop's controller skips a slot (measured on 2026-10-19).
- The board asks for 251-byte link-layer packets (`esp_ble_gap_set_pkt_data_len`) once per connection after authentication.

How the laptop receives (`split_notification`, `common/sensor.py`; `Bridge.enqueue`, `laptop/bridge.py`): a notification whose length is 38 × k with k from 1 to 6, and whose every packet decodes, becomes k inbox items in order, all with the notification's arrival time. Each gets its own `sensor` evidence record, with `batch_index` (0 to k - 1) and `batch_size` (k). `callback_received` and `observation_received` count packets; `notifications_received` counts notifications, and the receive silence is measured between notifications. A notification of any other length, or with any packet of another marker or version, stays one item, which the laptop counts as `malformed` and does not forward. Commands still carry exactly one packet (`decode_packet`).

The Ultra96 and the phone are unchanged: the laptop forwards one `SENSOR_BATCH` per packet, as before. Packets that shared a notification arrive at the Ultra96 within microseconds of each other.

**Provisional.** Siqiang answered on 2026-10-15 that a glove should send only while his module reports MOVING and nothing while IDLE (see "When a glove sends"). So the IDLE/MOVING state does not need to travel with each sample, and the 11-value layout stays. It is frozen once Wen Ree agrees and the scales are checked against Siqiang's real sample log. His module sets the MPU-6500 to ±2 g and ±250 °/s (`hardware/gloves/integration_files/glove_sensor.cpp:27-28` and `:454-455`), so its values fit the ranges above: gravity-removed acceleration stays within about ±3 g, and the gyro within ±250 °/s plus its bias. A wider sensor range needs new scales first.

Golden vectors: `tests/fixtures/comms-golden.json` with `comms-dummy.bin` and `comms-boundaries.bin`. They are hand-specified, and `firmware/esp32/test/host_packet.cpp` prints the same bytes. The fixture-row vector is device 2, `boot_id` 0x78563412, `seq` 42, `uptime_ms` 0x01020304 and the values `[1200, -300, -8500, 4000, -2000, 1500, 1250, -3000, 600, 6000, 5500]` (0.12 g, −0.03 g, −0.85 g, 40 °/s, −20 °/s, 15 °/s, 12.5°, −30°, 6°, 0.6, 0.55):

### Dummy data

A board that does not run Siqiang's module uses the built-in dummy glove module (`COMMS_GLOVE_MODULE` 0, the default; `firmware/esp32/src/dummy_glove.cpp`). Each of its samples carries one row of `common/dummy_fixtures.json`, chosen at random and independently of `seq`. Its `gloveRead` writes the row as physical values, int16 / scale (`dummyFixtureSample`, `comms_dummy_gate.h:27-33`), and the normal scaling turns them back into the same int16 row, so the packet carries exactly the row (host-tested in `firmware/esp32/test/host_glove.cpp`). The file holds 2 to 64 rows of exactly 11 int16 values; it holds 4 today. After editing it, run `python -m tools.generate_dummy_fixtures` (or `python flash.py`, which runs it every time, `flash.py:91`) and rebuild the firmware. The generator refuses a row that is not exactly 11 int16 values (`load_fixtures`, `common/sensor.py:101-107`). The firmware build refuses only a stale `comms_fixtures.h` whose rows are not 11 wide (`comms_packet.h:16-17`): running `platformio` directly does not regenerate the header and builds the old rows without an error. Python reads the file when its process starts. The firmware uses ESP randomness; build with `-DCOMMS_FIXTURE_SEED=<n>` for a reproducible sequence of reads (`dummy_glove.cpp:13-22`). One row is drawn per send tick that reads the module (`gloveRead`, `dummy_glove.cpp:29-33`), idle ticks and ticks dropped because the link changed included, so the rows of the sent samples repeat exactly only for an ungated dummy with no dropped tick. `--seed` controls the laptop's and the mock source's choice, not the firmware's. `-DCOMMS_INITIAL_RATE_HZ` sets the firmware's starting rate (default 10, valid 1 to 200; the `-glove` environments use 50). The dummy never reports IDLE unless it is built with `-DCOMMS_DUMMY_IDLE_MS` (see "When a glove sends").

### Scaling on the board

`firmware/esp32/include/comms_sample.h` turns one sample of 11 physical floats into the 11 int16 of the packet (`scaleSample`, lines 36-65). Every sample a glove module reads and reports as MOVING passes through it, from either module (`prepareSample`, lines 97-114, called by `produceSample`, `firmware/esp32/src/main.cpp:404-431`). The firmware fills the 11 values with NaN before each read, so a channel the module leaves unwritten refuses the sample.

- Each value is multiplied by its scale and rounded half away from zero.
- A NaN or infinity refuses the whole sample.
- A value outside int16 is clamped to the limit and counted (`clamped`, on the board's serial `comms_stats` line only) by default. Built with `-DCOMMS_OUT_OF_RANGE_DROP=1`, it refuses the whole sample instead. **This policy is provisional** until Wen Ree answers. A clamped value cannot be told apart from a real value at the limit.
- A refused sample is not sent, takes no `seq` and is counted (`refused` in the source statistics), so it shows only as a longer `uptime_ms` step, never as a gap.

## When a glove sends

A board sends a sample only while its glove module reports MOVING (Siqiang's answer of 2026-10-15). Nothing is sent while the glove is IDLE, except by a recording build (see "A gated board"), and the IDLE/MOVING state itself does not travel. Status: verified on 2026-10-16 on the right board with the gated dummy module (see "Status"); not yet run with Siqiang's module on a glove.

**The glove module.** The firmware calls four plain functions, declared in `firmware/esp32/include/comms_glove.h:53-71`:

| Function | When the firmware calls it | Contract |
|---|---|---|
| `bool gloveBegin()` | In `setup()`, before BLE starts, up to 3 times by default (`COMMS_GLOVE_BEGIN_ATTEMPTS`, 1 to 10) with a 500 ms pause between tries (`COMMS_GLOVE_BEGIN_RETRY_MS`, 0 to 10000), until it returns `true` (`beginWithRetries`, `comms_glove.h:86-98`; `main.cpp:441-450`; decision D38, hand-off 6.5) | May block (Siqiang's module calibrates for about 5 s, glove held still), and each try repeats the calibration; the board starts advertising only after the last call returns. `false` = no sensor, or its set-up or calibration failed. Must be safe to call again after `false`. After each failed try except the last the board prints `glove_begin_failed attempt=<n> retry_ms=<ms>`, and then always `glove_begin ok=<0|1> module=<dummy|external> gated=<0|1> attempts=<n>`. When every try fails, the board still advertises, and its ticks count as unread (seen on 2026-10-16 with the `-glove` build on a board without sensors: `attempts=3`) |
| `void gloveUpdate()` | Every main-loop pass (about every 1 to 2 ms), outside any lock, connected or not (`main.cpp:506`) | Must not wait. A slow call delays one send tick, not the rate; a pass longer than the send interval (20 ms at 50 Hz) skips ticks |
| `bool gloveRead(float out[11])` | At a send tick, only while the laptop is connected and subscribed, so calls can be seconds apart | Must not wait. `true` = one current sample, in the packet's channel order and units; `false` = no valid sample now |
| `bool gloveShouldSend()` | Right after a successful `gloveRead` | Must not wait. `true` = MOVING, send it; `false` = IDLE, skip it |

The build switch `COMMS_GLOVE_MODULE` selects the module: 0 (the default) the built-in dummy, 1 an external module. The environments `firebeetle32-left-glove` and `firebeetle32-right-glove` link Siqiang's module and start at 50 Hz; `python flash.py --glove` flashes them. Their copies of his module (`firmware/esp32/lib/glove_sensor/src/` and the weights header `firmware/esp32/movement_model_params.h`) are made unchanged from `hardware/gloves/integration_files/` by `python -m tools.sync_glove_module` (`tools/sync_glove_module.py:26-32`); `--check`, `flash.py --glove` and `tests/test_glove_module_sync.py` refuse copies that differ. There `gloveShouldSend` is his `gloveIsMoving()` (`src/glove_module.cpp:10-18`).

**A gated board.** A board is gated (`kGloveGated`, `comms_glove.h:79-80`) in two cases. It runs an external module, unless that build adds `-DCOMMS_GLOVE_SEND_ALL=1` (every sample, IDLE included, for recording sessions). Or it runs the dummy built with `-DCOMMS_DUMMY_IDLE_MS=<ms>` above 0: a cycle from boot, MOVING for `COMMS_DUMMY_MOVING_MS` (default 3000), then IDLE for `<ms>` (`dummyMoving`, `comms_dummy_gate.h:17-21`); the default 0 never gates. The board reports it in bit 0 of the source statistics flags and on its serial lines `glove_begin ok=… module=… gated=… attempts=…` and `comms_ready … glove=… gated=…`.

**One send tick.** Send ticks run at the board's rate. A tick produces a sample only while the laptop is connected, authenticated and subscribed with an MTU of at least 41; other ticks are not counted in the source statistics. The board then reads the module outside its connection lock, and the tick has one of four outcomes (`SampleOutcome` and `prepareSample`, `comms_sample.h:82-114`):

| Outcome | Cause | Sent | `seq` | Counted in the source statistics |
|---|---|---|---|---|
| Send | read, MOVING, scaled | yes, through the send queue | the next one, when it leaves the queue | `next_seq`, with `submitted` (sent) or `failures` (dropped from a full queue) |
| Idle | read, IDLE | no | none | `idle` |
| Unread | `gloveRead` returned `false` | no | none | `unread` |
| Refused | scaling refused the sample | no | none | `refused` |

If the link changed while the module was read, the tick is dropped and nothing is counted (`race_dropped`, on the serial `comms_stats` line only). So once the laptop has turned notifications off, the statistics no longer change. A late main-loop pass delays one tick without lowering the rate; ticks covered by a longer stall are skipped, never caught up (`sendTickDue`, `comms_sample.h:73-78`). Samples that waited for the link are sent together (see "Sensor notifications").

**What the receivers can rely on.** Within one `(device_id, boot_id)`, `seq` only increases and never repeats. A gap in `seq` means samples were lost after the board numbered them: dropped from the board's full send queue (counted in `failures`), or lost on the laptop or with a dropped link. A pause (idle, unread or refused ticks), a disconnect, or samples discarded from the send queue when notifications stopped show only as a jump in `uptime_ms`, never as a gap. Samples may arrive several to a notification, with the same arrival time. The two gloves gate independently, so one can be silent while the other sends. With gated builds, the model's `on_sample` receives only samples sent while MOVING. Ungated builds (the default dummy, and a recording build with `-DCOMMS_GLOVE_SEND_ALL=1`) send every sample they read, and nothing in the packet marks an IDLE sample.

**Timing of Siqiang's module** (his code, read on 2026-10-15). His detector evaluates a 50-sample (1 s) window every 200 ms. It reports MOVING after 2 windows in a row above its threshold and IDLE after 3 in a row below, and `gloveIsMoving()` is false until the first window has filled. So MOVING comes at the earliest about 0.2 to 0.4 s after motion starts (two evaluations 200 ms apart), and later when the 1 s window needs more motion to cross the threshold. IDLE comes at least about 0.4 to 0.6 s after motion stops, and up to about 1.6 s after vigorous motion, because the 1 s window still holds that motion. Samples before the MOVING decision are never sent and cannot be sent later. His module also restarts the detector after a failed sensor read, a non-finite sample or more than 100 ms between `gloveUpdate` calls (`hardware/gloves/integration_files/glove_sensor.cpp:487-497` and `:533-537`). Sending then stops for at least about 1.2 s (the 1 s window refills, and a second window 200 ms later must agree), even in the middle of a gesture. In this firmware `gloveUpdate` runs every 1 to 2 ms, so the restart happens once after boot (BLE set-up runs between `gloveBegin` and the first `gloveUpdate`) and after a transient sensor read failure. His standalone sketch (`hardware/gloves/model_threshold_variant_1/debug_esp32_ml_movement_detector_v1.ino`) never restarts its detector: it only skips a sample after a failed read or a gap of more than 100 ms.

## Source statistics

The read characteristic `6e1c0006-7a45-4dc4-b678-3f2d5a9c1001` returns 36 bytes, little-endian, Python format `<4sBB2xIIIIIII` (`serializeSourceStats`, `comms_source_stats.h:39-65`; `parse_source_stats`, `laptop/source_audit.py:55-78`):

| Offset | Size | Field | Value |
|---|---|---|---|
| 0 | 4 | Marker | ASCII `LCS3`. It follows the packet version (`LCS4` with sensor version 4, `LCS5` with version 5) |
| 4 | 1 | `device_id` | 1 or 2 |
| 5 | 1 | Flags | Bit 0 = a gated board (see "When a glove sends"). Bit 1 = the board may send several packets per notification; every board since 2026-10-19 sets it. The other bits are 0 |
| 6 | 2 | Reserved | Zero |
| 8 | 4 | `boot_id` | As in the packet |
| 12 | 4 | `next_seq` | The `seq` the next sent sample will take |
| 16 | 4 | `submitted` | Samples sent in notifications the BLE stack accepted (one per packet, not per notification) |
| 20 | 4 | `failures` | Samples dropped from the board's full send queue; each took a `seq` (until 2026-10-19: refused submissions) |
| 24 | 4 | `idle` | Send ticks skipped because the module reported IDLE |
| 28 | 4 | `unread` | Send ticks without a valid sample from the module |
| 32 | 4 | `refused` | Send ticks whose sample the scaling refused |

The seven counters are uint32 totals since power-up. The laptop accepts exactly 36 bytes with the marker `LCS3`, zero reserved bytes and no flag other than bits 0 and 1. A laptop older than 2026-10-19 accepts only bit 0, so it refuses a board that may batch before subscribing (`source statistics flags contain unknown bits`) instead of counting its notifications as malformed. The 24-byte `LCS3` value of the first version-3 build (`<4sB3xIIII`, without the flags and the last three counters) is no longer accepted; it ran only on the right board.

The audited relays (`demo.py run`, `live` and `start`, through `laptop/dual_bridge.py`, and `tools.check_board`) read the statistics once before subscribing and once after stopping, to reconcile "generated on the board (the change in `next_seq`) = received by the laptop = acknowledged by the Ultra96". Their reports add `gated`, `source_idle`, `source_unread`, `source_refused` and `source_ticks` (generated + idle + unread + refused: every send tick while the laptop listened). Idle ticks never make a board's audit unclean, but a clean audit needs at least one sent sample (`report`, `laptop/source_audit.py:174-198`), so a gated glove kept still for the whole capture is unclean. For a gated board, `laptop/dual_bridge.py` requires generated + idle to reach 90% of the ticks expected while its sensor notifications were on (`source_ticking_seconds` × the rate), and does not judge silence once the board has reported idle ticks (`board_coverage`, `laptop/dual_bridge.py:490-515`). An ungated board keeps the earlier rules. The relays refuse a board with older firmware before subscribing. The 24-byte values of the 2026-10-14 build, of version 2 (`LCS1`) and of Week 7 (`W7S1`) get `source statistics must contain exactly 36 bytes; flash this board with the current firmware`; a 36-byte value with zero reserved bytes and another marker gets `invalid source statistics magic; flash this board with the current firmware` (non-zero reserved bytes are refused first, with `source statistics reserved bytes must be zero`, `laptop/source_audit.py:66-67`). The audit is off by default (`BridgeConfig.source_audit`, `laptop/bridge.py:48`): the plain `python -m laptop.bridge` does not read the statistics, so it does not refuse a version-2 board but counts its 32-byte packets as `malformed`.

## JSON messages

Each network frame is a 4-byte big-endian length followed by a strict UTF-8 JSON object of 1 to 16384 bytes (`common/wire.py`). Duplicate keys and non-finite numbers are refused. The set of keys must match exactly. There is no error message: on any error the receiving side closes the connection. On the Ultra96's ingest port the rest of a frame must arrive within 5 s of its first byte, and the wait before that byte is the ingest idle limit (see "Ingest connections on the Ultra96").

| `type` | `v` | Port, direction | Keys (exactly these) |
|---|---|---|---|
| `SENSOR_BATCH` | 3 (4 or 5 with sensor version 4 or 5) | 8888, laptop → board | `v`, `type`, `session_id`, `device_id`, `boot_id`, `seq`, `uptime_ms`, `values`, `request_id` |
| `INGEST_ACK` | 3 (4 or 5 with sensor version 4 or 5) | 8888, board → laptop | `v`, `type`, `session_id`, `device_id`, `boot_id`, `seq`, `request_id`, `status` |
| `SUBSCRIBE` | 1 | 9999, phone → board | `v`, `type`, `session_id` |

The version-1 subscription envelopes are unchanged: they never carried the packet version, and every app built before 2026-10-28 sends only them. A version-2 subscription (2026-10-28, opt-in) also asks for hand events (see "Hand events"); the comms test app and the game installed on the owner's iPhone on 2026-10-28 ask for it first and fall back to version 1 when a service refuses it (the Ultra96's did until 22:21 that night). The three monitor envelopes (2026-10-18) are at `v` 1 like them. They pass only between the service and the laptop's board view, never to or from a phone (see "Board monitor on the gateway port"). Every peer refuses any other version for each type.

An example result from a model:

```json
{"v":3,"type":"GESTURE_RESULT","session_id":"ltc-comms","device_id":1,"boot_id":305419896,"seq":42,"request_id":null,"result_id":"1:305419896:42","gesture":"CHOP","confidence":0.93}
```

Field rules:

- `session_id`: a string of 1 to 128 characters, none below U+0020 and no surrogates. It must equal the configured session, or the connection is closed. It is configuration, not a password.
- `device_id` is 1 or 2. `boot_id`, `seq` and `uptime_ms` are integers from 0 to 4294967295. `values` is a list of exactly 11 integers from −32768 to 32767, in the packet's channel order.
- `request_id` is always present in the three version-3 messages. It is `null` for ordinary samples and for model results. For a command it is an integer from 1 to 4294967295 and equals `seq`.
- `INGEST_ACK` repeats `device_id`, `boot_id`, `seq` and `request_id` of the `SENSOR_BATCH` it answers. `status` is `accepted` or `duplicate`.
- `result_id` is `device_id:boot_id:seq` in decimal, with the prefix `cmd:` when `request_id` is not null. A receiver refuses a result whose `result_id` does not match its own fields. The phone de-duplicates by `result_id` (the latest 4096).

### Label and confidence rules

- `gesture`: a string of 1 to 32 characters, each from `A–Z a–z 0–9 _ -`. Communications does not know the label set; Wen Ree and Jie Ling agree it. The six model classes `PICKUPHOLD`, `PLACEDOWN`, `CHOP`, `WASH`, `THROW` and `FIREEXT` fit.
- `confidence`: a JSON number, not a boolean, finite, from 0 to 1 inclusive. The integers 0 and 1 are allowed. It is passed on unrounded (a numpy float32 0.93 arrives as 0.9300000071525574).

The same rules are implemented identically in four places: `ultra96/protocol.py:44-53` (used by the board's `emit` before a result is sent, by the laptop's test subscribers such as `laptop/phone_simulator.py`, and by the laptop's board view for the result events of `MONITOR_UPDATE`), `phone/receiver.py`, `phone/unity/CommsPhoneCore.cs` and `CommsCore/Protocol.swift`. A result the phone rejects ends the phone session and clears its passwords, so the board refuses an invalid model result before it is sent. In the adversarial review of 2026-10-14, 11,421 result bodies were validated identically by the board's check, the Python receiver and a compiled C# harness. The Swift check is compiled and tested on Linux in a Swift 6.1 container and on macOS (its own protocol tests), and built for iOS on 2026-10-16; it was not part of that comparison.

All three network participants must use the same session. For the `demo.py` commands, `--session-id` or `LTC_COMMS_SESSION` changes it; for `tools.deploy_service`, `--session-id`; the phone app has it compiled in. The Ultra96 service started for Week 7 used `week7-demo`; on 2026-10-16 the version-3 service with `ltc-comms` replaced it. ## Ingest connections on the Ultra96

A gated glove's stream is silent while the player is still. Since 2026-10-15 the service therefore no longer closes a quiet ingest connection after 5 s: that closing lost the first frames after each pause as ambiguous drops while the laptop reconnected over TLS. It still closes one that has been quiet for at least 5 s to free a slot when all eight are taken (see "Free slots"). Status: the idle limit was verified on the real Ultra96 on 2026-10-16 with the default of 600 s. Two tests each kept one ingest connection silent. The next sample was accepted after 7, 30 and 120 s in the first and after 590 s in the second; after a further 620 s of silence the board had closed the second connection. Freeing a slot ran in host tests only.

- **Idle limit.** On port 8888 the service waits up to the ingest idle limit for the first byte of the next frame. Once it arrives, the rest of the header and the body must arrive within 5 s (`read_frame` with `idle_timeout`, `common/wire.py:49-83`; `_ingest`, `ultra96/server.py:320-352`). The limit is set with `--ingest-idle-timeout SECONDS` (default 600, allowed 5 to 86400) or the constructor argument `ingest_idle_timeout` (any positive finite number of seconds). A connection that stays silent longer is closed and counted in `rejected`. `tools.deploy_service` and `demo.py service --start` pass no such option, so the default applies. The idle limit does not apply to the gateway port 9999.
- **Free slots.** Both ports share eight client connections (`MAX_CLIENTS`, `ultra96/server.py:47`). When all eight are taken and another client connects, the service closes the ingest connection that has waited longest for its next frame, if it has waited at least 5 s (`_evict_idle_ingest`, `ultra96/server.py:249-263`; counted in `idle_evicted`, with a warning in the log). It admits the newcomer once that connection has closed. It waits up to 2 s for this; if the slot is still taken, the newcomer is refused (`client_limit`, `ultra96/server.py:239-242`). The eviction frees the slot of a laptop that vanished while the SSH tunnel's `sshd` still holds its socket. A streaming connection, the phone's connection and a board monitor's connection (see "Board monitor on the gateway port") are never closed this way; if none qualifies, the newcomer is refused (`client_limit`). A live glove that was only still reconnects when it next sends, and loses the frames then in flight, as under the old 5 s limit.

## Results: model results and command echoes

For each `SENSOR_BATCH` the Ultra96 service checks the message, de-duplicates it and then writes the `INGEST_ACK` (`ultra96/server.py:320-352`):

- **A new sample** (`request_id` null) goes to the model's `on_sample` before the ACK is written. Results come only from the model, through `emit`.
- **A new command** (`request_id` set) never reaches the model. Its values are transformed dummy rows and its `seq` comes from the command space, so it would corrupt the model's windows. The service itself publishes one command echo: a random label from `REST`, `FIST`, `OPEN`, `POINT`, confidence 1.0, `request_id` = `seq`, `result_id` `cmd:device_id:boot_id:seq`. Echoes come only from the owner's command tests on the laptop.
- **An exact retry** of an identity already accepted gets `status: duplicate` and reaches neither the model nor the phone. The laptop treats a duplicate ACK for a command as an error. A different payload under an identity already seen closes the connection.

Replay protection lives in memory only. For each `(device_id, boot_id)` the service keeps a high-water mark of `seq` that only rises; it also keeps the latest 4096 sample fingerprints across all pairs together (`ultra96/server.py:157` and `:419-420`), so with two gloves streaming at the same rate each has about 2048. A sample at or below its pair's mark that is not among them is refused and the connection closed. Commands use a separate ledger. One process allows at most 128 `(device_id, boot_id)` pairs and 4096 commands, never evicted; after that the service refuses new ones and must be restarted. Replay protection across a restart needs a fresh session ID.

A model result is checked twice. `emit` checks the shape at once (`normalize_result` and `emit`, `ultra96/model.py:84-100` and `:168-187`): the label and confidence rules, `device_id` 1 or 2, `boot_id` and `seq` uint32; a result that fails is counted on the event loop (`model_results_rejected`). On the event loop the service then refuses a result that names a `(device_id, boot_id)` with no accepted sample in this process, or a `seq` above the highest one accepted for it (`model_results_rejected`), and a result whose `result_id` was already emitted among the latest 4096 (`model_results_duplicate`) (`_model_result`, `ultra96/server.py:362-389`). Otherwise it publishes a `GESTURE_RESULT` with `request_id: null`. A `seq` inside a gap (never received, but below the highest accepted) is not detected. **Each result must name a different sample**; usually the newest one in the model's window, from either glove.

**The dummy model.** Without `--model`, the service uses its built-in dummy model (`ultra96/model.py:38-50`): for every accepted sample it emits one result for that same sample, with a random label from `REST`, `FIST`, `OPEN`, `POINT` and confidence 1.0. These labels are not game actions. With the dummy model every accepted input (sample or command) gives one result on the board, so `demo.py`'s `Phone expected increase` and the rehearsal checks hold. They do not hold for a real model, whose result rate waits for Wen Ree's answer.

Delivery to the phone is unchanged from version 2: one subscriber at a time (a newcomer replaces it), a queue of 32 results with the oldest dropped when full, a 2 s limit on waiting on the board, and results dropped at once when no phone is subscribed. Results are not resent. A board monitor (next section) is not a subscriber: it neither replaces the phone nor takes any of its results.

## Board monitor on the gateway port

The live view of `python demo.py start` shows, per glove, what the Ultra96 accepted, each model result and whether it was written to the phone. Model results exist only on the Ultra96 (an `INGEST_ACK` carries none, and `GESTURE_RESULT` goes only to the subscriber), so the laptop reads them over a read-only connection to the gateway port 9999, reached through a second local forward (`127.0.0.1:19999` → `127.0.0.1:9999`) in the same SSH login as the samples. That connection sends `MONITOR`, never `SUBSCRIBE`, so it never claims or replaces the phone's subscription and takes none of its results. A third port was not added because the deploy tool's port checks and rollback and the `demo.py service --start` guard know only 8888 and 9999; the event log was not used because it may not carry labels (decision D40, hand-off 6.5). The board side is `ServiceMonitor` in `ultra96/monitor.py`, entered from `_gateway` in `ultra96/server.py`; the envelopes and their check are in `ultra96/protocol.py`; the laptop side is `laptop/board_monitor.py`. Status: built and tested on the laptop on 2026-10-18 (`tests/test_ultra96_monitor.py`), committed as `2b3be2b`, and on the Ultra96 since the owner's redeploy of 2026-10-19 (PID 147215); the board view connected to it in both runs of that night. The Ultra96 still runs the service deployed on 2026-10-16, which has no monitor: it reads `MONITOR` as an invalid `SUBSCRIBE`, closes the connection and counts it in `rejected`, and `demo.py start` then runs without its board view. The Ultra96 runs the service with the monitor since the owner's redeploy of 2026-10-19 (step 1 of "Running the updated software").

Unchanged by the monitor: the 38-byte packet, `SENSOR_BATCH`, `INGEST_ACK`, `SUBSCRIBE`, `SUBSCRIBED` and `GESTURE_RESULT`, the ports (8888 and 9999 on loopback), and the phone's subscription and delivery (see "Results"). A phone (the Swift client, the C# and the Python receivers) never sends `MONITOR` and never receives a monitor envelope, so the phone clients are unaffected. The monitor envelopes are at `v` 1, like the subscription envelopes.

**The exchange.**

- The laptop opens a TLS connection to port 9999, as a subscriber does, and sends `{"v":1,"type":"MONITOR","session_id":"<session>"}` as its first frame, which must arrive within 5 s, as a `SUBSCRIBE` must. The service tells the two apart by the first frame's `type`; any other first frame is checked as a `SUBSCRIBE`, as before. `MONITOR` is checked strictly: exactly these three keys, `v` the integer 1, and the configured session. A refused `MONITOR` closes the connection and is counted in `rejected`, and so is a `MONITOR` sent to the ingest port 8888.
- The service answers once with `{"v":1,"type":"MONITORING","session_id":"<session>"}`, then sends one `MONITOR_UPDATE` every 0.25 s (`MONITOR_INTERVAL`, `ultra96/protocol.py`). While events are waiting it sends up to 4 updates back to back in one tick (`FRAMES_PER_TICK`, `ultra96/monitor.py`).
- After `MONITOR` the connection is send-only, like a subscriber's after `SUBSCRIBE`: any byte from the laptop, or its EOF, ends the session (not counted in `rejected`). A write that has not drained within 2 s, or a write buffer that stays above 16384 bytes for more than 2 s (the service skips ticks while it is above), ends it and is counted in `rejected`.
- One monitor at a time: a new `MONITOR` replaces the attached one, whose connection is closed and aborted at once so that it frees its slot. A monitor connection takes one of the eight shared client connections (`MAX_CLIENTS`) and is never closed to free a slot (see "Free slots").
- The monitor never touches the phone's subscription: not the subscriber, its queue of 32 results, the `subscribers` or `replaced` counters, nor the event log (`--event-log-dir`). The service's standard output lines and the keys of its `stopped` line are unchanged.

**`MONITOR_UPDATE`.** Exactly these 13 keys:

| Key | Type | Value |
|---|---|---|
| `v`, `type`, `session_id` | integer, string, string | 1, `MONITOR_UPDATE`, the configured session |
| `update` | integer ≥ 0 | 0 for the first update on each connection, then +1 for each update |
| `uptime_seconds` | number ≥ 0 | Seconds since the service started (monotonic clock, rounded to 3 decimals) |
| `model` | string of 1 to 128 printable characters | The model's name: `dummy` for the built-in dummy model, otherwise the model module's name (cut to 128 characters, with `?` for a character that is not printable) |
| `subscriber` | integer ≥ 1, or `null` | The current subscriber's number, or `null` when nothing is subscribed. Each `SUBSCRIBE` the service accepts takes the next number from 1 (the `subscriber_id` of the event log) |
| `identities` | integer ≥ 0 | `(device_id, boot_id)` pairs with an accepted sample in this process |
| `identity_limit` | integer ≥ 1 | The most pairs one process accepts (128; see "Results") |
| `devices` | object with exactly the keys `"1"` and `"2"` | Each glove's counters (below) |
| `service` | object | Exactly `rejected`, `client_limit`, `idle_evicted`, `subscribers`, `replaced`, `model_samples`, `model_errors`, `model_slow_calls` and `model_results_late` (integers ≥ 0) and `model_max_call_ms` (a number ≥ 0): the service's counters of these names, which its `stopped` line prints at shutdown |
| `events` | list of at most 100 arrays (`MAX_MONITOR_EVENTS`) | The events since the previous update, oldest first (below) |
| `events_dropped` | integer ≥ 0 | Events lost on this connection because its buffer was full |

Each glove's counters are integers ≥ 0, cumulative since the service started and kept whether or not a monitor is attached (plain integers updated on the service's event loop, with no I/O; only the monitor's own task encodes and writes updates):

| Counter | Counts |
|---|---|
| `accepted` | New inputs (samples and commands) answered `accepted` |
| `duplicates` | Exact retries answered `duplicate` |
| `results` | Model results that passed the event-loop checks and were published |
| `commands` | Command echoes published |
| `refused` | Model results that the event-loop checks refused (`unknown_identity` or `duplicate`; see "Results") |
| `sent` | Results and echoes written completely to the subscriber's connection: the point the event log records as `result_write_complete`. It is not a phone receipt |
| `unsent` | Results and echoes not written: no subscriber, dropped as the oldest of a full queue, dropped after 2 s, abandoned when the subscription ended, or a failed or cancelled write |

Every published result or echo ends in exactly one of `sent` and `unsent`, so once nothing waits in the queue or is being written, `results` + `commands` = `sent` + `unsent`.

Each event is an array whose last item `t` is the service's uptime in seconds when it happened (the clock of `uptime_seconds`):

| Event | When |
|---|---|
| `["result", device_id, boot_id, seq, gesture, confidence, t]` | A model result was published |
| `["command", device_id, boot_id, seq, gesture, confidence, t]` | A command echo was published |
| `["refused", device_id, boot_id, seq, reason, t]` | The event loop refused a model result; `reason` is `unknown_identity` or `duplicate` |
| `["subscriber", "claimed", subscriber, null, t]` | A `SUBSCRIBE` was accepted |
| `["subscriber", "ended", subscriber, reason, t]` | A subscription ended; `reason` is the one the event log records for `subscriber_ended` (for example `peer_eof`, `replaced` or `error`): 1 to 64 characters matching `[A-Za-z][A-Za-z0-9_.-]{0,63}` |

`device_id` is 1 or 2, `boot_id` and `seq` are uint32, `subscriber` is an integer ≥ 1, and `gesture` and `confidence` follow the label and confidence rules. Events are kept only while a monitor is attached, in a buffer of 4096 (`EVENT_CAPACITY`, `ultra96/monitor.py`); when it is full the oldest is pushed out and counted in `events_dropped`. Nothing from before the connection is replayed; the counters cover that time. Each update takes at most 100 events, and those that would make the frame exceed 16384 bytes wait for the next update.

An example update (the numbers are illustrative):

```json
{"v":1,"type":"MONITOR_UPDATE","session_id":"ltc-comms","update":40,"uptime_seconds":3605.25,"model":"dummy","subscriber":1,"identities":2,"identity_limit":128,"devices":{"1":{"accepted":500,"duplicates":0,"results":498,"commands":2,"refused":0,"sent":500,"unsent":0},"2":{"accepted":500,"duplicates":0,"results":500,"commands":0,"refused":0,"sent":500,"unsent":0}},"service":{"rejected":0,"client_limit":0,"idle_evicted":0,"subscribers":1,"replaced":0,"model_samples":998,"model_errors":0,"model_slow_calls":0,"model_results_late":0,"model_max_call_ms":0.08},"events":[["result",2,305419896,499,"REST",1.0,3605.241]],"events_dropped":0}
```

**On the laptop.** `laptop/board_monitor.py` runs in its own thread and event loop, apart from the capture's data path. It checks `MONITORING` and every update with `validate_message` (`ultra96/protocol.py`): exact key sets at every level, integers that are not booleans, finite numbers, and the label and confidence rules in each result and command event. On a refused frame, or 5 s without an update, it closes the connection and reconnects, with a back-off of up to 5 s. Before its first `MONITORING`, a service that closes the connection after `MONITOR` (one that predates the monitor, or one configured with another session) is not asked again in that run, and `demo.py start` continues without the board view; after one, the same answer counts as an outage and it keeps reconnecting. The `sent` counts give the summary of `demo.py start` the number of results the Ultra96 wrote to the phone during the run (see "Running the updated software").

**The service log.** In the same change the service stopped logging one INFO line per accepted input (`LOG.info("accepted session=… device=… boot=… seq=…")` in `_ingest`). It was synchronous standard-error output before every ACK, nothing read it, and on the board it went without bound into the service log under `BOARD_ROOT/evidence/`. The `accepted` counter of each glove replaces it.

## Separate model process: the runner socket (`ultra96/model_bridge.py`)

For a model that cannot run inside the service process (the service runs as `xilinx` with `/usr/bin/python3` and no sudo). Built on 2026-10-18 and tested on Linux with the service and a runner as two processes. On the Ultra96 since 2026-10-19 (17:50 +08:00): Wen Ree's runner, started by `tools.deploy_service --runner-module`, loaded its bitstream and connected; no result has been seen yet.

- **Start.** The service runs with `--model ultra96.model_bridge` (no `--model-path`). One deploy command starts both: `python -m tools.deploy_service --model ultra96.model_bridge --runner <board path of the runner script>` starts the service, then the runner as root through sudo (the owner types the sudo password), with `/usr/local/share/pynq-venv/bin/python` (`--runner-python` changes it; `--runner-arg` adds arguments), in a login shell, in the script's folder, and replaces the runner it started last (`ultra96/model_runner_launch.py`). A runner started as a module from its own folder uses `--runner-module <module> --runner-cwd <board folder>` in place of `--runner` (2026-10-19); for Wen Ree's runner: `--runner-module src.socket_worker --runner-cwd /tmp/cnn_conv1d/ai_integration`, with its `--weights` and `--bit` as `--runner-arg` values. A runner can also be started by hand, as any user and under any Python 3, before or after the service, but not next to `--runner`: the deploy cannot stop a runner started by hand, so stop it first. With two runners connected the launcher stops its new one again and reports `conflict`. Either way the runner is the client: it connects to a Unix stream socket that the service listens on, and it keeps running and connects again when the service restarts.
- **Socket.** `/var/tmp/cg4002-week7-yanjie-20260907/model-runner.sock` on the board: `model-runner.sock` in the deployment folder (`BOARD_ROOT`, `tools/demo_service.py:13`), or the path in the service's environment variable `COMMS_MODEL_SOCKET`. Mode 0600, owned by `xilinx`: `xilinx` and root can connect. A lock file `model-runner.sock.lock` beside it keeps a second service from taking over the socket of a running one; a socket left by a service that died is replaced at the next start.
- **Framing.** One JSON object per line, UTF-8, ended by `\n`, in both directions. A line from the runner may be at most 4096 bytes.
- **Service to runner.** First `{"type": "hello", "format": 1, "channels": ["ax", "ay", "az", "gx", "gy", "gz", "yaw", "pitch", "roll", "flex1", "flex2"]}`, then one line per newly accepted stream sample, in the order the service accepted them: `{"type": "sample", "device_id": 1, "boot_id": 7, "seq": 42, "uptime_ms": 12345, "values": [11 numbers]}`. The fields are exactly the arguments of `on_sample` (see "Board-side model interface"): `values` in physical units, in the order of `channels`; the two gloves interleaved, with no pairing or alignment. A runner ignores message types and fields it does not know.
- **Runner to service.** One line per result: `{"type": "result", "gesture": "CHOP", "confidence": 0.93, "device_id": 1, "boot_id": 7, "seq": 42}`. The fields are exactly the arguments of `emit`, under the same rules: the label rule, confidence 0 to 1, and the identity of one sample the service sent, at most one result per sample. A result may be sent at any time after its sample. In sensor-version-4 or -5 mode a runner may also send `hand_hello` and `hand_event` lines (see "Hand events").
- **Behaviour.** One runner at a time; a new connection replaces the old one, which sees the end of its stream. The service never waits for the runner: ACKs do not depend on it, and samples are not stored for it. A sample is dropped when no runner is connected, or when 1024 lines already wait for the runner (about 10 s of both gloves at 50 Hz). A line that is not JSON (including JSON nested too deeply to parse), not a result, longer than 4096 bytes or missing a field is skipped and counted, and the connection stays open; a result `emit` refuses is counted. When the service stops, the runner reads the end of the stream and should connect again (the example does, once a second). Since 2026-10-19 one glove's samples can reach the runner in small groups, up to 6 within microseconds (one BLE notification, see "Sensor notifications"), when its BLE link falls behind; at 50 Hz in the slow link state the groups are 1 or 2 samples about every 30 ms, and 3 or 4 after a skipped slot. Each line's `uptime_ms` is the glove's own clock at the sample, 20 ms apart at 50 Hz whatever the grouping.
- **Log lines.** The bridge logs `model runner connected (pid N)` (the connecting process, where Linux reports it) and `a new model runner connected; closing the previous one` when a second runner takes the connection; the launcher reads both.
- **Counters.** The bridge logs `samples_sent`, `samples_dropped_no_runner`, `samples_dropped_full`, `results`, `results_refused`, `bad_lines` and `connections` (in versions 4 and 5 also `hand_hellos`, `hand_events` and `hand_refused`) when a runner disconnects. The service's own `model_*` metrics count the samples and results as for any model.
- **Sensor versions 4 and 5.** With `ultra96.server --sensor-version 4` or `5` the hello names the twelve channels (`flex3` last) and offers hand events, and each sample carries 12 values in physical units; the two versions give the runner the same hello and the same units (version 5's gyro restored with its scale 10 before the bridge). `configure_sensor_version` sets this before the bridge starts and refuses a change afterwards. An eleven-channel runner must not be started against it (`tools.deploy_service` refuses `src.socket_worker` and `src.socket_worker_full` with `--sensor-version 4` or `5`), nor the hand12 worker against version 3. The runner is not told which of 4 and 5 the service runs; the staging tool takes the version from the bundle so that the two match.
- **The hand12 runner (Wen Ree's `src/socket_worker_hand.py` with Communications' compat delivery, since 2026-10-28; from 2026-10-27 to 2026-10-28 the deleted Communications adapter `ultra96/hand_runner.py`).** It runs Wen Ree's `src.hand_runtime.HandEngine` and `src.hand_events.EventEncoder` unchanged, one engine and one encoder for both hands, with his hand12 backend (`src.hand_backend`, NumPy or the FPGA overlay `cnn_hand12_v1`), and delivers in **compat mode** through this socket: each `pulse`, `state_start`, `state_refresh` and `idle` event becomes one result line, `device_id` = the hand that made it, `boot_id` and `seq` = the source sample of the event; `state_end` and `reset` events are logged only, because a version-3 result has no place for them (the owner's decision, 2026-10-27). Each source sample gets at most one result. It accepts only the twelve-channel hello (the eleven-channel one ends it), a hand is reset by the engine itself on a new `boot_id`, a `seq` jump or a receive gap over 0.5 s, without touching the other hand, and it connects again after every end of the bridge connection with a fresh worker epoch. `--observe-only` sends nothing. Since 2026-10-28 it also sends Wen Ree's structured `HAND_EVENT` envelopes when the bridge offers them, as `hand_event` lines beside the unchanged result lines (see "Hand events"); the compat results do not change.
- **Example.** `ultra96/model_runner_example.py` is the smallest runner: standard library only, it imports nothing from this repository and can be copied. The model goes where it is marked.

## Per-result function on the phone: `CommsNextResult`

The game takes results one at a time with a fourth C function of the Swift package (`Sources/CommsBridge/DisplayMailbox.swift:27-47` and `:70-74`, queue in `Sources/CommsCore/DisplayState.swift`). **Status: compiled and tested on Linux in a Swift 6.1 container (72 tests, `DisplayMailboxTests` and `DisplayStateTests` among them, 2026-10-15) and on macOS (73 tests on 2026-10-16, then 76 with that day's fix to the setup saving); built for iOS on 2026-10-16. The rebuild of the Week 7 export of 2026-10-16, signed and installed on the owner's iPhone that day, defines it, but nothing in that export calls it; in the acceptance run of 2026-10-17 that app received its results through the display text. Its limits are provisional.** The game can take results with it only from a game build that calls it: on the owner's iPhone, from 2026-10-18 Jie Ling's export `ConnectionTest_V2` (that game was gone from the phone at about 22:58 on 2026-10-28), and since 23:00 that night her `SinkTest_V1 2` (as `com.CG4002.unityTutorial.olson`), whose code calls it.

```c
int32_t CommsNextResult(char* buffer, int32_t capacity);
```

In C# (only in the iOS build, so inside `#if UNITY_IOS && !UNITY_EDITOR`): `[DllImport("__Internal")] static extern int CommsNextResult(byte[] buffer, int capacity);`

- Queue: every result the client accepts (version 3, the rules above, a `result_id` not among the latest 4096) is appended with its arrival time. At most 32 wait; when the queue is full, the oldest is dropped and counted (`pendingDropped`). A result that has waited 2 s or more since it reached the phone is dropped and counted (`pendingExpired`) the next time the queue is examined, also when only `CommsCopyDisplay` is polled.
- One call first drops expired results, then looks at the oldest one left:
  - none: returns 0 and writes nothing;
  - the buffer is null or smaller than the result's bytes plus a terminating 0: writes nothing, keeps the result queued and returns −(bytes + 1), the capacity needed;
  - otherwise: writes the result as one compact UTF-8 JSON object plus a terminating 0, removes it from the queue and returns the number of bytes (without the 0).
- The object is `{"result_id":"…","gesture":"…","confidence":…,"device_id":…}`, for example `{"result_id":"1:305419896:42","gesture":"CHOP","confidence":0.93,"device_id":1}`. `confidence` is written as Swift prints the received number (`1.0`, not `1`). With labels of at most 32 characters a result is well under 512 bytes.
- A new Connect and a stop (Disconnect, the app becoming inactive, `CommsStop`) empty the queue; a new Connect also resets the counters. An automatic reconnect keeps the queue, and so does a terminal error, which reports only a status (`DisplayState.clear`); the waiting results still expire.
- It never blocks. Call it on the main thread every frame, in a loop while it returns a positive number. Each result that is not dropped is taken out at most once; results lost before the phone never arrive.

The C# reference receiver differs on one point. Its queue (`FreshResultQueue` in `phone/unity/CommsPhoneCore.cs`, created with 32 results and 2 s at `CommsPhoneReceiver.cs:44`) is emptied at every connection attempt, automatic reconnects included (`CommsPhoneCore.cs:387` and `:426`).

No phone app has connected to the board's hand-event service yet. It runs **beside** the compat results: the `GESTURE_RESULT` stream, its counts, its de-duplication and the board monitor's numbers are the same with or without it. A field guide for the game is [hand-events-for-the-game.md](hand-events-for-the-game.md).

**The event** is Wen Ree's envelope, unchanged (`common/hand_contract.py`, `_EVENT_FIELDS` and `validate_event`; his `docs/HAND_COMMS_INTEGRATION.md`), exactly these 15 keys:

```json
{"v":4,"type":"HAND_EVENT","event_format":1,"session_id":"ltc-comms","worker_epoch":"006cd40f2e970c1f106915264e6d84e8","device_id":2,"event_seq":1,"event_id":"006cd40f2e970c1f106915264e6d84e8:2:1","kind":"state_start","gesture":"WASH","confidence":0.509,"source":{"boot_id":3866574055,"seq":105192,"uptime_ms":68404947},"state_id":"006cd40f2e970c1f106915264e6d84e8:2:1","lease_ms":1000,"reason":"confirmed"}
```

- `device_id` 1 = LEFT hand, 2 = RIGHT hand. `worker_epoch` is 32 lowercase hex, new for every connection of the worker to the bridge. Each hand has its own `event_seq`, 1, 2, 3, ... within an epoch (at most 2^53 − 1), and `event_id` is `worker_epoch:device_id:event_seq`.
- `kind` and `gesture`: `pulse` with `PICKUP`, `DROP` or `THROW`; `state_start`, `state_refresh` and `state_end` with `CHOP`, `WASH` or `POURING`; `idle` with `IDLE`; `reset` with null.
- `confidence`: a number in [0, 1] for `pulse`, `state_start`, `state_refresh` and `idle` (the worker sends it only strictly above its threshold); null for `state_end` and `reset`.
- `source`: the sample the event came from, an object of exactly `boot_id`, `seq` and `uptime_ms` (uint32). It may be null only for `reset` (a reset may also carry the hand's last source: Wen Ree's `EventEncoder.reset` copies it). Two events may name one sample: a CHOP-to-POURING transition is `state_end` CHOP then `state_start` POURING, with different `event_id`s.
- `state_id`: a `state_start`'s own `event_id`; on `state_refresh` and `state_end` the state they belong to; null otherwise. `lease_ms`: the worker's lease (100 to 2000; 1000) on `state_start` and `state_refresh`, 0 otherwise. A consumer that sees no refresh within `lease_ms` ends the state on its own clock.
- `reason`: `confirmed` on the four prediction kinds; on `state_end` and `reset` one of `confirmed_transition`, `prediction_timeout`, `source_reset`, `connection_reset`, `worker_disconnect`, `manual_reset`.

**Runner socket** (`ultra96/model_bridge.py`; see "Separate model process"). In sensor-version-4 mode the bridge's hello carries `"hand_events": 1`. A runner that sees it may send, besides its `result` lines:
- once per connection, before anything else: `{"type": "hand_hello", "hello": H}`, H being Wen Ree's format-2 hello (`make_hello`: `type`, `format`, `sensor_version`, `channels`, `class_names`, `event_format`, `session_id`, `worker_epoch`, `lease_ms`, `confidence_threshold`, `confirmations`);
- `{"type": "hand_event", "event": E}` for each event E, unchanged.
Wen Ree's worker `src/socket_worker_hand.py` does both (since 2026-10-28): every event of its encoder, all six kinds, the hand line before the event's compat `result` line, which is unchanged. In version-3 mode the hello has no `hand_events` and hand lines are bad lines. The bridge hands the lines to the service through the model port's optional `start_hand_events(emit_hand)` (`emit_hand(kind, payload, connection)`, `kind` `hello`, `event` or `closed`, thread-safe like `emit`) and counts `hand_hellos`, `hand_events` and `hand_refused`.

**The service** (`ultra96/hand_gate.py`, `HandGate`, versions 4 and 5 only; it uses Wen Ree's `ultra96/hand_admission.HandAdmission` unchanged, whose sample check accepts versions 4 and 5 since 2026-10-29, see "Sensor version 5"). Every newly accepted stream sample goes to the gate with its acceptance time, before the model. A hello is checked against the session and starts a new epoch on its runner connection (both hands' states and `event_seq` marks start afresh); the last 512 samples per hand are replayed into a new admission ledger, so an event can name a sample accepted before the hello. Each event is then checked, on the event loop, in this order:
1. its runner connection is the current one and has a hello (`no_hello`, `not_current`);
2. Wen Ree's admission: the schema against the hello, an exact accepted source, and for a prediction the hand's current boot and a source accepted at most 0.5 s earlier (`invalid`, `stale_source`);
3. de-duplication by `event_id`: the same `event_seq` again is `duplicate`, a lower one `out_of_order`;
4. the hand's state, on the service's clock: an expired lease ends the active state (`hand_states_expired`); a `state_refresh` must name the active state and gesture (`orphan_refresh`); a `state_end` must name the active state or the state the gate itself last ended for that hand (by expiry or a glove reconnect), so the worker's own end still gets through (`orphan_end`); `state_start`, `pulse`, `idle` and `reset` end any active state.
A new `boot_id` on one hand (its glove reconnected or restarted) ends that hand's state only (`hand_resets`); a runner connection that closes ends both (`worker_disconnect`). The gate never creates or changes an event: an accepted one is published exactly as the runner sent it. Metrics: `hand_hellos`, `hand_hellos_refused`, `hand_events_accepted`, `hand_events_refused`, `hand_events_duplicate`, `hand_states_expired`, `hand_resets`, `hand_events_published` (put on a version-2 subscriber's queue), `hand_events_unrequested` (the subscriber is version 1), `hand_events_no_subscriber`, `hand_events_dropped` (queue drops and stale), `hand_gate_errors`. Observer events (`--event-log-dir`): `hand_hello_accepted`, `hand_hello_refused`, `hand_event_published` (every accepted event, also one then counted as unrequested or with no subscriber), `hand_event_refused`, `hand_state_ended`, `hand_event_enqueued`, `hand_event_write_complete`, `hand_event_dropped`. Hand events touch neither the board monitor's per-glove counters nor the result observer events; `MONITOR_UPDATE` is unchanged.

**Subscription.**
- Version 1, unchanged: `{"v":1,"type":"SUBSCRIBE","session_id":S}`, answered by `{"v":1,"type":"SUBSCRIBED","session_id":S}`, then `GESTURE_RESULT` frames only.
- Version 2, opt-in: `{"v":2,"type":"SUBSCRIBE","session_id":S,"event_format":1}`, answered by `{"v":2,"type":"SUBSCRIBED","session_id":S,"event_format":1}`, then `GESTURE_RESULT` and `HAND_EVENT` frames in one ordered stream. A version-3 service answers it too and sends only results.
- **Why opt-in:** every receiver installed or released before 2026-10-28 treats any frame after `SUBSCRIBED` as a `GESTURE_RESULT` and closes the connection on anything else (the Swift client's flat parser also refuses a nested object and more than 10 keys), so a `HAND_EVENT` would disconnect any app built before 2026-10-28 (the comms test app and the game installed on the owner's iPhone on 2026-10-28 have the new client; builds on other phones may not). A client accepts only the `SUBSCRIBED` of the version it sent (`ultra96.protocol.validate_subscribed`).
- The two kinds share the subscriber's queue (32 frames, 2 s): when it is full, the oldest `HAND_EVENT` gives way first, and with only results queued a new `HAND_EVENT` is dropped itself, so results are dropped only as for a version-1 subscriber.
- An older service refuses a version-2 `SUBSCRIBE` (it closes the connection before `SUBSCRIBED`). The Swift and C# clients, which ask for version 2 by default, then subscribe with version 1 for the rest of that client's life; the Swift status reads `...; no hand events from this service; retrying with subscription version 1`.

**Phone side** (Swift `CommsNative`, the C# core `phone/unity/CommsPhoneCore.cs`, the Python `phone/receiver.py --hand-events`). Each client dispatches the frames after `SUBSCRIBED` by `type`: `GESTURE_RESULT` exactly as before; `HAND_EVENT` (on a version-2 subscription only) checked without the hello by the rules above (15 keys, types, ranges, `event_id`, the kind/gesture/confidence/state/lease/reason pairing; the threshold needs the hello and is the service's check). A `HAND_EVENT` that fails is counted and dropped and the connection stays open, so the results are not lost with it; a frame that is not JSON, or of any other type, closes the connection as before. A per-hand tracker (as Wen Ree's `EventConsumer`, on the phone's own clock) keeps, per hand, the highest `event_seq` of the current epoch (equal: duplicate; lower: out of order; both ignored), ends both hands on a new `worker_epoch`, starts, refreshes and ends states only by matching `state_id`, ends a state when its lease runs out, and resets when the phone subscribes again. The Swift package exports two more C functions with the return convention of `CommsNextResult`: `CommsHandState` (both hands' state as JSON, never 0) and `CommsNextHandEvent` (the next accepted event as JSON; 64 waiting at most, 2 s each). On 2026-10-28 the three clients made the same decision on every one of 2,407 real `HAND_EVENT` frames of the laptop runs.

## Protected BLE controls

Controls use the same service: the write characteristic `6e1c0007-7a45-4dc4-b678-3f2d5a9c1001` and the response notifications `6e1c0008-7a45-4dc4-b678-3f2d5a9c1001`. Both require authenticated, encrypted BLE permissions, and the firmware checks that the request comes from the current peer.

Every control message begins with the 14-byte little-endian header `<2sBBBBII` (`common/control.py:16`):

| Field | Meaning |
|---|---|
| Magic/version | `B7`, control protocol 1 |
| Opcode | 1 command; 2 rate; 16 begin file; 17 chunk; 18 end; 19 abort |
| Device | 1 or 2 |
| Status | Request 0; response 0 OK, 1 invalid, 2 busy, 3 ordering, 4 integrity, 5 conflict, 6 unsupported |
| ID | Nonzero uint32 request/transfer identity |
| Offset | uint32 file offset; zero for commands/rate/abort |

A response sets bit 7 of the opcode. Controls require a negotiated ATT MTU of at least 64 (`MIN_CONTROL_MTU` in `common/control.py:14`, `controlFitsMtu` in `comms_control.h:31`). Payloads are at most `min(180, MTU - 3 - 14)` bytes: 47 at the floor, 180 from MTU 197. Each BLE write carries exactly one control message; the network framing does not apply here.

The two MTU floors are separate: sensor notifications need 41, controls need 64.

**Commands.** The payload is exactly one 38-byte version-3 sensor packet, so a command frame is 52 bytes and so is its response. The laptop builds it from a random fixture row: marker `LC`, version 3, this board's `device_id`, the board's current `boot_id` (read from the source statistics), `seq` equal to the request ID, and `uptime_ms` 0. Before the command changes any state, the firmware answers "invalid" to a payload of another length, marker, version, device or boot, or with a `seq` that differs from the request ID (`comms_control.h:129-133`). The response carries the same packet with `uptime_ms` replaced by the board's clock and 1 added to each of the 11 values, 32767 wrapping to −32768. The sensor stream keeps its own sequence and accounting. The firmware needs at least 52 bytes of output space for a response (`kControlMinOutput` = 14 + max(38, 36), the larger of a sensor packet and the 36-byte file metadata, `comms_control.h:16-20`).

The laptop stores the original and the expected values, verifies the response, and forwards the returned packet over its own TLS connection as a `SENSOR_BATCH` with `request_id` = `seq`; the Ultra96 answers it with one `cmd:` echo (see "Results"). The firmware caches eight command responses per connection and rejects older evicted requests; IDs increase within a connection. A disconnect clears the local control state. The Ultra96's command ledger stops a repeated command identity from causing another result.

One control transaction is active per device. Keyboard keys `1` and `2` submit a random command to the corresponding device without Enter. Each device has a bounded queue of eight waiting commands. Overload or a disconnect rejects explicitly. Accepted commands finish or are recorded as failed; a timeout is not retried automatically. A board ACK is evidence of ingestion and does not prove phone receipt.

**Rate.** Rate commands carry a uint16 in Hz (1 to 200) and return the accepted rate. They change the board's pacing. These are configurable operating points, not measured maximum-speed claims.

On supported Windows versions, rates above 10 Hz also request the operating system's throughput-oriented BLE connection preference for that connection's lifetime. Reports distinguish request acceptance from the observed interval, peripheral latency and supervision timeout. The preference is released during cleanup; unsupported or denied requests remain visible as diagnostics. This trades power and available concurrent connections for throughput, so sustainable performance still requires a measured two-board capture. ATT MTU alone does not establish the connection interval or the link-layer data length.

## Files

The supported direction is laptop to ESP RAM, 1 to 65536 bytes. Begin carries 36 bytes: the uint32 length and the SHA-256 digest. Ordered chunks contain file bytes at the declared offset. Responses carry the next expected offset. Identical already-received bytes may be retried; missing, out-of-order or conflicting chunks are rejected. End succeeds only after the entire file has arrived and the receiver has computed and matched its digest; its response returns the length plus the computed digest (36 bytes, a 50-byte frame).

The client retries an identical chunk up to twice after a timeout. Failure aborts, and a disconnect or 30 seconds of receiver inactivity discards an unfinished file. Restart with a new transfer ID. Resuming after power loss is not supported. Files and commands use separate accounting from sensor goodput.

With the NUS VPN connected and the phone subscribed, it opens the SSH tunnel itself, so no tunnel terminal is needed: one OpenSSH process through both hops (Windows' own `ssh.exe`) with two forwards, `127.0.0.1:18889` → 8888 for the samples and `127.0.0.1:19999` → 9999 for the board view. The owner types both passwords at OpenSSH's own prompts, and nothing is stored. It then captures both gloves at 50 Hz unless `--rate` is given, shows a live view per glove that is redrawn in place (each step's count and rate, the latest packet, the newest model results), and stops on q, Ctrl+C or `--duration`. Its run folder holds one log, `run.log`, with every packet and ACK, every model result while the board view is connected, and at its end the report, a summary and the same `CAPTURE PASSED` check as `demo.py report`. Its board view sends `MONITOR`, not `SUBSCRIBE`, so the phone keeps its subscription. To show model results and delivery to the phone it needs the redeployed service (step 1); against the service deployed on 2026-10-16 the run works without it and shows those counts as `n/a`. `python demo.py tunnel` now opens both forwards too, so `python demo.py start --no-tunnel` can use a tunnel that is already open.

A write on the board is not a phone receipt.

Reports include per-device and combined decimal kbps. The boundary is unique valid 38-byte sensor packets received at the laptop, including application headers and excluding BLE/TLS/SSH overhead, commands and files. ## History: what version 3 replaced

Version 2 was current until 2026-10-14 and is described in `docs/co-protocol-v2.md` at commit `c42b386`. Version 3 removed:

- The 32-byte sensor packet (`<2sBBIII8h`, the same 16-byte header with eight int16 values) and its version bytes 1 and 2. The sensor MTU floor was 35, a command frame 46 bytes, and the firmware's control output floor 50 bytes.
- Version 1, the deterministic-formula dummy: values computed from `seq` (`dummy_values(seq)` in Python, `dummyValue` and `serializeDummyPacket` in the firmware, selected with `COMMS_LEGACY_DUMMY=1`), the receivers' formula checks, and a result label fixed by `seq % 4`. Reproducible dummy data now comes only from `-DCOMMS_FIXTURE_SEED` and `--seed`.
- The source-statistics marker `LCS1`.
- `SENSOR_BATCH`, `INGEST_ACK` and `GESTURE_RESULT` at `v` 1 (without `request_id`) and `v` 2 (with it); updated receivers had accepted both result versions.
- The fixed result vocabulary: every receiver accepted only `REST`, `FIST`, `OPEN`, `POINT` with confidence 1.0, and every accepted input got one dummy result directly from the service. There was no model interface.
- The server's capacity parameters `max_v2_namespaces` and `max_v2_commands`, now `max_namespaces` and `max_commands` with the same limits (128 and 4096).

Earlier on 2026-10-14 the cleanup merged as PR #18 had already removed the Week 7 markers `W7` and `W7S1`.

Within version 3, on 2026-10-15: the source statistics grew from 24 bytes (`<4sB3xIIII` with `LCS3`, which ran only on the right board) to 36; a board now sends a sample only when its glove module reports MOVING (the default dummy module always does), so a gated board is silent while its glove is still; and the Ultra96 stopped closing an ingest connection after 5 s without a frame. It now waits up to the ingest idle limit (600 s by default), and closes a connection quiet for at least 5 s only to free a slot when all eight are taken.

Within version 3, on 2026-10-18 (built and tested on the laptop; committed as `2b3be2b`, on the Ultra96 since 2026-10-19): the gateway port gained the board monitor's three envelopes at `v` 1 (`MONITOR`, `MONITORING`, `MONITOR_UPDATE`; see "Board monitor on the gateway port"), and the service stopped logging one INFO line per accepted input. No existing message, field, limit or port changed.
