## Purpose and boundaries

- This chapter answers four questions. How do we prove the code is correct (tests)? What was measured on real hardware (evidence)? How do we operate and redeploy on site (operations)? What must Communications change in its own code when real data and the real model arrive (extension points)?
- Communications only sends each module's data out and confirms that the next module receives it accurately. It passes every result through unchanged and never merges, splits, filters or reinterprets results. Pairing the left and right gloves, building model windows, deciding gesture or idle, model accuracy, mapping labels to game actions, and any script in `vis/` are teammates' work. Wen Ree and Jie Ling agree between themselves the label names, how often a label fires, and whether several identical labels in a row mean one action or several. The division of work at each hand-over is the table in section 3.1 of the hand-off document (the owner's proposal, final when the teammates confirm it). This chapter does not cover the teammates' parts.
- Evidence has 5 levels. No level replaces another. Level 1 is `submitted` in the board's source statistics. Level 2 is the laptop's `received`. Level 3 is `INGEST_ACK`. Level 4 is the Ultra96 event `result_write_complete`. Level 5 is `Received` on the phone screen. `CAPTURE PASSED`, printed by `demo.py`, is level 3. It proves only that the Ultra96 service accepted the input. It does not prove that the phone received the result.
- On level 2: the report field `received` counts the packets that the writer task took from the queue and processed (`laptop/bridge.py:399`). The BLE callback count is a separate field, `callback_received` (`laptop/bridge.py:301,999`). The progress line prints the callback count as `received=` and the report's `received` as `processed=` (`laptop/dual_bridge.py:145-146`). The two differ when the queue drops packets.
- Current identifiers: packet magic `LC`, statistics magic `LCS1`, session ID `ltc-comms`, local evidence folder `.comms-local/`. Since 2026-10-14 the code accepts only this set. For the old identifiers see "History and removed items".
- The connection is settled. The laptop and the phone each dial out through the VPN, `stujump:22` and port 22 of the Ultra96. Ports `8888` and `9999` on the Ultra96 are reached only through the SSH channel. This chapter does not discuss other routes.
- Teammates' code is read-only. This chapter cites `hardware/`, `src/`, `models/` and `vis/` only to show what the interfaces already reveal in the teammates' code. It does not describe their internal implementation.
- The archived design records and measurement records cited here are under `docs/archive/`. The whole `docs/` folder exists only on olsonwangyj's fork, not in the team repository. Teammates who clone the team repository cannot see these sources.

The two default ports differ. `demo.py` uses `18889`. Running `tools.ssh_tunnel`, `laptop.dual_bridge` or `tools.comms_demo sender` directly uses `18888`. The tunnel and the capture must use the same port.

`LTC_COMMS_SESSION` is read once, when arguments are parsed. It affects three commands: `demo.py run`, `demo.py live` and `demo.py service --start`. A `--session-id` on the command line takes precedence. The phone's session ID is compiled into the app and does not come from this variable. The app has it in two places: `IntegrationController.swift:74` (the value the client uses) and the form text `DUMMY gestures · session ltc-comms` in `SetupViewController.swift:51`. A session change edits both. The only other environment variables in Communications scope are: `PYTHONIOENCODING=utf-8`, which `demo.py` sets for the capture child process (`demo.py:242`); the Xcode symbol-upload switch `WEEK7_ALLOW_SYMBOL_UPLOAD` (`configure_xcode.py:151-155`); and the test-only `ISH_TEST_SSHD`, `B07_TEST_LISTENERS` and `B07_TEST_SS_STATUS`.

### Extension point 1: 8 channels become 11 int16 values

The owner's direction of 2026-10-14, final when the teammates confirm; planned, not built (sections 4.2 and 8, step 1 of the hand-off document): the real-data packet is a new format, **protocol version 3**. With the 11 values only it is 38 bytes. The final layout is frozen only after Siqiang and Wen Ree answer whether the glove's IDLE/MOVING state travels, because an extra field changes the length, the MTU floor and `on_sample`. The scales are checked against the real sample log Siqiang is asked to push (proposed Fri 10-16) before they are fixed. Only the newest version is supported (the owner's rule): version 3 replaces versions 1 and 2 everywhere, including the dummy test data, which moves to the 11-value format. There is no interoperability between versions, so the firmware, the laptop, the Ultra96 service and the phone app are upgraded together.

`GESTURE_RESULT` cannot take extra fields freely. None of the four validators allows an extra field:

1. The iPhone parser accepts at most 10 fields, and a v2 result already has exactly 10. Values may only be strings, numbers or `null`. Arrays, nested objects and booleans fail, and the failure is terminal (`Protocol.swift:179,183-188`; `CommsClient.swift:199`).
2. The C# reference implementation compares the field count exactly: 9 for v1, 10 for v2 (`CommsPhoneCore.cs:46,70`).
3. The Ultra96 check and the Python receiver both require the key set to be exactly equal (`ultra96/protocol.py:46-48`; `phone/receiver.py:111-115`).
4. The field allow-list of the Ultra96 event log does not include new fields either. Extra fields make the log receipt incomplete (`ultra96/diagnostics.py:24-30,99-100`).

So one result can carry the identity of only one sample. Section 7.2 of the hand-off document already defines the model output under this constraint: the model hands over the `(device_id, boot_id, seq)` of one sample it used for the result (usually the newest one in the window; either glove is fine), and each result must point to a different sample, because the phone de-duplicates by `result_id` and drops a second result with the same identity.

Only `CommsStart`, `CommsCopyDisplay` and `CommsStop` can be called today. The firmware still sends dummy data, the Ultra96 still makes up dummy labels (`ultra96/server.py:264-267`), and every receiver still accepts only `REST`, `FIST`, `OPEN` and `POINT` with confidence 1.0. Finished documents are not finished integration.

**Glove sensor module (Siqiang), to be called by `firmware/esp32/src/main.cpp`:**

- The build environment is PlatformIO with the Arduino framework, board type `firebeetle32` (`firmware/esp32/platformio.ini`).
- The main loop ends each pass with `delay(1)` (`main.cpp:560`), so the periodic update is called about once per millisecond. The packet section (`main.cpp:500-512`) runs while it holds `connectionStateMutex` (taken at `:483`, released at `:549`), and the BLE callbacks also take this lock. So "read one sample" must not block and must not call `delay()`. The reference sketch calls `delay(100)` when a read fails (`imu_v7.ino:563`). That wait cannot stay in the integrated code.
- Initialisation must return success or failure in bounded time. `setup()` also initialises BLE (`main.cpp:420`). If initialisation loops forever, the board never advertises. The reference sketch waits forever when I2C fails (`imu_v7.ino:483-485`).
- Classic Bluetooth cannot be used. The Communications firmware uses BLE (`main.cpp:420`), and the reference sketch uses `BluetoothSerial` (`imu_v7.ino:2,439`). Both cannot hold the Bluetooth controller at the same time.
- The module must not read the serial port and must not call `Serial.begin` again. The Communications firmware already opens the serial port at `main.cpp:405`, reads the `erase-bonds` command from it (`main.cpp:373-389`), and shows the passkey on it.
- Left or right identity is set by the Communications build flag `COMMS_DEVICE_ID` (`platformio.ini:21,26`): left is 1, right is 2. The module does not handle it. The default environment `firebeetle32` sets no flag, so `COMMS_DEVICE_ID` falls back to 1 (`main.cpp:21-23`).
- Communications controls the send tick. The initial value is `COMMS_INITIAL_RATE_HZ` (default 10, allowed 1 to 200, `main.cpp:24-26,38-39`), and the laptop can change it at run time. The reference sketch outputs at 50 Hz (`imu_v7.ino:83`).
- The Communications firmware uses no GPIO or I2C, so SDA 21, SCL 22 and ADC 34 and 35 are all free.

**Ultra96 model (Wen Ree), to be called by `ultra96/server.py`:**

- The hook is at `ultra96/server.py:264-267`. This code runs synchronously inside the coroutine that receives samples, and `INGEST_ACK` is written only after it (`:273-275`). The service is a single asyncio event loop, so the model's entry point must return immediately. Otherwise the ACKs of both gloves are held up. The laptop waits at most 5 seconds for one ACK (`io_timeout` at `laptop/bridge.py:41`), and a sample's freshness limit on the laptop is 2 seconds (`laptop/bridge.py:40`).
- The result queue has no lock (`ultra96/server.py:32-77`), so results must be put into it on the service's event-loop thread. Planned, not built: the `emit` that Communications provides may be called from any thread and moves each result back onto the event loop (section 7.2 of the hand-off document). This is the owner's code.
- Samples reach the hook with gaps in `seq` after a reconnect, and they are not resent: on a BLE disconnect the laptop discards that glove's queued samples, and on a TLS reconnect the samples already written but not acknowledged count as ambiguous drops. While a glove is disconnected it makes no samples, so that time shows only as a jump in `uptime_ms` (code references under "Risks olsonwangyj must watch"; section 7.2 of the hand-off document tells Wen Ree).
- Every result the model hands over is passed on unchanged. A queued result is still subject to the Ultra96's 2-second waiting limit, which is not an end-to-end bound (see "Risks olsonwangyj must watch").
- A result's `confidence` must be a finite number. Frames are serialized with `allow_nan=False` (`common/wire.py:40`), so NaN or infinity makes the send fail.
- Result messages cannot take extra fields; see the previous subsection.
- What is deployed on the Ultra96 now is only `common/` and `ultra96/`, 10 files in total, run as an ordinary user with `/usr/bin/python3` and only the standard library.
- If the model cannot load under that interpreter and user, it runs as a separate process on the Ultra96, and Communications passes the same fields to it in a format the owner sends on Thu 10-15 (section 7.2 of the hand-off document). Wen Ree's first connectable version (proposed Fri 10-16) is pushed to the team repo: for the in-process option with its module and function names; for the separate-process option with how to start it, its dependencies, and its input and output in that format.
- The owner's direction of 2026-10-14, final when Wen Ree confirms: the model gets the 11 `values` as physical floats (section 7.2 of the hand-off document). Transport stays int16 (`ultra96/protocol.py:67-69` checks for int16 integers today). Communications decodes the values and divides each by its scale before calling `on_sample`; restoring cannot recover precision dropped when packing. Any normalisation the model needs is Wen Ree's.

**Game (Jie Ling), which will call the C functions in `ios-visualizer/CommsNative/Sources/CommsBridge/DisplayMailbox.swift` (no script in `vis/` calls them yet):**

- `CommsCopyDisplay` writes only when the text differs from the last delivered text and its byte count is strictly smaller than the buffer capacity. Otherwise it returns 0 (`DisplayMailbox.swift:10-25`). There is only one global record of the "last delivered" text, so there can be only one poller.
- `CommsStop` immediately sets the status to `Stopped`, removes the button, the form and the notification observers, and clears the passwords (`DisplayMailbox.swift:48-55`). Call it only when the app no longer uses Communications. Do not call it on a scene change or when the app goes to the background.
- Line 2 of the text is the status. `Subscribed` is set when the Ultra96 answers `SUBSCRIBE` with `SUBSCRIBED` (`Subscriber.swift:49`; `CommsClient.swift:146`). It means only that the subscription handshake succeeded. It does not prove that results are flowing.
- The display text is a status display, not a game input. It keeps only the latest result, so results that arrive between two polls can be lost, and `confidence 1.0` in it is a literal. The shown result is cleared 2 seconds after the phone received it (`DisplayState.swift:109`).
- The owner's direction of 2026-10-14, final when Jie Ling confirms; planned, not built: a fourth bridge function, `CommsNextResult`, plus a `confidence` field in the Swift `GestureResult`. Each call writes the oldest waiting result as one compact JSON object and returns the bytes written, 0 when nothing is waiting, or the negative of the bytes needed when the buffer is too small (nothing is written and the result is kept). The game calls it in a loop while it returns a positive number, with a 512-byte buffer. It promises arrival order, de-duplication by `result_id`, and that each result that is not dropped can be taken out at most once. It does not promise that every result is delivered. The provisional V1 limits (32 waiting, oldest dropped when full, dropped 2 s after reaching the phone, drops counted) and the rules for emptying the queue are in section 7.3 of the hand-off document; the limits are revisited after Wen Ree says how often results come (its section 13). The owner plans to have it ready by Sun 10-18 (its section 6.4). Jie Ling does everything in Unity: the C# that calls the Communications functions, the game logic, and the iOS Xcode export, pushing the Unity changes to the team repo (`vis/`) and the export to a separate branch with Git LFS (the export is large; the Week 7 one had 3,479 files). olsonwangyj links `CommsNative` into `UnityFramework` of that export, installs the app on the phone, and writes short integration notes.

### D. Common faults: symptom, cause, recovery

| Symptom | Cause | Recovery |
|---|---|---|
| `demo.py` exits at once with `CA file not found: …` | The file given by `--ca` does not exist. The default path exists only on the original laptop. | Pass `--ca` explicitly. |
| `Board setup is incomplete; finish python flash.py before pairing or capture.` | `boards.json` has the status `incomplete`. | Rerun `python flash.py` and finish both boards. |
| Neither board makes progress, and after 30 seconds `startup:TimeoutError` appears in the runtime failures | The boards are not powered or not in range, or the laptop's Bluetooth is off. Each scan is limited to 8 seconds. After a failure the retry delay starts at 0.5 seconds and doubles up to 5 seconds. | Check power and Bluetooth, then rerun. |
| One board never becomes active; `live.log` shows `BLE attempt failed: invalid source statistics magic; flash this board with the current firmware`; `ble_errors` and `source_stats_errors` grow; startup times out after 30 seconds | That board still runs Week 7 firmware. ## Cautions and known limits

### Risks olsonwangyj must watch

- **The server certificate lasts only 30 days, and the September certificate has expired.** The laptop's copy of the server certificate (the same one deployed to the Ultra96 in September) expired at `2026-10-06 15:11:29 UTC` (`docs/archive/reports/week7-continuation-report-2026-09-07.md:733-734`). The 28 September deployment record says the existing TLS files were kept (`docs/archive/test-evidence/co-live-deployment-2026-09-28.md:12`), and the repository has no record of a later certificate change. Only the laptop's copy was checked; the Ultra96's actual certificate has not been checked. If the Ultra96 still uses that certificate, the service starts as usual, but the laptop gets no ACK at all and the phone stays at `Disconnected: SSH, TLS or protocol verification failed; correct setup and reconnect`. The CA is valid until 2027-09-06 and its SHA-256 matches the fingerprint enrolled in the phone source, so renewing with `--renew-server-from` is enough (section C step 1).
- **Without `--renew-server-from` the CA is replaced as well.** Then the fingerprint in the phone source (`Configuration.swift:12`) and the laptop's `--ca` must both change, and the app must be rebuilt.
- **The Ultra96 has only one subscriber.** Any second subscriber displaces the phone, including desktop test tools.
- **The service process never reclaims identity capacity.** Each process records at most 128 combinations of device and boot ID and 4096 command IDs. When full, it rejects new input. Every glove power-on and every `--mock` run uses capacity. A service that runs a long time without a restart will hit the limit. Restarting the service clears the deduplication state.
- **Results are not resent, and the 2-second rule is not an end-to-end bound.** With no subscriber, results are dropped at once. The result queue holds 32 entries, and when it is full the oldest is dropped (`ultra96/server.py:35,56-60`). A queued result is dropped once it has waited 2 seconds on the Ultra96 (`get_timed`). The write gets only what is left of those 2 seconds (`_send_results`, `ultra96/server.py:69-77,366-387`); if it does not finish in time, the board ends that phone subscription (`result_send_failed`, `reason=error`), abandons what is still queued, and the phone reconnects. This limits only how long a result waits on the Ultra96 (queue plus write). It is not an end-to-end latency bound and not a promise that the phone receives the result: bytes already handed to TCP/TLS cannot be recalled, and `result_write_complete` is logged with `phone_receipt_confirmed=False`. The phone has its own 2-second display window, counted from when it received the result (`DisplayState.swift:109`).
- **Samples are not resent either, so reconnects can leave gaps in `seq`.** On a BLE disconnect the laptop discards that glove's queued samples (`generation_dropped`; `laptop/bridge.py:113-120,910`). On a TLS reconnect, samples already written but not acknowledged count as `ambiguous_dropped` (`laptop/bridge.py:462-469` for one frame at a time; `:484-498` for the ACK window). While a glove is disconnected it makes no samples and `seq` does not advance, so that time shows only as a jump in `uptime_ms`.
- **None of the teammate interfaces exists in code yet.** Everything in section 7 of the hand-off document is planned, not built; only `CommsStart`, `CommsCopyDisplay` and `CommsStop` exist. Every measured result so far used the 32-byte dummy packet and dummy labels.
- **Personal accounts and local paths are written as defaults.** `demo.py:40-41`, `demo.py:49-50`, `tools/ssh_tunnel.py:85-86`, `tools/demo_service.py:11-18`. Those in `tools/demo_service.py` cannot be overridden by arguments.
- **The real Bluetooth addresses of the two boards are built-in defaults.** Without `boards.json`, `load_boards()` returns the addresses at `tools/demo_boards.py:10` and reports no error. With other boards or another machine it will try to connect to devices that do not exist. This machine now has `.comms-local/boards.json`.
- **`BOARD_SOURCE` at `tools/demo_service.py:12` points to the 28 September source folder.** If it is not changed after a redeploy, `python demo.py service --start` still starts the old code.
- **The repository has no deployment script.** The 28 September deployment used `co_deploy.py` in the ignored folder `.week7-local/`. That script started the service in a new background session and wrote its PID to `BOARD_ROOT/evidence/server.pid`, so that process does not depend on any SSH session. The folder also holds the mapping file, past evidence and capture records, none of them under version control.
- **A service started by `python demo.py service --start` is the foreground process of that SSH session.** Closing that terminal, the laptop sleeping or the VPN dropping all make the service exit with the session (inferred from the code, not measured). This applies only to the `--start` path. The 28 September process was started in the background by `co_deploy.py` and does not depend on an SSH session.
- **The phone's host, host keys and session ID are compiled into the app.** `Configuration.swift:8-12`; `IntegrationController.swift:74` holds the session the client uses, and the form text in `SetupViewController.swift:51` repeats it, so both change together. Changing the Ultra96 or the session ID means rebuilding the app. Direct mode (`useJump` off) was never verified on site; V1 keeps using the jump host.
- **The phone's "automatic retry" means logging in to both SSH hops again and again.** When the Ultra96 service is not running, the session does not match, or another subscriber displaced the phone, the phone treats each case as a closed connection. It logs in to the jump host and the Ultra96 again with the passwords, at intervals that start at 0.5 seconds and double up to a cap of 5 seconds, with no limit on attempts, for as long as the app is in the foreground (`CommsClient.swift:181-213`). Whether the jump host limits frequent logins cannot be confirmed from the repository.
- **A different laptop needs `known_hosts` first.** Both SSH hops check host keys strictly, and nothing in the repository writes `known_hosts`.
- **The single-board diagnostic tools cannot choose a board.** `laptop.ble_counter_receiver`, `laptop.mtu_probe` and `tools.rehearse_comms --ble` scan by service UUID and connect to the first board they find. Both boards advertise the same name, so power only one board when using these tools. They also do not set the rate; the board keeps its last rate.
- **`flash.py` rewrites the Git-tracked `comms_fixtures.h` every time.** After a change to `common/dummy_fixtures.json`, the boards must be reflashed before their data changes.
- **`patch_export.py` recognises only one export.** It matches the Week 7 export by the SHA-256 of `Assembly-CSharp.cpp` and the hashes of four method bodies. A project re-exported from `vis/` is rejected with `Unknown receiver source; expected the verified sanitized import.` and is not changed.
- **The evidence does not record the board or server versions.** The source fingerprint in the report describes only the laptop's working tree.
- **Phone evidence is totals only.** Per-result IDs on the phone side were never saved.
- **The Ultra96 diagnostic log has a 50 MiB limit.** After the limit it only stops logging, and `status.json` marks the log incomplete.
- **No range test was done.** The assessment requirement that "the boards are not connected to the laptop's USB" has no dedicated evidence either.
- **The full chain of the current code has never run on real hardware.** The code that accepts only `LC`, `LCS1` and `ltc-comms` has had only a single-board check, on the left board.

### Neither end records rejection reasons

- **Ultra96 service:** invalid frames, mismatched fields, mismatched sessions, v2 identity conflicts and exhausted capacity are all caught by the same `except`. It only does `rejected += 1` and closes the connection. It writes no log and sends no message back (`ultra96/server.py:224-227`). The Ultra96 service has only two kinds of log line: an INFO line for each accepted input (`:262-263`) and an ERROR line when the listener task dies (`:202`). The metrics are printed only once, with the `stopped` line when the process stops (`:453`). They cannot be queried while it runs.
- **Laptop:** no reason is recorded for any transport failure. A TLS connect or handshake failure increments only `transport_errors`. An ACK timeout or a mismatched ACK increments both `ack_errors` and `transport_errors` (`laptop/bridge.py:454,467` for one frame at a time; `:620,666` for the ACK window). Only BLE failures write `BLE attempt failed: …` (`:804`).
- **Consequence:** an expired certificate, a session mismatch, a blocked port and a protocol mismatch between the two ends (for example only one end upgraded to 11 values) look alike in both logs. On the laptop the only difference is whether `ack_errors` grows as well. During the 38-byte migration, upgrading one end first shows up as connections that are closed silently. So every end upgrades together, which is also the owner's rule: only the newest version is supported, with no interoperability between versions (section 8, step 1 of the hand-off document).

Local TLS rehearsal (with its own server and subscriber, and synthetic input):

```powershell
python -m tools.generate_comms_pki --output-dir <new empty folder outside the repository>
python -m tools.rehearse_comms --pki-dir <same folder> --duration 30 --target 100
```

- This generates one-off rehearsal certificates, not deployment certificates.
- It prints one JSON line. `passed` is true, and `results` equals `bridge.acked` minus `bridge.duplicate_acks`. It does not go through SSH and does not represent the real Ultra96.

The full dual bridge with two synthetic inputs on this machine (start the server in another terminal first):

```powershell

python -m laptop.dual_bridge --ca <folder>/ca-cert.pem --mock --duration 10
```

- In the last JSON line, `clean` is true and `mock_input` is true. Every `--mock` run uses two of the server's identity slots.

On a Mac:


Check each item:

1. Firmware: the serial port shows `comms_ready device_id=<1 or 2> packet_bytes=32 packet_version=2 rate_hz=10 protected=1 control_version=1 file_max_bytes=65536`. After pairing, it shows a line starting with `ble_security_complete success=1 auth_mode=13 approved=1 current_peer=1`.
