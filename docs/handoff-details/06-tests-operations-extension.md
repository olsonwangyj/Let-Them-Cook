## Purpose and boundaries

- This chapter answers four questions. How do we prove the code is correct (tests)? What was measured on real hardware (evidence)? How do we operate and redeploy on site (operations)? What must Communications change in its own code when real data and the real model arrive (extension points)?
- Communications only sends each module's data out and confirms that the next module receives it accurately. It passes every result through unchanged and never merges, splits, filters or reinterprets results. Pairing the left and right gloves, building model windows, deciding gesture or idle, model accuracy, mapping labels to game actions, and any script in `vis/` are teammates' work. Wen Ree and Jie Ling agree between themselves the label names, how often a label fires, and whether several identical labels in a row mean one action or several. The division of work at each hand-over is the table in section 3.1 of the hand-off document (the owner's proposal, final when the teammates confirm it). This chapter does not cover the teammates' parts.
- Evidence has 5 levels. No level replaces another. Level 1 is `submitted` in the board's source statistics. Level 2 is the laptop's `received`. Level 3 is `INGEST_ACK`; for a stream sample it also means that the model's `on_sample` returned. Level 4 is the Ultra96 event `result_write_complete`. Level 5 is `Received` on the phone screen. Since the model interface (2026-10-14), the `stopped` line of the Ultra96 service also counts `model_samples` and `model_results`: how many samples went to the model and how many of its results the service accepted for sending (level 3a in section 4.7 of the hand-off document). `CAPTURE PASSED`, printed by `demo.py`, is level 3. It proves only that the Ultra96 service accepted the input. It does not prove that the phone received the result.
- On level 2: the report field `received` counts the packets that the writer task took from the queue and processed (`laptop/bridge.py:404`). The BLE callback count is a separate field, `callback_received` (`laptop/bridge.py:307,1012`). The progress line prints the callback count as `received=` and the report's `received` as `processed=` (`laptop/dual_bridge.py:149-150`). The two differ when the queue drops packets.
- Current identifiers: packet magic `LC` with protocol version 3 (38 bytes), statistics magic `LCS3` (36 bytes since 2026-10-15), session ID `ltc-comms`, local evidence folder `.comms-local/`. The current code (local `main`; the team main since `7d8317a`) accepts only this set, and since 2026-10-16 the Ultra96 service runs it; the subscription envelopes `SUBSCRIBE` and `SUBSCRIBED` stay at version 1. For the old identifiers (`W7`, `W7S1`, `LCS1`, protocol versions 1 and 2) see "History and removed items".
- The connection is settled. The laptop and the phone each dial out through the VPN, `stujump:22` and port 22 of the Ultra96. Ports `8888` and `9999` on the Ultra96 are reached only through the SSH channel. This chapter does not discuss other routes.
- Teammates' code is read-only. This chapter cites `hardware/`, `src/`, `models/` and `vis/` only to show what the interfaces already reveal in the teammates' code. It does not describe their internal implementation. The firmware builds Siqiang's module from byte-identical copies in `firmware/esp32/lib/glove_sensor/` (made by `tools/sync_glove_module.py`); nobody edits those copies.
- The archived design records and measurement records cited here are under `docs/archive/`. The whole `docs/` folder exists only on olsonwangyj's fork, not in the team repository. Teammates who clone the team repository cannot see these sources.

### Conditions for `CAPTURE PASSED`

All the conditions `demo.py` checks before it passes a capture (`demo.py:143-159`, `205-212`):

| Condition | Requirement |
|---|---|
| Process and report | `exit-code.txt` is 0; `clean` is true; `mock_input` is false; `report_saved` is true. |
| Each board | `clean` and `protected_ble` are true; `unfinished` is false; `source.complete` and `source.clean` are true. |
| Counts | `source.generated` is a positive integer, and `source.source_submitted`, `source.received`, `source.acked`, and the device-level `received`, `sent` and `acked` all equal it. A gated glove that stays still for the whole capture generates nothing and does not pass. Idle ticks do not count here. |
| Missing | `source.missing_received` and `source.missing_acked` are both 0. |
| Packet examples | `packets.jsonl` has at least one `sensor` and `sensor_ack` pair with the same identity for each board. Each `sensor` record must be protocol version 3, and its `raw_hex` must decode with the current decoder and match the recorded fields; an ACK record that carries a version must be version 3 (`tools/video_evidence.py:46-52,96-104,113-114`). |

On a pass it prints `CAPTURE PASSED: physical ESP input through Ultra96 ingestion ACKs.` and then `Phone expected increase: N`. N is the sum of `generated` over both boards, plus the number of completed commands on both boards (`demo.py:213-215`). The next line says that this count holds while the Ultra96 runs the built-in dummy model, one result per accepted sample or command (`demo.py:216-217`). Whether the phone received anything is not checked here. Since 2026-10-15 the table above the verdict has two more columns, `Gated` (`yes`, `no` or `N/A`) and `Idle` (the board's idle ticks); they do not change the verdict (`demo.py:181-190`).

`laptop.dual_bridge`'s own `clean` is where each board's `clean` in the table above comes from. It also requires the following, which are easy to miss (`laptop/dual_bridge.py:333-368,561-563`):

1. During startup, both boards became ready within `--startup-timeout`, and the progress callback never raised an exception (`progress_error` is false).
2. No board has a runtime failure record (for example `startup:TimeoutError`, `writer:…`, `transport_close:…`).
3. Coverage and silence (`board_coverage`, `laptop/dual_bridge.py:391-416`). A board that is not gated: the number of packets received in the observation period is above 0 and at least "0.9 × observation time × rate", and the longest silence does not exceed `freshness` (2 seconds). A gated board (its source statistics carry the gated flag; since 2026-10-15): `generated` + `source_idle` is above 0 and at least "0.9 × `source_ticking_seconds` × rate", because its counters cover the whole time its notifications were on, which starts before the common window and ends after it; silence is not judged once it has reported idle ticks, because a still player is silent. "Rate" is `--rate` when given (`demo.py run` always gives it, default 10), otherwise `--expected-rate`.
4. All anomaly fields are 0: `malformed`, `stale_dropped`, `generation_dropped`, `duplicate_acks`, `ack_errors`, `ambiguous_dropped`, `transport_errors`, `ble_errors`, `cleanup_errors`, `identity_mismatches`, `source_stats_errors`, `disconnects`, `queue_dropped`, `callback_generation_dropped`, `gaps`, `duplicates`, `out_of_order`, `new_boots`. `duplicate_acks` is included: if any `INGEST_ACK` has `status` `duplicate`, that board is judged not clean. Such an ACK still proves that the Ultra96 service received the input (level 3). The two statements do not contradict each other.
5. The commands' `failed` and `pending` are 0. `rejected` (a key press while the queue is full or the board is not connected) does not affect the verdict (`laptop/controls.py:335-337`).
6. The control channel's `response_errors`, `duplicate_responses`, `notification_dropped` and `native_pending` are all 0 (`laptop/controls.py:279-281`).
7. `sensor_goodput.tracking_overflow` is 0.
8. If any of the evidence writer's `dropped`, `write_errors` or `unfinished` is non-zero, the overall `clean` is set to false at the end. A failed report write does the same.

### What `demo.py report` requires of its input

- It requires `exit-code.txt` and `packets.jsonl` next to `report.json`. A report from running `python -m laptop.dual_bridge --report …` directly has no `exit-code.txt` and gets `CAPTURE NOT PASSED: missing, incomplete or unreadable evidence (…)` (`demo.py:162-175`).
- Without a path, it takes the `B07-*` folder with the newest modification time in the output folder, even if that run was interrupted (`demo.py:275-281`). It looks only in `.comms-local/`, not in `.week7-local/`. This machine has no capture under `.comms-local/` yet, so running it without a path reports `Demo could not complete: No B07 captures in …; run a capture first.`.
- Captures made before version 3 no longer pass. The packet-example check refuses any `sensor` record whose version is not 3. Verified on 2026-10-14 with two of the old `W7` captures in `.week7-local/` (their records carry version 2): an old capture that was judged clean at the time still meets the count conditions when opened with a path, then gets `PACKET EXAMPLES NOT PASSED: packets.jsonl line …: sensor version is protocol version 2; this tool reads only version-3 captures (check older captures with the code from before version 3)` and `CAPTURE NOT PASSED: packet evidence could not be verified.`. An old capture that was not clean at the time already fails at the count conditions. To review `W7` captures, use the team main commit `880abba` (formerly `ec398b6`; same files), which still decodes `W7`. To review version-2 `LC` captures, use `c42b386` or `5a004c6` (the team main after PR #18). This machine has no saved version-2 `LC` capture: the version-2 checks of the right board are JSON summaries, not capture folders.
- It only rereads saved evidence. It sends no packets and uses no network.

`imu_v7.ino` in the table means `hardware/gloves/29_sept/imu_v7.ino`. The field order comes from its `:649-658`. Siqiang's integration module of 2026-10-15, which the `-glove` builds use, configures the same ranges: ±2 g and ±250 degrees/s (`hardware/gloves/integration_files/glove_sensor.cpp:27-28,454-455`), angles from `atan2f` and `asinf` (`:256-270`), and flex as the ADC reading divided by 4095 (`:522-523`). In normal use every value is expected to fit, but that is not guaranteed: the final value depends on the module's processing (for example the gyro calibration bias is subtracted), not only on the raw sensor range.

Values outside the int16 range (the rule is provisional; to be agreed with Wen Ree, sections 8 step 1 and 13 of the hand-off document): `scaleSample` supports both options as a build flag. By default it clamps the value to the int16 limit and counts it (`clamped`); built with `-DCOMMS_OUT_OF_RANGE_DROP=1` it refuses the whole sample and counts it (`rejected`). NaN and infinity always refuse the sample. A refused sample must take no `seq`, so it shows only as a longer `uptime_ms` step, never as a gap (`comms_sample.h:8-13,31-65`). It never drops a connection or a whole gesture. A clamped value cannot be told apart from a real value at the limit (3.2767 g can be either); if the model needs to know which samples were clamped, a per-sample flag is needed, which changes the packet and `on_sample` again. Neither option guarantees that the gesture is still recognised. Where the counts go (built 2026-10-15): each refused sample adds 1 to `refused` in `SampleCounters`, which travels in the 36-byte `LCS3` statistics and in the serial `comms_stats` line; each clamped channel value adds 1 to `clamped`, which appears only in the `comms_stats` line (`comms_sample.h:86-114`; `main.cpp:598-605`).

`GESTURE_RESULT` still cannot take extra fields. None of the four validators allows one:

1. The iPhone parser accepts at most 10 fields, and a version-3 result has exactly 10. Values may only be strings, numbers or `null`. Arrays, nested objects and booleans fail, and the failure is terminal (`Protocol.swift:201-202,206-210`; `CommsClient.swift:199`).
2. The C# reference implementation compares the field count exactly: 10 (`CommsPhoneCore.cs:51,75-79`).
3. The Ultra96 check and the Python receiver both require the key set to be exactly equal (`ultra96/protocol.py:67-68`; `phone/receiver.py:99-103`).
4. The field allow-list of the Ultra96 event log does not include new fields either. Extra fields make the log receipt incomplete (`ultra96/diagnostics.py:17-31,100-101`).

So one result can carry the identity of only one sample. Section 7.2 of the hand-off document defines the model output under this constraint: the model hands over the `(device_id, boot_id, seq)` of one sample it used for the result (usually the newest one in the window; either glove is fine), and each result must point to a different sample, because the phone de-duplicates by `result_id` and the service refuses a second result with the same identity.

Siqiang's takes about 5.1 seconds (gyro calibration; the glove must be still) and returns `false` promptly when the IMU is missing (verified on 2026-10-16 on the right board, which has none: `glove_begin ok=0` 0.71 s after reset with one try; with the retry, `ok=0 … attempts=3` at 1.71 s). It also returns `false` when the IMU's WHO_AM_I is not exactly 0x70, and when any one calibration read fails (issues 3 and 5 below). A board whose `gloveBegin()` returned `false` at every try still advertises, connects through its existing bond and answers commands; its send ticks then count as `unread`, and it sends nothing (verified the same day). The retry: `comms::beginWithRetries` (`comms_glove.h:86-98`) calls it until it returns `true`, at most `COMMS_GLOVE_BEGIN_ATTEMPTS` times (default 3, 1 to 10), with `COMMS_GLOVE_BEGIN_RETRY_MS` (default 500, 0 to 10000) between tries, and the firmware prints `glove_begin_failed attempt=<n> retry_ms=<ms>` before each pause. Each retry repeats Siqiang's calibration, so a glove that fails twice during calibration advertises up to about 10 to 11 seconds later than normal; with no IMU the three tries add about 1 second. Calling it again after `false` is safe: his `gloveBegin()` resets its own state at the start, and `Wire.begin()` on a bus already started returns `true` in the Arduino-ESP32 core 2.0.17 used here (`framework-arduinoespressif32` 3.20017, `libraries/Wire/src/Wire.cpp:300-303`). The comment on `gloveBegin()` in `comms_glove.h` asks this of any module.
- `gloveUpdate()` runs once per main-loop pass, outside `connectionStateMutex`, whether or not the laptop is connected (`main.cpp:506`). The pass ends with `delay(1)` (`main.cpp:607`).
- At a send tick, only while the laptop is connected and subscribed, `produceSample` calls `gloveRead` and then `gloveShouldSend` outside the mutex (`main.cpp:404-412`). The output array is filled with NaN first, so a channel the module leaves unwritten refuses the sample (`:405-406`), and `uptime_ms` is taken after the read (`:409`). Under the mutex the tick is committed only if the laptop is still ready; only a sample to send takes a `seq` (`:414-430`). The BLE callbacks also take this mutex, and none of the glove calls runs under it.
- None of the calls may wait. A slow call delays the next send tick but not the rate, as long as one pass (the call plus about 1 ms) stays shorter than the send interval (20 ms at 50 Hz); a longer pass skips ticks (`comms_glove.h:58-63`; `comms_sample.h:67-78`). Siqiang says one call takes at most about 10 to 20 ms, usually far less.
- Classic Bluetooth cannot be used: the Communications firmware uses BLE (`main.cpp:465`), and both cannot hold the Bluetooth controller at the same time. Siqiang's integration module uses none. His Bluetooth Classic recording script can no longer connect to a glove that runs the Communications firmware; section F gives the recording route.
- The module must not read the serial port and must not call `Serial.begin` again. The Communications firmware already opens the serial port at `main.cpp:435`, reads the `erase-bonds` command from it (`main.cpp:369-385`), and shows the passkey on it.
- Left or right identity is set by the Communications build flag `COMMS_DEVICE_ID` (`platformio.ini:35,40,48,56`): left is 1, right is 2. The module does not handle it; left and right use the same module code, and Siqiang's 12th value and Bluetooth names were only for his PC. The default environment `firebeetle32` sets no flag, so `COMMS_DEVICE_ID` falls back to 1 (`main.cpp:26-28`).
- Communications controls the send tick. The initial value is `COMMS_INITIAL_RATE_HZ` (default 10, allowed 1 to 200, `main.cpp:29-31,40-41`); the `-glove` environments set 50. The laptop can change it at run time, and `demo.py run` always sets it (default 10), so captures with the gloves need `--rate 50`. Siqiang's movement classifier keeps its own 50 Hz window inside `gloveUpdate`, whatever the send rate.
- The 11 floats go through `prepareSample` and `scaleSample` (`comms_sample.h:36-65,97-114`). A sample with NaN or infinity is refused and not sent.
- The Communications code itself uses no GPIO or I2C. Siqiang's module uses I2C on SDA 21 and SCL 22 at 400 kHz with a 2 ms timeout, and ADC 34 and 35 (`hardware/gloves/integration_files/glove_sensor.cpp:14-17,42,444-445`).

Issues found in Siqiang's module (1, 2 and 4 on 2026-10-15, 3 and 5 on 2026-10-16; reported to the owner; his files are untouched). The numbers are those of section 7.1 of the hand-off document. Line numbers are those of `hardware/gloves/integration_files/glove_sensor.cpp`; the copy has the same lines.

1. `glove_sensor.cpp:4` includes `"../../../movement_model_params.h"`. From `hardware/gloves/integration_files/` that path resolves to the repository root, where no such file exists, so the file does not compile where it lives. The header sits in the same folder, so `#include "movement_model_params.h"` would fix it. Not blocking: the copies are built in the layout the path expects, and the sync tool also puts the header beside the copied `.cpp`, so the corrected include works too.
2. A failed IMU read, a non-finite sample, or more than 100 ms between two `gloveUpdate` calls resets the whole movement classifier (`glove_sensor.cpp:487-489,494-496,533-535`). `gloveIsMoving()` then stays false for at least about 1.2 seconds (the 1-second window refills, its first decision comes at once and the second 200 ms later; `:301-311,396-416`), so sending stops for that long, even in the middle of a gesture. In the Communications firmware `gloveUpdate` runs every 1 to 2 ms, so only the first call after boot (BLE setup runs after `gloveBegin`) and transient I2C failures (2 ms timeout) trigger it.
3. One failed IMU read during calibration makes `gloveBegin()` fail: `calibrateGyroscope()` returns `false` at the first failed read of its 1000 (`glove_sensor.cpp:171-172`), and `gloveBegin()` then returns `false` (`:464-465`). Until 2026-10-16 the Communications firmware called `gloveBegin()` once in `setup()`, so after such a glitch the glove counted every tick as `unread` and sent nothing until it was power-cycled. Mitigated in Communications by the boot retry (D38; `main.cpp:441-450`): one transient failure now costs one more calibration of about 5 seconds; only a failure at every try leaves the glove without data. The root cause stays in Siqiang's module (an FYI for him; his decision).
4. A design property for Wen Ree: a decision comes every 200 ms (`glove_sensor.cpp:46-50,382-388,412-416`). MOVING needs two positive decisions in a row, so it comes at the earliest about 0.2 to 0.4 seconds after the 1-second window starts to look like motion, and the window can itself lag the start of the motion, more so for gentle motion. IDLE needs three negative decisions in a row, at least about 0.4 to 0.6 seconds after the window looks still; because the window covers the last second, it may first look still up to about 1 second after the motion stops. Samples before the MOVING decision are not sent and cannot be sent later (the measured ceiling of about 66 packets per second per board leaves no room to catch up). The two gloves gate independently, so one glove can be silent while the other sends.
5. `gloveBegin()` returns `false` unless the IMU's WHO_AM_I register reads exactly 0x70 (`glove_sensor.cpp:24-25,447-449`), while Siqiang's tested sketch only prints a warning for another value and carries on (`hardware/gloves/model_threshold_variant_1/debug_esp32_ml_movement_detector_v1.ino:608-610`). Effect in Communications: a glove whose IMU reports another WHO_AM_I (for example a compatible MPU variant) boots with `glove_begin ok=0 … attempts=3` and sends nothing, as the sensorless checks of 2026-10-16 showed for a missing IMU; the boot retry does not help, because every try fails the same way. The question for Siqiang is which value each glove prints.

**Ultra96 model (Wen Ree), called by `ultra96/server.py` through `ultra96/model.py`:**

- The call is at `ultra96/server.py:327-330`. It runs synchronously inside the coroutine that receives samples, and `INGEST_ACK` is written only after it (`:337-339`). The service is a single asyncio event loop, so the model's `on_sample` must return immediately. Otherwise the ACKs of both gloves are held up. The laptop waits at most 5 seconds for one ACK (`io_timeout` at `laptop/bridge.py:42`), and a sample's freshness limit on the laptop is 2 seconds (`laptop/bridge.py:41`). Calls longer than 5 ms are counted in `model_slow_calls`, and the slowest in `model_max_call_ms` (`ultra96/model.py:30,159-166`).
- The result queue has no lock (`ultra96/server.py:58-109`), so results must be put into it on the event-loop thread. Built: the `emit` that Communications provides may be called from any thread and moves each result onto the event loop with `call_soon_threadsafe` (`ultra96/model.py:168-187`). It returns `True` when the arguments are valid and the service is running, otherwise `False`.
- Samples reach the model with gaps in `seq` after a reconnect, and they are not resent: on a BLE disconnect the laptop discards that glove's queued samples, and on a TLS reconnect the samples already written but not acknowledged count as ambiguous drops. While a glove is disconnected it makes no samples, so that time shows only as a jump in `uptime_ms` (code references under "Risks olsonwangyj must watch"; section 7.2 of the hand-off document tells Wen Ree). The same holds for movement gating: the model receives only samples sent while the glove reports MOVING, each pause shows as a jump in `uptime_ms` with no `seq` gap, and the two gloves gate independently.
- Every result the model hands over is passed on unchanged, including its confidence, unrounded: a numpy float32 0.93 arrives as 0.9300000071525574 (decision D17, section 6.5 of the hand-off document). A queued result is still subject to the Ultra96's 2-second waiting limit, which is not an end-to-end bound (see "Risks olsonwangyj must watch").
- A result's `confidence` must be a finite number from 0 to 1. `emit` checks it before the result is queued (`ultra96/model.py:84-100`; `ultra96/protocol.py:36-40`), and frames are serialised with `allow_nan=False` (`common/wire.py:40`).
- Result messages cannot take extra fields; see the previous subsection.
- What `tools.deploy_service` uploads to the Ultra96 is only `common/` and `ultra96/`: 11 files (`common/*.py`, `common/dummy_fixtures.json` and `ultra96/*.py`; `tools/deploy_service.py:327-336`). The service runs as an ordinary user with `/usr/bin/python3` and only the standard library. The 28 September snapshot had 10 files; `ultra96/model.py` is the new one.
- If the model cannot load under that interpreter and user, it runs as a separate process on the Ultra96, and Communications passes the same fields to it in a format the owner sends on Thu 10-15 (section 7.2 of the hand-off document). Wen Ree's first connectable version (proposed Fri 10-16) is pushed to the team repo: for the in-process option with its module and function names; for the separate-process option with how to start it, its dependencies, and its input and output in that format.
- The owner's direction of 2026-10-14, final when Wen Ree confirms, and built: the model gets the 11 `values` as physical floats. `ModelPort.on_sample` passes `physical_values(values)` (`ultra96/model.py:155`; `common/sensor.py:92-98`). ## Why it is designed this way

| Design point | Reason | Rejected alternative | Source |
|---|---|---|---|
| Packet tests use hand-written golden bytes, not expected values generated by the codec under test | The firmware, the laptop and the Ultra96 must decode the same bytes into the same values. The version-3 vectors were written the same way. | Using one side's output as the other side's expected value. | `docs/archive/test-evidence/week7-packet-firmware-evidence.md:30-35`; `tests/test_sensor.py:1`; `tests/fixtures/comms-golden.json` |
| The firmware's packing, security checks, event parsing and sample scaling live in portable headers and are tested with host C++ | Regression testing without flashing a board. | Verifying only on the board. | `docs/archive/reports/week7-system-technical-report.md:257` |
| Read source statistics once before and once after capture, and reconcile by interval | Looking only at the first and last received sequence numbers cannot detect a lost first or last packet. | Using `last_seq - first_seq`. | `docs/archive/design/specs/2026-09-17-dual-esp-reception.md:11-13`; `docs/archive/reports/week7-system-technical-report.md:303` |
| On stop, first turn notifications off on the remote side, drain the tail packets, then read the final counts | A plain stop lost the last packet in 3 of 12 runs at 100 Hz. ## Cautions and known limits

### Risks olsonwangyj must watch

- **The server certificate lasts only 30 days.** The September certificate expired at `2026-10-06 15:11:29 UTC` (`docs/archive/reports/week7-continuation-report-2026-09-07.md:733-734`). On 2026-10-16 `tools.deploy_service --server-cert-dir` installed the renewed pair from the same CA on the Ultra96 (`certificate_not_after` `Nov 13 14:27:35 2026 GMT`; the old pair is in `BOARD_ROOT/tls/backup-20261016T050629Z`), and the remote rehearsals' TLS verified it against the existing CA. An expired certificate lets the service start as usual, but the laptop gets no ACK at all and the phone stays at `Disconnected: SSH, TLS or protocol verification failed; correct setup and reconnect`. The renewed certificate expires before the final demo, so renew again in early November and redeploy with `--server-cert-dir`. The CA is valid until 2027-09-06 and its SHA-256 matches the fingerprint enrolled in the phone source; it did not change, so the laptop's `--ca` and the CA imported on the phone stay valid.
- **Without `--renew-server-from` the CA is replaced as well.** Then the fingerprint in the phone source (`Configuration.swift:19`) and the laptop's `--ca` must both change, and the app must be rebuilt.
- **The Ultra96 has only one subscriber.** Any second subscriber displaces the phone, including desktop test tools.
- **Run one rehearsal or test at a time.** The Ultra96 sends every result to its one subscriber, whatever input produced it. On 2026-10-16 a BLE rehearsal that overlapped the idle test saw the idle test's two results as unexpected and was judged failed, although all 562 of its own samples matched. Any other input during a rehearsal or a capture breaks its exact correlation and the phone count.
- **Every password login needs the NUS VPN.** Off the VPN, stujump offers only public-key login (seen from the laptop on 2026-10-16), and the laptop has no SSH key pair; nothing in Communications uses keys. On the phone, from the code: the app stops with the terminal `Jump host does not offer password authentication`, clears the passwords and does not retry, so the phone needs its own VPN before Connect, and a VPN drop during a session ends the same way if stujump stays reachable (section D).
- **The service process never reclaims identity capacity.** Each process records at most 128 combinations of device and boot ID and 4096 command IDs. When full, it rejects new input. Every glove power-on and every `--mock` run uses capacity, and so does every synthetic rehearsal and probe. A service that runs a long time without a restart will hit the limit. Restarting the service clears the deduplication state. The tests of 2026-10-16 used 5 identities in the service deployed that day; restart (redeploy) it before V1.
- **Results are not resent, and the 2-second rule is not an end-to-end bound.** With no subscriber, results are dropped at once. The result queue holds 32 entries, and when it is full the oldest is dropped (`ultra96/server.py:61,82-86`). A queued result is dropped once it has waited 2 seconds on the Ultra96 (`get_timed`, `:95-103`). The write gets only what is left of those 2 seconds (`_send_results`, `:463-484`); if it does not finish in time, the Ultra96 ends that phone subscription (`result_send_failed`, `reason=error`), abandons what is still queued, and the phone reconnects. This limits only how long a result waits on the Ultra96 (queue plus write). It is not an end-to-end latency bound and not a promise that the phone receives the result: bytes already handed to TCP/TLS cannot be recalled, and `result_write_complete` is logged with `phone_receipt_confirmed=False`. The phone has its own 2-second display window, counted from when it received the result (`DisplayState.swift:141`).
- **Samples are not resent either, so reconnects can leave gaps in `seq`.** On a BLE disconnect the laptop discards that glove's queued samples (`generation_dropped`; `laptop/bridge.py:114-120,920`). On a TLS reconnect, samples already written but not acknowledged count as `ambiguous_dropped` (`laptop/bridge.py:465-472` for one frame at a time; `:487-502` for the ACK window). While a glove is disconnected it makes no samples and `seq` does not advance, so that time shows only as a jump in `uptime_ms`. A gated glove that is still makes no packets either; its pauses also show only as jumps in `uptime_ms`.
- **The model's `on_sample` runs on the service's only event loop, before the ACK** (`ultra96/server.py:327-339`). A model that does its inference inside `on_sample` holds up the ACKs of both gloves (the laptop waits at most 5 seconds; sample freshness is 2 seconds). `model_slow_calls` and `model_max_call_ms` show it, but only in the `stopped` line.
- **Most of the teammate interfaces exist only on the Communications side, on `main` (local and the fork) and, since pull request #19 was merged on 2026-10-16, on the team main (`7d8317a`).** The firmware calls the glove module, and Siqiang's module is built into the `-glove` environments, but no glove has run it; the model interface runs the dummy model; `CommsNextResult` is compiled and tested on Linux and macOS and linked into the Week 7 iPhone build installed on the owner's iPhone on 2026-10-16, which does not call it; the model module and the game script do not exist yet. Since 2026-10-16 the Ultra96 runs the version-3 service with the dummy model, and the phone app built from current source is installed and subscribed to it on the afternoon of 2026-10-16. Every measured result so far used dummy data and dummy labels.
- **Version 3 has run with both boards, with dummy data only.** On 2026-10-16 the right board passed `tools.check_board` with the plain and gated builds, and the plain build again after the boot retry, against a service on the laptop, and the remote rehearsal through the real Ultra96 at about 10 Hz to a desktop subscriber; on 2026-10-17 the left board passed the plain check, and both boards passed the acceptance run through the real Ultra96 to the phone at 10 Hz and 50 Hz, with every result received on the phone. The gated firmware has not run through the Ultra96 (the idle tests cover the service side), and no glove with sensors has run the `-glove` build. The last full-chain capture on hardware was on 2026-10-01, with Week 7 `W7` packets.

### Neither end records rejection reasons

- **Ultra96 service:** invalid frames, mismatched fields, mismatched sessions or versions, identity conflicts and exhausted capacity are all caught by the same `except`. It only does `rejected += 1` and closes the connection. It writes no log and sends no message back (`ultra96/server.py:287-288`). An ingest connection closed after the idle limit (600 seconds without a frame) is counted the same way, silently. The service's log lines are an INFO line for each accepted input (`:325-326`), an ERROR line when a listener task dies (`:263`), a WARNING when all 8 client slots are full and it closes an idle ingest connection (`client slots full; closing an ingest connection idle for … s`, counted in `idle_evicted`; `:245-247`), and the model warnings, at most one of each kind per second (`ultra96/model.py:143-148`). Its JSON lines on standard output are `model_ready`, `listening`, `stopped` (with the metrics, printed only once, when the process stops, `ultra96/server.py:573`), `observation_stopped` with `--event-log-dir` (`:516`), and in failure cases `model_failed` and `exit_with_model_threads`. The metrics cannot be queried while it runs.
- **Laptop:** no reason is recorded for any transport failure. A TLS connect or handshake failure increments only `transport_errors`. An ACK timeout or a mismatched ACK increments both `ack_errors` and `transport_errors` (`laptop/bridge.py:457,470` for one frame at a time; `:623,669` for the ACK window). Only BLE failures write `BLE attempt failed: …` (`:809`).
- **Consequence:** an expired certificate, a session mismatch, a blocked port and a protocol version mismatch between the two ends (for example a version-3 laptop against the version-2 service that ran on the Ultra96 until 2026-10-16) look alike in both logs. On the laptop the only difference is whether `ack_errors` grows as well. An end that has not moved to version 3 shows up as connections that are closed silently. So every end upgrades together, which is also the owner's rule: only the newest version is supported, with no interoperability between versions (section 8, step 1 of the hand-off document).
