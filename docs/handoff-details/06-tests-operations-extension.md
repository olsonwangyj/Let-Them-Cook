## Purpose and boundaries

- This chapter answers four questions. How do we prove the code is correct (tests)? What was measured on real hardware (evidence)? How do we operate and redeploy on site (operations)? What must Communications change in its own code when real data and the real model arrive (extension points)?
- Communications only sends each module's data out and confirms that the next module receives it accurately. It passes every result through unchanged and never merges, splits, filters or reinterprets results. Pairing the left and right gloves, building model windows, deciding gesture or idle, model accuracy, mapping labels to game actions, and any script in `vis/` are teammates' work. Wen Ree and Jie Ling agree between themselves the label names, how often a label fires, and whether several identical labels in a row mean one action or several. The division of work at each hand-over is the table in section 3.1 of the hand-off document (the owner's proposal, final when the teammates confirm it). This chapter does not cover the teammates' parts.
- Evidence has 5 levels. No level replaces another. Level 1 is `submitted` in the board's source statistics. Level 2 is the laptop's `received`. Level 3 is `INGEST_ACK`; for a stream sample it also means that the model's `on_sample` returned. Level 4 is the Ultra96 event `result_write_complete`. Level 5 is `Received` on the phone screen. Since the model interface (2026-10-14), the `stopped` line of the Ultra96 service also counts `model_samples` and `model_results`: how many samples went to the model and how many of its results the service accepted for sending (level 3a in section 4.7 of the hand-off document). `CAPTURE PASSED`, printed by `demo.py`, is level 3. It proves only that the Ultra96 service accepted the input. It does not prove that the phone received the result.
- On level 2: the report field `received` counts the packets that the writer task took from the queue and processed (`laptop/bridge.py:399`). The BLE callback count is a separate field, `callback_received` (`laptop/bridge.py:302,997`). The progress line prints the callback count as `received=` and the report's `received` as `processed=` (`laptop/dual_bridge.py:145-146`). The two differ when the queue drops packets.
- Current identifiers: packet magic `LC` with protocol version 3 (38 bytes), statistics magic `LCS3`, session ID `ltc-comms`, local evidence folder `.comms-local/`. On the branch `comms/protocol-v3` the code accepts only this set; the subscription envelopes `SUBSCRIBE` and `SUBSCRIBED` stay at version 1. For the old identifiers (`W7`, `W7S1`, `LCS1`, protocol versions 1 and 2) see "History and removed items".
- The connection is settled. The laptop and the phone each dial out through the VPN, `stujump:22` and port 22 of the Ultra96. Ports `8888` and `9999` on the Ultra96 are reached only through the SSH channel. This chapter does not discuss other routes.
- Teammates' code is read-only. This chapter cites `hardware/`, `src/`, `models/` and `vis/` only to show what the interfaces already reveal in the teammates' code. It does not describe their internal implementation.
- The archived design records and measurement records cited here are under `docs/archive/`. The whole `docs/` folder exists only on olsonwangyj's fork, not in the team repository. Teammates who clone the team repository cannot see these sources.

### Conditions for `CAPTURE PASSED`

All the conditions `demo.py` checks before it passes a capture (`demo.py:143-159`, `201-208`):

| Condition | Requirement |
|---|---|
| Process and report | `exit-code.txt` is 0; `clean` is true; `mock_input` is false; `report_saved` is true. |
| Each board | `clean` and `protected_ble` are true; `unfinished` is false; `source.complete` and `source.clean` are true. |
| Counts | `source.generated` is a positive integer, and `source.source_submitted`, `source.received`, `source.acked`, and the device-level `received`, `sent` and `acked` all equal it. |
| Missing | `source.missing_received` and `source.missing_acked` are both 0. |
| Packet examples | `packets.jsonl` has at least one `sensor` and `sensor_ack` pair with the same identity for each board. Each `sensor` record must be protocol version 3, and its `raw_hex` must decode with the current decoder and match the recorded fields; an ACK record that carries a version must be version 3 (`tools/video_evidence.py:46-52,96-104,113-114`). |

On a pass it prints `CAPTURE PASSED: physical ESP input through Ultra96 ingestion ACKs.` and then `Phone expected increase: N`. N is the sum of `generated` over both boards, plus the number of completed commands on both boards (`demo.py:209-211`). The next line says that this count holds while the Ultra96 runs the built-in dummy model, one result per accepted sample or command (`demo.py:212-213`). Whether the phone received anything is not checked here.

`laptop.dual_bridge`'s own `clean` is where each board's `clean` in the table above comes from. It also requires the following, which are easy to miss (`laptop/dual_bridge.py:329-360,525-527`):

1. During startup, both boards became ready within `--startup-timeout`, and the progress callback never raised an exception (`progress_error` is false).
2. No board has a runtime failure record (for example `startup:TimeoutError`, `writer:…`, `transport_close:…`).
3. The number of packets received in the observation period is above 0 and at least "0.9 × observation time × rate". The longest silence does not exceed `freshness` (2 seconds).
4. All anomaly fields are 0: `malformed`, `stale_dropped`, `generation_dropped`, `duplicate_acks`, `ack_errors`, `ambiguous_dropped`, `transport_errors`, `ble_errors`, `cleanup_errors`, `identity_mismatches`, `source_stats_errors`, `disconnects`, `queue_dropped`, `callback_generation_dropped`, `gaps`, `duplicates`, `out_of_order`, `new_boots`. `duplicate_acks` is included: if any `INGEST_ACK` has `status` `duplicate`, that board is judged not clean. Such an ACK still proves that the Ultra96 service received the input (level 3). The two statements do not contradict each other.
5. The commands' `failed` and `pending` are 0. `rejected` (a key press while the queue is full or the board is not connected) does not affect the verdict (`laptop/controls.py:335-337`).
6. The control channel's `response_errors`, `duplicate_responses`, `notification_dropped` and `native_pending` are all 0 (`laptop/controls.py:279-281`).
7. `sensor_goodput.tracking_overflow` is 0.
8. If any of the evidence writer's `dropped`, `write_errors` or `unfinished` is non-zero, the overall `clean` is set to false at the end. A failed report write does the same.

A clamped value cannot be told apart from a real value at the limit (3.2767 g can be either); if the model needs to know which samples were clamped, a per-sample flag is needed, which changes the packet and `on_sample` again. Neither option guarantees that the gesture is still recognised. The counters exist only inside `SampleScaleStats`; nothing reports them yet. `GESTURE_RESULT` still cannot take extra fields. None of the four validators allows one:

1. The iPhone parser accepts at most 10 fields, and a version-3 result has exactly 10. Values may only be strings, numbers or `null`. Arrays, nested objects and booleans fail, and the failure is terminal (`Protocol.swift:201-202,206-210`; `CommsClient.swift:199`).

4. The field allow-list of the Ultra96 event log does not include new fields either. Extra fields make the log receipt incomplete (`ultra96/diagnostics.py:17-31,100-101`).

**Glove sensor module (Siqiang), to be called by `firmware/esp32/src/main.cpp`:**

- The build environment is PlatformIO with the Arduino framework, board type `firebeetle32` (`firmware/esp32/platformio.ini`).
- The main loop ends each pass with `delay(1)` (`main.cpp:557`), so the periodic update is called about once per millisecond. The send block (`main.cpp:499-510`) runs while it holds `connectionStateMutex` (taken at `:482`, released at `:546`), and the BLE callbacks also take this lock. So "read one sample" must not block and must not call `delay()`. The reference sketch calls `delay(100)` when a read fails (`imu_v7.ino:563`). That wait cannot stay in the integrated code.
- Initialisation must return success or failure in bounded time. `setup()` also initialises BLE (`main.cpp:419-420`). If initialisation loops forever, the board never advertises. The reference sketch waits forever when I2C fails (`imu_v7.ino:483-485`).
- Classic Bluetooth cannot be used. The Communications firmware uses BLE (`main.cpp:419`), and the reference sketch uses `BluetoothSerial` (`imu_v7.ino:2,439`). Both cannot hold the Bluetooth controller at the same time.
- The module must not read the serial port and must not call `Serial.begin` again. The Communications firmware already opens the serial port at `main.cpp:404`, reads the `erase-bonds` command from it (`main.cpp:372-388`), and shows the passkey on it.

- Communications controls the send tick. The initial value is `COMMS_INITIAL_RATE_HZ` (default 10, allowed 1 to 200, `main.cpp:27-29,38-39`), and the laptop can change it at run time. The reference sketch outputs at 50 Hz (`imu_v7.ino:83`).
- The 11 floats go through `scaleSample` (`comms_sample.h:36-65`). A sample with NaN or infinity is refused and not sent.
- The Communications firmware uses no GPIO or I2C, so SDA 21, SCL 22 and ADC 34 and 35 are all free.

### D. Common faults: symptom, cause, recovery

| Symptom | Cause | Recovery |
|---|---|---|
| `demo.py` exits at once with `CA file not found: …` | The file given by `--ca` does not exist. The default path exists only on the original laptop. | Pass `--ca` explicitly. |
| `Board setup is incomplete; finish python flash.py before pairing or capture.` | `boards.json` has the status `incomplete`. | Rerun `python flash.py` and finish both boards. |

|---|---|---|---|
| Packet tests use hand-written golden bytes, not expected values generated by the codec under test | The firmware, the laptop and the Ultra96 must decode the same bytes into the same values. The version-3 vectors were written the same way. | Using one side's output as the other side's expected value. | `docs/archive/test-evidence/week7-packet-firmware-evidence.md:30-35`; `tests/test_sensor.py:1`; `tests/fixtures/comms-golden.json` |
| The firmware's packing, security checks, event parsing and sample scaling live in portable headers and are tested with host C++ | Regression testing without flashing a board. | Verifying only on the board. | `docs/archive/reports/week7-system-technical-report.md:257` |
| Read source statistics once before and once after capture, and reconcile by interval | Looking only at the first and last received sequence numbers cannot detect a lost first or last packet. | Using `last_seq - first_seq`. | `docs/archive/design/specs/2026-09-17-dual-esp-reception.md:11-13`; `docs/archive/reports/week7-system-technical-report.md:303` |

| A fault trial is judged not clean even when recovery succeeds | Clean means the run had no loss or interruption at all. | Passing once recovered. | `docs/archive/design/week7-selected-design-2026-09-06.md:38`; `docs/archive/design/specs/2026-09-17-dual-esp-reception.md:16` |

## Cautions and known limits

### Risks olsonwangyj must watch

- **The server certificate lasts only 30 days, and the September certificate has expired.** The laptop's copy of the server certificate (the same one deployed to the Ultra96 in September) expired at `2026-10-06 15:11:29 UTC` (`docs/archive/reports/week7-continuation-report-2026-09-07.md:733-734`). The 28 September deployment record says the existing TLS files were kept (`docs/archive/test-evidence/co-live-deployment-2026-09-28.md:12`), and the repository has no record of a later certificate change. Only the laptop's copy was checked; the Ultra96's actual certificate has not been checked. If the Ultra96 still uses that certificate, the service starts as usual, but the laptop gets no ACK at all and the phone stays at `Disconnected: SSH, TLS or protocol verification failed; correct setup and reconnect`. A renewed pair from the same CA is ready on the laptop (valid to 2026-11-13 14:27:35 UTC) and is installed by `tools.deploy_service --server-cert-dir` (section C step 1). That date is before the final demo, so renew again in early November. The CA is valid until 2027-09-06 and its SHA-256 matches the fingerprint enrolled in the phone source.
- **Without `--renew-server-from` the CA is replaced as well.** Then the fingerprint in the phone source (`Configuration.swift:12`) and the laptop's `--ca` must both change, and the app must be rebuilt.
- **The Ultra96 has only one subscriber.** Any second subscriber displaces the phone, including desktop test tools.
- **The service process never reclaims identity capacity.** Each process records at most 128 combinations of device and boot ID and 4096 command IDs. When full, it rejects new input. Every glove power-on and every `--mock` run uses capacity. A service that runs a long time without a restart will hit the limit. Restarting the service clears the deduplication state.
- **Results are not resent, and the 2-second rule is not an end-to-end bound.** With no subscriber, results are dropped at once. The result queue holds 32 entries, and when it is full the oldest is dropped (`ultra96/server.py:45,66-70`). A queued result is dropped once it has waited 2 seconds on the Ultra96 (`get_timed`, `:79-87`). The write gets only what is left of those 2 seconds (`_send_results`, `:411-432`); if it does not finish in time, the Ultra96 ends that phone subscription (`result_send_failed`, `reason=error`), abandons what is still queued, and the phone reconnects. This limits only how long a result waits on the Ultra96 (queue plus write). It is not an end-to-end latency bound and not a promise that the phone receives the result: bytes already handed to TCP/TLS cannot be recalled, and `result_write_complete` is logged with `phone_receipt_confirmed=False`. The phone has its own 2-second display window, counted from when it received the result (`DisplayState.swift:141`).
- **Samples are not resent either, so reconnects can leave gaps in `seq`.** On a BLE disconnect the laptop discards that glove's queued samples (`generation_dropped`; `laptop/bridge.py:114-120,908`). On a TLS reconnect, samples already written but not acknowledged count as `ambiguous_dropped` (`laptop/bridge.py:460-467` for one frame at a time; `:482-497` for the ACK window). While a glove is disconnected it makes no samples and `seq` does not advance, so that time shows only as a jump in `uptime_ms`.
- **The model's `on_sample` runs on the service's only event loop, before the ACK** (`ultra96/server.py:275-287`). A model that does its inference inside `on_sample` holds up the ACKs of both gloves (the laptop waits at most 5 seconds; sample freshness is 2 seconds). `model_slow_calls` and `model_max_call_ms` show it, but only in the `stopped` line.
- **Only the Communications side of the teammate interfaces exists, and only on a local branch.** The sensor-module call is not in `main.cpp` yet; the model interface runs the dummy model; `CommsNextResult` is written, not compiled; nothing on the teammates' side exists; nothing of it is deployed. Every measured result so far used dummy data and dummy labels.
- **Version 3 has run only on one board, against a service on the laptop.** Nothing of version 3 has run on the Ultra96, on the phone, or with both boards together. The last full-chain capture on hardware was on 2026-10-01, with Week 7 `W7` packets.
- **The installed phone app cannot read version-3 results.** The Week 7 build accepts only versions 1 and 2 (never 3), the four dummy labels and confidence 1.0, and subscribes to `week7-demo`. After the redeploy it cannot subscribe, and the first version-3 result would end its session with a terminal error. The phone needs the Mac build (section C steps 4 and 5).
- **Personal accounts and local paths are written as defaults.** `demo.py:40-41`, `demo.py:49-50`, `tools/ssh_tunnel.py:85-86`, `tools/demo_service.py:13,16,60-61`, `tools/deploy_service.py:39-40,428-429`. Those in `tools/demo_service.py` and the two host names in `tools/deploy_service.py` cannot be overridden by arguments; `tools.deploy_service` has `--jump-user` and `--board-user` for the accounts.
- **The real Bluetooth addresses of the two boards are built-in defaults.** Without `boards.json`, `load_boards()` returns the addresses at `tools/demo_boards.py:10` and reports no error. With other boards or another machine it will try to connect to devices that do not exist. This machine has `.comms-local/boards.json`.
- **`python demo.py service --start` follows the newest local deployment record.** Without one it falls back to `BOARD_SOURCE` (`tools/demo_service.py:16`), the 28 September folder, with the dummy model. A deployment made by hand, or from another laptop, leaves no record here, so `--start` would then start the old code, or the folder of an older record.
- **`tools/deploy_service.py` has never connected to the Ultra96.** Its board-side program was verified in WSL only; its SSH half (`paramiko`, two hops) has never run. It needs `paramiko` (in `requirements-dev.txt`, added with the documents after `3b94990`) and both host keys in `~/.ssh/known_hosts`. Login problems end with a traceback, not a `FAILED:` line (inferred from the code).
- **A service started by `python demo.py service --start` is the foreground process of that SSH session.** Closing that terminal, the laptop sleeping or the VPN dropping all make the service exit with the session (inferred from the code, not measured). This applies only to the `--start` path. A service started by `tools.deploy_service`, like the 28 September process started by `co_deploy.py`, runs in its own session and does not depend on an SSH session.
- **The phone's host, host keys and session ID are compiled into the app.** `Configuration.swift:8-12`; `IntegrationController.swift:74` holds the session the client uses, and the form text `session ltc-comms` in `SetupViewController.swift:51` repeats it, so both change together. Changing the Ultra96 or the session ID means rebuilding the app. Direct mode (`useJump` off) was never verified on site; V1 keeps using the jump host.
- **The phone's "automatic retry" means logging in to both SSH hops again and again.** When the Ultra96 service is not running, the session does not match, or another subscriber displaced the phone, the phone treats each case as a closed connection. It logs in to the jump host and the Ultra96 again with the passwords, at intervals that start at 0.5 seconds and double up to a cap of 5 seconds, with no limit on attempts, for as long as the app is in the foreground (`CommsClient.swift:181-213`). Whether the jump host limits frequent logins cannot be confirmed from the repository.
- **A different laptop needs `known_hosts` first.** Both SSH hops check host keys strictly, for the tunnel, `demo.py service` and `tools.deploy_service`, and nothing in the repository writes `known_hosts`.
- **The single-board diagnostic tools cannot choose a board.** `laptop.ble_counter_receiver`, `laptop.mtu_probe` and `tools.rehearse_comms --ble` scan by service UUID and connect to the first board they find. Both boards advertise the same name, so power only one board when using these tools. They also do not set the rate; the board keeps its last rate. `tools.check_board left|right` connects by the board's address and sets the rate, so the other board may stay powered.
- **The opt-in Linux deploy test stops processes.** With `B07_LINUX_DEPLOY_TEST=1`, pytest runs `tests/linux/deploy_remote_test.sh`, which starts and `pkill`s this user's `ultra96.server` processes inside WSL Linux. Never run it on the Ultra96.
- **`flash.py` rewrites the Git-tracked `comms_fixtures.h` every time.** After a change to `common/dummy_fixtures.json`, the boards must be reflashed before their data changes.
- **`patch_export.py` recognises only one export.** It matches the Week 7 export by the SHA-256 of `Assembly-CSharp.cpp` and the hashes of four method bodies. A project re-exported from `vis/` is rejected with `Unknown receiver source; expected the verified sanitized import.` and is not changed.
- **The evidence does not record the board or server versions.** The source fingerprint in the report describes only the laptop's working tree.
- **Phone evidence is totals only.** Per-result IDs on the phone side were never saved.
- **The Ultra96 diagnostic log has a 50 MiB limit.** After the limit it only stops logging, and `status.json` marks the log incomplete.
- **No range test was done.** The assessment requirement that "the boards are not connected to the laptop's USB" has no dedicated evidence either.

### Neither end records rejection reasons

- **Ultra96 service:** invalid frames, mismatched fields, mismatched sessions or versions, identity conflicts and exhausted capacity are all caught by the same `except`. It only does `rejected += 1` and closes the connection. It writes no log and sends no message back (`ultra96/server.py:242-243`). The service's log lines are an INFO line for each accepted input (`:273-274`), an ERROR line when a listener task dies (`:218`), and the model warnings, at most one of each kind per second (`ultra96/model.py:143-148`). Its JSON lines on standard output are `model_ready`, `listening`, `stopped` (with the metrics, printed only once, when the process stops, `ultra96/server.py:519`), `observation_stopped` with `--event-log-dir` (`:464`), and in failure cases `model_failed` and `exit_with_model_threads`. The metrics cannot be queried while it runs.
- **Laptop:** no reason is recorded for any transport failure. A TLS connect or handshake failure increments only `transport_errors`. An ACK timeout or a mismatched ACK increments both `ack_errors` and `transport_errors` (`laptop/bridge.py:452,465` for one frame at a time; `:618,664` for the ACK window). Only BLE failures write `BLE attempt failed: …` (`:802`).
- **Consequence:** an expired certificate, a session mismatch, a blocked port and a protocol version mismatch between the two ends (for example the version-3 laptop against the version-2 service still on the Ultra96) look alike in both logs. On the laptop the only difference is whether `ack_errors` grows as well. An end that has not moved to version 3 shows up as connections that are closed silently. So every end upgrades together, which is also the owner's rule: only the newest version is supported, with no interoperability between versions (section 8, step 1 of the hand-off document).
