## Role and boundaries

- Each glove has one FireBeetle ESP32. The firmware makes the board a BLE peripheral and GATT server. The laptop is the central.
- The firmware does four things. At each send tick of the configured rate it takes one sample from the glove module and, unless the module says IDLE, scales it. It packs the sample into a fixed-length, little-endian binary packet (38 bytes, protocol version 3). It hands the packet to the one authenticated laptop through protected BLE notifications. It provides source-side counters and a control channel, which the laptop uses for reconciliation, rate changes and file transfer.
- Upstream boundary: the glove module, four functions declared in `comms_glove.h` (`gloveBegin`, `gloveUpdate`, `gloveRead`, `gloveShouldSend`; see "Glove module and movement gating"). The build switch `COMMS_GLOVE_MODULE` picks the implementation. The default environments link the built-in dummy module `src/dummy_glove.cpp`, which hands over the rows of the dummy data table (11 values per row, in the version-3 channel order) as physical floats. The `-glove` environments link Siqiang's sensor module: a byte-identical copy, under `firmware/esp32/lib/glove_sensor/`, of the files he pushed to the team repo on 2026-10-15 (`hardware/gloves/integration_files/`, team commit `51593be`), plus the send decision in `src/glove_module.cpp`. The I2C and ADC code is Siqiang's; Communications code has none. Status: built (all six environments compile and link: the left, right and both `-glove` environments on 2026-10-15, the default `firebeetle32` and `firebeetle32-unprotected-diagnostic` on 2026-10-16 at `4c6ab4c`; with the `gloveBegin()` retry of 2026-10-16, `firebeetle32-right` and `firebeetle32-right-glove`, the two images flashed that afternoon, and `firebeetle32-left`, flashed on 2026-10-17; host tests pass). On hardware (2026-10-16, right board; the left board, plain build only, on 2026-10-17): the dummy module, plain and gated, verified; the `-glove` build verified on a board without sensors, where `gloveBegin()` fails (three tries since the retry of decision D38) and the board still advertises, connects through its existing bond and answers commands but sends nothing (see "Verifying gating on a board"). Siqiang's module has not run with sensors: no glove has been flashed. The version-3 layout stays 11 values: the IDLE/MOVING state does not travel in the packet, because the glove sends only while Siqiang's detector says MOVING (his answer of 2026-10-15). The scales are still provisional (see "Real glove data packet: version 3"). The interface is in section 7.1 of the hand-off document, and who does what at this hand-over is in its section 3.1. The log of real samples asked of Siqiang for Fri 2026-10-16 is not in the team repo yet (as of `be97a04`, the team main after pull request #20).
- Downstream boundary: when `esp_ble_gatts_send_indicate` returns `ESP_OK`, the packet counts as "submitted". This is evidence level 1 (source statistics field `submitted`, hand-off document section 4.7). Submission is not delivery. The laptop proves delivery by reconciliation against the source statistics ([detail chapter 3](03-laptop-relay-and-tools.md)).
- Pairing left and right samples, building model windows, deciding gesture or idle, and producing labels belong neither to the firmware nor to Communications. They are Wen Ree's work on the model side. Label names, how often a label fires, and whether several identical labels in a row mean one action or several are agreed between Wen Ree and Jie Ling; Communications passes every result through unchanged and never merges, splits, filters or reinterprets results (hand-off document sections 3 and 3.1). The two boards do not know about each other.
- The firmware has no network: no Wi-Fi, no SSH, no TLS, and no session ID. The VPN, `stujump`, and the Ultra96's ingest port 8888 and gateway port 9999 have nothing to do with the firmware.
- This chapter also covers the host-side `flash.py`, `tools/check_board.py`, `tools/demo_boards.py`, `tools/generate_dummy_fixtures.py`, `tools/sync_glove_module.py`, `common/dummy_fixtures.json` and their tests.

## Data formats and constants

**GATT service and characteristics.** All UUIDs end in `-7a45-4dc4-b678-3f2d5a9c1001` (`main.cpp:43-50`). The service reserves 32 handles when it is created (7 characteristics plus 4 CCCDs, `main.cpp:473-474`). Neither version 3 nor the gating of 2026-10-15 changed the GATT table (UUIDs, properties, permissions). Version 3 changed the length of the 0005 value (32 to 38 bytes) and of the command frames; gating changed only the length of the 0006 value (24 to 36 bytes).

| UUID prefix | Code constant | Properties | Permissions in the protected build | Value | Purpose |
|---|---|---|---|---|---|
| `6e1c0001` | `kServiceUuid` | Primary service | — | — | Put in the advertising packet |
| `6e1c0002` | `kCounterUuid` | Notify + CCCD | Characteristic `READ_ENC_MITM`; CCCD `READ_ENC_MITM` plus `WRITE_ENC_MITM` | 4-byte `uint32` little-endian counter | Diagnostic counter stream |
| `6e1c0003` | `kMtuControlUuid` | Write | `WRITE_ENC_MITM` | Exactly 2 bytes, `uint16` little-endian: the requested probe length | MTU probe request |
| `6e1c0004` | `kMtuProbeUuid` | Notify + CCCD | Same as 0002 | N bytes; byte i equals the low 8 bits of i | MTU probe reply |
| `6e1c0005` | `kSensorUuid` | Notify + CCCD | Same as 0002 | 38-byte version-3 sensor packet | Data stream |
| `6e1c0006` | `kSourceStatsUuid` | Read | `READ_ENC_MITM` | 36-byte source statistics | Reconciliation |
| `6e1c0007` | `kControlUuid` | Write | `WRITE_ENC_MITM` | Control frame of 14 to 194 bytes | Control requests |
| `6e1c0008` | `kResponseUuid` | Notify + CCCD | Same as 0002 | Response of 14, 16, 50 or 52 bytes | Control responses |

- The write characteristics have only `PROPERTY_WRITE` (write with response). Prepared writes and non-zero offsets are not supported.
- The diagnostic build (`COMMS_UNPROTECTED_DIAGNOSTIC=1`) sets none of these permissions.
- Notification gate: the firmware sends a notification only when four conditions all hold: connected, the characteristic is subscribed, authenticated (the diagnostic build does not require authentication), and no bond erase in progress (`main.cpp:92-94`, `comms_security.h:16-19`).

**Advertising and device name.**

| Item | Value |
|---|---|
| Device name | `LTC-COMMS` (the same on both boards; they are told apart by Bluetooth address and by the `device_id` in the packet) |
| Advertising content | Service UUID `6e1c0001-…`; scan response enabled |
| Advertising interval, transmit power | Not set by the firmware; library defaults |
| Simultaneous connections | 1. While a connection exists, a new connection is disconnected immediately |
| Advertising start and stop | Stops when a connection is established; the main loop restarts it after a disconnect; no advertising during a bond erase |

**Security parameters (protected build, `main.cpp:239-253`).**

| Parameter | Value | Meaning |
|---|---|---|
| `ESP_BLE_SM_AUTHEN_REQ_MODE` | `ESP_LE_AUTH_REQ_SC_MITM_BOND` | LE Secure Connections, MITM, bonding |
| `ESP_BLE_SM_IOCAP_MODE` | `ESP_IO_CAP_OUT` | Display only (DisplayOnly); the laptop enters the passkey |
| `ESP_BLE_SM_MAX_KEY_SIZE` | 16 | Key length 16 bytes |
| `ESP_BLE_SM_SET_INIT_KEY`, `ESP_BLE_SM_SET_RSP_KEY` | `ESP_BLE_ENC_KEY_MASK` plus `ESP_BLE_ID_KEY_MASK` | Distribute the encryption key and the identity key |
| `ESP_BLE_SM_ONLY_ACCEPT_SPECIFIED_SEC_AUTH` | Enabled | Pairing below the mode above is not accepted |
| `kRequiredAuthMode` | `0x0d` (`comms_security.h:10`) | Application-level gate: all three bits must be set: SC `0x08`, MITM `0x04` and bond `0x01`. `main.cpp:37-38` uses `static_assert` to confirm that it equals the SDK's `ESP_LE_AUTH_REQ_SC_MITM_BOND` |
| Passkey | 6 decimal digits, generated fresh by the stack for each pairing | Printed only to the local serial port: `PAIR LOCALLY: enter NNNNNN on Windows (do not record)` |

Each parameter is set with its own call to `esp_ble_gap_set_security_param`, and each return value is checked. If any one fails, the firmware prints `ble_security_configuration_failed` and aborts start-up.

**Sensor packet: 38 bytes, little-endian, protocol version 3 (`kPacketSize = 38`, `comms_packet.h:11-15`).** The Python format is `<2sBBIII11h` (`common/sensor.py:20`). Version 3 is the only version the firmware produces and the only one any receiver accepts (the owner's rule; hand-off document sections 4.2 and 8, step 1). The layout is provisional (see "Real glove data packet: version 3").

| Offset | Length | Type | Field | Values |
|---|---|---|---|---|
| 0 | 2 | ASCII | Packet magic | `LC` (`4C 43`) |
| 2 | 1 | `uint8` | Version | Always 3 (`kPacketVersion`). The version byte says nothing about whether the values are dummy rows or real readings |
| 3 | 1 | `uint8` | `device_id` | 1 means left, 2 means right; any other value makes serialization fail |
| 4 | 4 | `uint32` | `boot_id` | Taken once per power-up with `esp_random()` |
| 8 | 4 | `uint32` | `seq` | Starts at 0, increases by 1 for each generated sample, wraps modulo 2^32 |
| 12 | 4 | `uint32` | `uptime_ms` | `millis()` taken right after this tick's `gloveRead()` and `gloveShouldSend()` (`main.cpp:409`; until 2026-10-15 it was taken at the start of the pass); the two boards are not synchronized |
| 16 | 22 | 11 × `int16` | Channels 0 to 10 | −32768 to 32767, in the order below |

| Channel | Offset | Field | Physical value from the sensor module | Wire value = physical value × | Representable range |
|---|---|---|---|---|---|
| 0, 1, 2 | 16, 18, 20 | `ax` `ay` `az` | g, gravity removed | 10000 | ±3.2767 g |
| 3, 4, 5 | 22, 24, 26 | `gx` `gy` `gz` | °/s, bias removed | 100 | ±327.67 °/s |
| 6, 7, 8 | 28, 30, 32 | `yaw` `pitch` `roll` | degrees | 100 | ±327.67° |
| 9, 10 | 34, 36 | `flex1` `flex2` | 0.0 to 1.0 | 10000 | ±3.2767 |

- The factors are `kChannelScale` in `comms_sample.h:22-24` and `SCALES` in `common/sensor.py:18`. The board service divides by `SCALES` to give the model physical floats, so the two lists must stay identical. They are provisional until checked against Siqiang's real sample log.
- With the default (dummy) environments the 11 values are a whole row `kDummyFixtures[randomWord % kDummyFixtureCount]`, chosen independently of `seq`. The rows are in wire units. The dummy module divides each value by its scale factor (`dummyFixtureSample`, `comms_dummy_gate.h:27-33`), and `prepareSample` scales it back, so the packet carries exactly the row: `host_glove.cpp` checks that every row and every `int16` value of every channel survives the round trip, and that the packet equals the one `serializeFixturePacket` (`comms_packet.h:51-57`) writes from the row directly. With the `-glove` environments the values are Siqiang's 11 floats, scaled by `prepareSample`.
- `serializePacket` (`comms_packet.h:27-45`) takes a reference to an array of exactly 11 values, so a caller with fewer values does not compile. It returns false for a null output, a capacity below 38, or a device ID other than 1 or 2. Each value is written as the low byte then the high byte of its `uint16` representation.
- The notification payload limit is MTU − 3, so the sensor stream needs an ATT MTU of at least 41 (`sensorFitsMtu`, `comms_security.h:21-22`, which follows `kPacketSize`).
- The golden vectors are in `tests/fixtures/comms-golden.json`, with the binary copies `comms-dummy.bin` and `comms-boundaries.bin`. They are hand-specified 38-byte version-3 packets, never regenerated by the codec under test, and each also carries the matching `SENSOR_BATCH` message (`v` 3, `request_id` null). `comms-dummy.bin` is device 2, `boot_id` `0x78563412`, `seq` 42, `uptime_ms` `0x01020304`, with dummy row 1 as values (`1200, -300, -8500, 4000, -2000, 1500, 1250, -3000, 600, 6000, 5500`): `4c430302123456782a00000004030201b004d4feccdea00f30f8dc05e20448f4580270177c15`. `comms-boundaries.bin` is device 1, `boot_id` and `seq` both `0xffffffff`, `uptime_ms` 0, values `-32768, 32767, -1, 0, 1, 255, 256, -256, 32766, -32767, 4660`: `4c430301ffffffffffffffff000000000080ff7fffff00000100ff00000100fffe7f01803412`. `host_packet.cpp` holds a literal copy of row 1 (`host_packet.cpp:17-19`), so editing `common/dummy_fixtures.json` never moves the golden vector.

**Source statistics record: 36 bytes, little-endian (`kSourceStatsSize = 36`, `comms_source_stats.h:13`; 24 bytes until 2026-10-15).** The Python format is `<4sBB2xIIIIIII` (`laptop/source_audit.py:14`).

| Offset | Length | Type | Field | Notes |
|---|---|---|---|---|
| 0 | 4 | ASCII | Statistics magic | `LCS3` (`comms_source_stats.h:49-52`); it was `LCS1` in version 2 |
| 4 | 1 | `uint8` | `device_id` | 1 or 2 |
| 5 | 1 | `uint8` | Flags | Bit 0 (`kSourceFlagGated`, `comms_source_stats.h:15`): a gated source, which skips the ticks its glove module calls IDLE. Taken from `kGloveGated`. Other bits 0 |
| 6 | 2 | — | Reserved | Always 0 |
| 8 | 4 | `uint32` | `boot_id` | The same as in the sensor packet |
| 12 | 4 | `uint32` | `next_seq` | The next sequence number to be allocated, which is also the number of samples generated since this power-up |
| 16 | 4 | `uint32` | `submitted` | Number of successful sensor packet submissions |
| 20 | 4 | `uint32` | `failures` | Number of failed sensor packet submissions |
| 24 | 4 | `uint32` | `idle` | Send ticks the glove module called IDLE (`gloveShouldSend()` false); nothing sent, no `seq` |
| 28 | 4 | `uint32` | `unread` | Send ticks without a valid sample (`gloveRead()` false); nothing sent, no `seq` |
| 32 | 4 | `uint32` | `refused` | Samples `scaleSample` refused (NaN, infinity, or out of range under the drop policy); nothing sent, no `seq` |

The six counters (`next_seq`, `submitted`, `failures`, `idle`, `unread`, `refused`) are totals since power-up and wrap as `uint32`; `boot_id` is the random identifier of this power-up (`main.cpp:451`). Only sensor packets and sensor ticks count. Submissions of the counter, the probe and control responses do not count. A tick is counted only while the laptop is subscribed to 0005 with the gate open and an MTU of at least 41, so `next_seq + idle + unread + refused` grows by one per send tick while the laptop listens (less any tick counted as `race_dropped`) and not at all otherwise. `clamped` and `race_dropped` are on the serial line only (see "Serial output"). The marker follows the packet version: `static_assert(kPacketVersion == 3)` (`comms_source_stats.h:16`) stops the build whenever `kPacketVersion` changes, as a reminder to update the `LCS3` marker and the assert together. It does not read the marker itself. The marker stayed `LCS3` when the record grew to 36 bytes, because the 24-byte `LCS3` record never left the right board; the length alone now refuses older firmware. The laptop refuses, before subscribing, any value that is not exactly 36 bytes with `source statistics must contain exactly 36 bytes; flash this board with the current firmware` (`laptop/source_audit.py:61-64`); this is what a version-2 board (24 bytes, `LCS1`) and a board with the version-3 firmware of 2026-10-14 (24 bytes, `LCS3`) now get. It then refuses non-zero reserved bytes, a marker other than `LCS3` (`invalid source statistics magic; flash this board with the current firmware`) and unknown flag bits (`laptop/source_audit.py:66-73`).

**Control frame header: 14 bytes, little-endian (`<2sBBBBII`).** Requests are written to 0007. Responses are notified on 0008. One BLE write carries exactly one frame. There is no TCP-style framing.

| Offset | Length | Field | Rule |
|---|---|---|---|
| 0 | 2 | Magic | ASCII `B7` (the team number B07, not Week 7). No response when it is not `B7` |
| 2 | 1 | Control version | Must be 1, otherwise status 6 |
| 3 | 1 | Opcode | The response opcode is the request opcode with the top bit set (plus `0x80`) |
| 4 | 1 | `device_id` | Must equal this board's ID, otherwise status 1 |
| 5 | 1 | Status | Must be 0 in a request, otherwise status 1; for responses see the status code table |
| 6 | 4 | `id` | `uint32`; must not be 0, otherwise status 1; returned unchanged in the response |
| 10 | 4 | `offset` | `uint32`; must be 0 for command, rate change, file begin and file abort |
| 14 | 0 to 180 | Payload | The whole frame is at most 194 bytes, and not more than MTU − 3 |

`ControlEngine::process` (`comms_control.h:65-103`) first returns 0, with no response, for a null input or output, a frame shorter than 14 bytes, an output buffer smaller than `kControlMinOutput` (52 bytes), or a magic other than `B7`. It then checks the control version, then frame length, `device_id`, status and `id`, and finally it dispatches on the opcode.

| Opcode | Name | Request payload | Success response | Rules |
|---|---|---|---|---|
| `1` | Command | 38-byte version-3 sensor packet (the request frame is 52 bytes) | 52 bytes: header plus the transformed packet | The payload must be exactly 38 bytes (`kPacketSize`) and `offset` must be 0. The payload's packet magic must be `LC`, its version 3 (`kPacketVersion`), its `device_id` and `boot_id` this board's current values, and its `seq` must equal `id`; otherwise status 1. A 32-byte version-2 payload therefore gets status 1, whatever its version byte. These checks run before the cache lookup and the transform, so a rejected command changes no state (`comms_control.h:129-133`). If the same `id` is already in the cache: identical content returns the cached response unchanged, with no second transform; different content gives status 5. If `id` is not greater than the highest `id` handled in this connection: status 5. Otherwise the firmware adds 1 to each of the 11 channels (wrapping as `uint16`, so 32767 plus 1 becomes −32768), replaces `uptime_ms` with this pass's `millis()`, stores the result in the cache and returns it (`comms_control.h:127-160`). |
| `2` | Rate change | 2 bytes, `uint16` little-endian, in Hz | 16 bytes: header plus the rate now in effect | The payload must be exactly 2 bytes, `offset` 0, and the value from 1 to 200; otherwise status 1. Takes effect immediately (`comms_control.h:84-92`). |
| `0x10` | File begin | 36 bytes (`kFileMetadataSize`): `uint32` total length plus 32-byte SHA-256 | 14 bytes | The payload must be exactly 36 bytes, `offset` 0, and the total length from 1 to 65536; otherwise status 1. Resent with the same `id`: if length and digest match, the reply is success and the response `offset` is the number of bytes received (also when the file is already complete); if they differ, status 5. Another file not yet complete: status 2. The previous file already complete: it is discarded and the new file starts. Memory allocation fails: status 2 (`comms_control.h:170-189`). |
| `0x11` | File chunk | 1 to 180 bytes | 14 bytes; `offset` is the next expected offset | Payload length outside 1 to 180: status 1. `id` is not the current file, there is no file, or `offset` is greater than the bytes received (a gap): status 3. `offset` plus length exceeds the total length: status 1. `offset` is less than the bytes received (an old chunk resent): status 3 if the chunk crosses the received position, status 5 if its content differs from what was received, accepted if it is identical. `offset` equals the bytes received: the chunk is written (`comms_control.h:190-207`). |
| `0x12` | File end | None | 50 bytes: header plus `kFileMetadataSize` (`uint32` length plus 32-byte digest) | The payload must be empty, otherwise status 1. Wrong `id`, `offset` not equal to the total length, or not all bytes received: status 3. On the first end the firmware computes SHA-256; a mismatch gives status 4. Another end after success returns the same 50 bytes without recomputing (`comms_control.h:208-222`). |
| `0x13` | File abort | None | 14 bytes | `offset` must be 0 and the payload empty, otherwise status 1. A file exists with a different `id`: status 3. Otherwise the file is discarded and success is returned; success is also returned when there is no file (`comms_control.h:96-100`). |
| Other | — | — | 14 bytes, status 6 | — |

| Status code | Enum name | Meaning |
|---|---|---|
| 0 | `ControlOk` | Success |
| 1 | `ControlInvalid` | Invalid field, length or value (including a command payload whose packet magic is not `LC`, whose version is not 3, or whose length is not 38) |
| 2 | `ControlBusy` | Control queue full, another file in transfer, or out of memory |
| 3 | `ControlOrder` | Order error: a gap, an end before all bytes arrived, an `id` mismatch |
| 4 | `ControlIntegrity` | SHA-256 mismatch |
| 5 | `ControlConflict` | Same `id` with different content, or a command `id` not greater than the highest one handled |
| 6 | `ControlUnsupported` | Unsupported control version or opcode; or rejected directly in the callback because the MTU is too small or the frame is longer than MTU − 3 |

### Real glove data packet: version 3 (built; scales provisional)

The direction of olsonwangyj, the Communications owner (2026-10-14; proposed to the teammates and final when they confirm): the 11 values are sent as 11 `int16` with fixed scale factors, in a new protocol version, version 3 (hand-off document sections 4.2, 8 step 1 and 13). **This is in the code since the evening of 2026-10-14 (branch `comms/protocol-v3`): built, and verified on the right board with the firmware of 2026-10-14, before gating, and again on 2026-10-16 with the firmware of that day, plain and gated, against a service on the laptop and, for the plain build, through the redeployed Ultra96 service, and later that day with the plain build with the `gloveBegin()` retry against a service on the laptop (see the status table below).** The layout and the factors are in "Data formats and constants" above. What is still open or worth knowing:

- **The IDLE/MOVING state does not travel; the layout stays 11 values.** Siqiang answered on 2026-10-15 that the gloves should send data only while his detector says MOVING, and nothing while IDLE. The owner asked that the Communications firmware call his decision. So the state is applied at the source (see "Glove module and movement gating") instead of being a 12th field, and the 38-byte layout, the MTU floor and `on_sample` stay as they are. The layout is still provisional only for the scale check against real samples and Wen Ree's agreement.
- **Measured so far: one board.** Application-level byte rate: 38 bytes × 50 Hz × 2 boards = 30.4 kbps while both gloves move; a gated glove sends nothing while IDLE, so the average is lower. One board sending the 38-byte packet at the 50 Hz setting was clean for a 65 s check on 2026-10-14 (2934 samples, version-3 firmware without gating) and on 2026-10-16 with the firmware of that day (3022 samples; the gated dummy 900 samples sent and 2140 idle ticks; with the `gloveBegin()` retry, later that day, 3033 samples; status table below). Two boards together with the 38-byte packet, any setting above 50 Hz with it, and Siqiang's detector on a real glove have not been measured. The 32-byte version-2 dummy packet was measured clean at 33.8 kbps combined (the 70 Hz setting, which delivered about 66 packets/s per board with the old send tick; hand-off document section 6.1).
- **Only the newest version is supported (the owner's rule, 2026-10-14).** A new version number means no receiver reads the new layout with the old 8-value one. There is no interoperability between versions: each component accepts only version 3, and an upgrade means reflashing both boards, redeploying the Ultra96 service and reinstalling the phone app together. Version 3 therefore replaced versions 1 and 2 everywhere, including the dummy test data (now 11 values per row) and the formula dummy (removed); there is no transition period (hand-off document section 8, step 1). The laptop carries the packet version into the `v` field of `SENSOR_BATCH` (`common/sensor.py:60`), and the Ultra96 service writes `v` 3 into every `GESTURE_RESULT` (`ultra96/server.py:333`, `367`), so the phone's result checks see version 3 too.
- **The scales are checked before they are fixed (the owner's direction, 2026-10-14).** The factors are checked against the log of real samples that Siqiang pushes to the team repo (asked for by Fri 2026-10-16, a proposed date; hand-off document section 6.4; not in the team repo as of `be97a04`) before they are fixed. A change of factors changes `kChannelScale` and `SCALES` together. Once the gloves run the Communications firmware, such a log can be recorded through the chain: a build with `-DCOMMS_GLOVE_SEND_ALL=1`, `python demo.py run`, then `python -m tools.export_capture` (CSV in the physical units; [detail chapter 3](03-laptop-relay-and-tools.md)).
- **Values outside the `int16` range (to be agreed with Wen Ree; asked in the message).** The two options are: clamp the value to the `int16` limit, or drop that one sample. The firmware supports both: `scaleSample` clamps by default, and a build with `-DCOMMS_OUT_OF_RANGE_DROP=1` drops the sample instead (provisional; decision D13 in hand-off document section 6.5). Either way Communications counts it and never drops a connection or a whole gesture. Since 2026-10-15 the counts are reported: a refused sample in `refused` (source statistics and the `comms_stats` serial line), a clamped channel value in `clamped` (serial line only). A clamped value cannot be told apart from a real value at the limit (3.2767 g can be either); if the model needs to know which samples were clamped, a per-sample flag is needed, which changes the packet and `on_sample` again. Neither option guarantees that a gesture is still recognised (hand-off document sections 8 step 1 and 13).
- **The model gets physical floats (the owner's direction, 2026-10-14; final when Wen Ree confirms).** The transport stays `int16`. On the Ultra96, Communications decodes each value and divides it by the same factor (`physical_values`, `common/sensor.py:92-98`; built), so the model receives the 11 values in the agreed physical units; any normalisation is Wen Ree's (hand-off document section 7.2). Restoring cannot recover precision lost when packing: acceleration and flex keep 4 decimal places, angular rate and angles 2.
- Ranges that can be read from Siqiang's module (`hardware/gloves/integration_files/glove_sensor.cpp`; he named `hardware/gloves/model_threshold_variant_1/debug_esp32_ml_movement_detector_v1.ino` the authoritative sketch on 2026-10-15, and the module's `movement_model_params.h` is identical to that sketch's): the accelerometer is set to ±2 g and the gyroscope to ±250 °/s (`glove_sensor.cpp:27-28`, `452-455`); the flex value is the 12-bit ADC reading divided by 4095 (`522-523`); `getEulerAngles` computes the angles with `atan2f` and `asinf` (`255-276`), so yaw and roll are within ±180° and pitch within ±90°. Acceleration has gravity removed (`getLinearAcceleration`, `278-290`), so one axis can in theory reach about ±3 g, still within ±3.2767 g, with a margin of only about 0.28 g (this is an inference). So in normal use every value is expected to fit, but that is not guaranteed: the final value depends on the module's processing, not only on the sensor's range (for example the module subtracts the gyro calibration bias from each reading, `504-506`). The actual range of each value is settled by the real sample log.

## Workflows

**A. Build and flash (`python flash.py` with no options, or `python flash.py --glove`, `flash.py:90-126`)**

1. Run `python -m tools.generate_dummy_fixtures`. It rewrites `firmware/esp32/include/comms_fixtures.h` from `common/dummy_fixtures.json`. With `--glove`, then run `python -m tools.sync_glove_module --check`; a stale or missing copy of Siqiang's module stops the script before any build (`flash.py:92-95`).
2. Build `firebeetle32-left`, then `firebeetle32-right` (with `--glove`: `firebeetle32-left-glove`, then `firebeetle32-right-glove`; the same applies to the uploads in steps 6 and 7). Only after both succeed does the script ask for a board to be connected. PlatformIO is taken from `~/.platformio/penv/Scripts/platformio.exe` first, and from `platformio` on PATH if that is missing (`flash.py:16-21`).
3. Prompt to connect the first board. The operator must press Enter and nothing else. Any other input is an error and exits; `q` cancels.
4. Run `platformio device list --serial --json-output` to list the serial ports. A port name must be `COM` plus digits; a duplicate or a bad format is an error. With one port, it is used. With several ports, the operator must type the port name, and it must be in the list.
5. Using PlatformIO's own interpreter and `esptool.py` (`~/.platformio/penv/Scripts/python.exe` and `~/.platformio/packages/tool-esptoolpy/esptool.py`), run `--chip esp32 --port COMx read_mac` with a 30-second limit. The output must contain exactly one factory MAC. The Bluetooth address is the factory MAC with 2 added to its last byte (`flash.py:68-87`).
6. First board: write the mapping as `incomplete` first (only `left`), then flash `firebeetle32-left`. This way, the old mapping can no longer be used for capture before the flash changes the board's identity.
7. Prompt to unplug the left board and connect the second board. Repeat steps 4 and 5. If the address equals the first board's, the script reports an error and exits without flashing. Then flash `firebeetle32-right`.
8. After both boards are flashed, write the complete mapping (`status: ready`), print `Board mapping saved: <path>`, `LEFT=…` and `RIGHT=…`, and finally print `Both uploads succeeded. …`.
9. Failure paths: any subprocess failure stops the script at once and returns that subprocess's exit code. No serial port, an invalid port name, no unique MAC read, a MAC last byte above 253, PlatformIO tools not found, and a MAC read timeout all return 2. A failure before the first board's MAC is read (for example a build failure or a MAC read failure) leaves the existing mapping unchanged. A failure after it is read (including a failed left or right flash) leaves the mapping at `incomplete`; `flash.py --pair` and `demo.py run` are then blocked until a full `python flash.py` (or `python flash.py --glove`) run completes.

A single board can also be flashed without `flash.py` (see "Reflash one board" under "How to run and verify"), and checked afterwards with `python -m tools.check_board`.

**B. Power-up (`setup()`, `main.cpp:434-499`)**

1. Open serial at 115200. Call `gloveBegin()` through `comms::beginWithRetries` (`comms_glove.h:86-98`, `main.cpp:441-448`; since 2026-10-16, decision D38): up to `COMMS_GLOVE_BEGIN_ATTEMPTS` (default 3) calls, stopping at the first that returns true. After a failed try that is not the last, print `glove_begin_failed attempt=<n> retry_ms=<ms>` and wait `COMMS_GLOVE_BEGIN_RETRY_MS` (default 500 ms); nothing is printed or awaited after the last try. Then print `glove_begin ok=<0|1> module=<dummy|external> gated=<0|1> attempts=<n>`, where `attempts` is the number of calls made (`main.cpp:449-450`). This comes before BLE: the dummy returns true at once (`attempts=1`); Siqiang's module calibrates the gyroscope (by the code a 2 s settle plus 1000 IMU reads, each followed by a 2 ms delay, so about 4 to 4.5 s, `glove_sensor.cpp:33-35`, `161-178`; Siqiang gives about 5.1 s for `gloveBegin()`; not measured), during which the glove must be held still, and the board advertises only after the last try. Each try repeats his calibration, so a glove whose calibration fails twice advertises up to about 10 to 11 s later than normal; a try that fails before the calibration (no sensor, or issue 5) returns at once, and the three tries then cost about 1 s, the two pauses (verified on the right board without sensors: `comms_ready` at 2.44 s instead of 1.44 s with one try). A `false` after the last try does not stop start-up: the board still advertises, and its send ticks then count as `unread` (verified on the right board without sensors on 2026-10-16, before and after the retry; see "Verifying gating on a board"). Then set `boot_id = esp_random()` and write it into the source statistics too.
2. Create `ControlEngine(device ID, boot_id, SHA-256 function, initial rate)` with `new (std::nothrow)`, then create the state mutex `connectionStateMutex`.
3. Call `BLEDevice::init("LTC-COMMS")`. Set the security parameters (the diagnostic build only prints `ble_security=UNPROTECTED_DIAGNOSTIC not_protected_evidence`). Register the custom GAP and GATTS callbacks. Set the local MTU to `ESP_GATT_MAX_MTU_SIZE` and print `ble_local_mtu_configured`. A failure to set the MTU does not abort start-up; only the return code is printed.
4. Create the service and the 7 characteristics, start the service, advertise the service UUID with scan response on, set `bleReady`, and print `comms_ready …`.
5. Failure paths: if the `ControlEngine` allocation fails, the mutex cannot be created, or any security parameter fails, `setup()` returns directly. `bleReady` stays false, the main loop only idles (it does not call `gloveUpdate()` either), and the board does not advertise. A `gloveBegin()` that never returns has the same effect.

**C. Connection and authentication**

1. The laptop connects, and `onConnect` runs (`main.cpp:119-145`). If a connection already exists or a bond erase is in progress, the new connection is disconnected at once. Otherwise the firmware records the connection ID and the peer address, sets `authenticated` to false, clears the subscriptions, the control queue, the command cache, the file and any pending MTU probe, resets the MTU to 23, stops advertising and prints `ble_connected …`.
2. Protected build: the firmware itself calls `esp_ble_set_encryption(peer, ESP_BLE_SEC_ENCRYPT_MITM)`. On failure it prints `ble_security_request_failed` and disconnects.
3. A security request from the peer (`onSecurityRequest`) is accepted only when there is a current connection and no bond erase is in progress.
4. First pairing: the stack generates a 6-digit passkey, `onPassKeyNotify` prints it to serial, and the operator enters it on Windows with the input hidden. With an existing bond, the link is encrypted directly and no passkey appears.
5. `onAuthenticationComplete` (`main.cpp:189-202`) sets `authenticated` only when all four hold: the peer address equals the current connection's, the result is success, `auth_mode` contains the three bits of `0x0d`, and no bond erase is in progress. It then prints `ble_security_complete …`. The callback structure contains key material; the firmware does not print it.
6. After MTU negotiation, `onMtuChanged` updates `negotiatedMtu` only for the current connection ID and prints `ble_mtu_changed`.
7. The laptop subscribes by writing each CCCD. While connected, `CccdCallbacks` sets the four subscription flags to each CCCD's current value.
8. Failure paths: if the authentication result belongs to the current peer but does not meet the requirement, the firmware disconnects the peer. If the peer asks the firmware to enter a passkey (`onPassKeyRequest`), the firmware returns the invalid value `UINT32_MAX`, so that pairing fails. Numeric-comparison confirmation (`onConfirmPIN`) is always refused.

**D. Each main-loop pass (`loop()`, `main.cpp:501-608`; restructured on 2026-10-15)**

The glove module is never called under `connectionStateMutex`. The pass takes the mutex in short sections, and the BLE callbacks never wait for a sensor call.

1. Record `nowMs = millis()`. If `bleReady` is false, only call `delay(1)` and return.
2. Read serial commands.
3. Call `gloveUpdate()` once, outside the mutex, whether or not the laptop is connected (`main.cpp:506`).
4. Under the mutex, check whether the bond erase has finished and whether advertising must restart; after releasing it, restart advertising if needed and print `ble_advertising_restarted` (`main.cpp:508-529`).
5. Take the mutex (`main.cpp:531-554`). First discard an incomplete file that has been idle for more than 30 seconds. Then check the send tick with `sendTickDue` (`main.cpp:537`, `comms_sample.h:67-78`): a tick is due when `micros()` is at least one interval (`1000000 / rate` µs) past the last deadline. The next deadline is then one interval after the previous deadline, not after this pass, so a late tick only shortens the gap to the next one and the rate is kept. A tick owed more than one interval late restarts the deadline from now: the ticks a long pass covered are dropped, never sent as a burst. Until 2026-10-15 "last send" was set to the current time instead, which lowered the rate (see "Cautions and known limitations").
6. On a tick, protected build, connected but not authenticated: increment `security_suppressed`. The notification gate is closed, and no data is sent.
7. On a tick, 0002 subscribed and gate open: send the 4-byte counter. Only a successful submission increments the counter and prints `ble_notify_submitted`.
8. On a tick, 0005 subscribed and gate open: if the MTU is below 41, increment `mtu_suppressed`; the glove module is not read. Otherwise mark a sample as due. When 0005 is not subscribed or the gate is closed, nothing happens: the glove module is not read and nothing is counted. Release the mutex.
9. A sample is due: `produceSample()` (`main.cpp:399-431`). Without the mutex: fill the 11 values with NaN; `readOk = gloveRead(values)`; `moving = readOk && gloveShouldSend()` (so `gloveShouldSend()` is called only after a successful read); take `sampleMs = millis()`; run `prepareSample` on a copy of the counters, which gives one outcome: `SampleUnread` (`unread` + 1), `SampleIdle` (`idle` + 1, not scaled), `SampleRefused` (`refused` + 1) or `SampleSend` (scaled; `clamped` grows by the clamped channel values). Then take the mutex and check again that the gate is open, 0005 is subscribed and the MTU is at least 41. If so, commit the counters, and for `SampleSend` allocate `seq`, serialize with `sampleMs` as `uptime_ms`, submit, and increment `submitted` or `failures`. If not, the link changed during the read: increment `race_dropped` only; no counter is committed and no `seq` is taken. Release the mutex. So once the laptop has turned notifications off, nothing in the source statistics changes; the laptop checks exactly that after its quiesce read.
10. Take the mutex again (`main.cpp:558-593`). Control queue not empty, 0008 subscribed and gate open: take the frame at the head of the queue and pass it to `ControlEngine::process` with a 194-byte response buffer; if there is a response, notify it. This step is not bound by the sensor send tick, but it handles at most one frame per pass. If the rate changed, restart the tick deadline from the current time and print `b07_rate_changed` (`main.cpp:568-571`).
11. A pending MTU probe: if 0004 is not subscribed or the gate is closed, print `reason=not_ready`. If the length exceeds MTU − 3 or `ESP_GATT_MAX_MTU_SIZE − 3`, print a rejection. Otherwise send the N-byte probe packet and, on success, print `mtu_probe_submitted`.
12. Release the mutex. If 1000 ms have passed since the last report, print `alive` and `comms_stats`. Finally call `delay(1)`.

**E. Reading source statistics (the laptop reads 0006)**

1. The callback copies `sensorStats` and the sample counters under the mutex, serializes them to 36 bytes with the gated flag from `kGloveGated`, and uses that as the read response (`main.cpp:216-231`). The read itself changes no counter.
2. The read permission is `READ_ENC_MITM`. The stack rejects unencrypted reads.
3. The laptop reads once before subscribing to 0005 and once after stopping notifications. It refuses a value that is not 36 bytes or not `LCS3` (see "Source statistics record"), and it reconciles using `next_seq` and `boot_id` from the two reads. It also reports `gated` and the `idle`, `unread` and `refused` deltas, and judges a gated board's coverage by its ticks, not by its packets alone ([detail chapter 3](03-laptop-relay-and-tools.md)).

**F. Control writes (the laptop writes 0007; handled in the GATTS callback on the Bluetooth task, `main.cpp:267-301`)**

1. Only real WRITE events on the 0007 handle are processed. If the length is outside 14 to 194, `offset` is non-zero, it is a prepared write, or the value is empty: print `b07_control_rejected reason=malformed bytes=…` and send no response.
2. Checks: no bond erase in progress; the write's connection ID equals the current connection; connected; 0008 subscribed; authenticated; MTU at least 64; frame length not above MTU − 3; queue not full. If all hold, the whole frame is copied into the queue.
3. Otherwise increment `control_queue_rejected`. If the write came from the current connection, which is authenticated and has subscribed to 0008, and the frame starts with `B7`, the firmware immediately replies with a 14-byte rejection: status 2 when frame length and MTU are both acceptable (that is, the queue is full), status 6 when they are not. The rejection frame keeps the request's `id` and `offset`. In all other cases (not authenticated, 0008 not subscribed, a write from another connection) there is no response.
4. The stack sends the ATT-level write response. It only says that the write arrived, not that the application accepted it. Application acceptance is shown only by the response on 0008 (comment at `main.cpp:288-289`).

**G. MTU probe writes (the laptop writes 0003, `main.cpp:302-322`)**

1. Only real WRITE events on the 0003 handle are processed. The write must be exactly 2 bytes, with `offset` 0, not a prepared write, and a non-empty value; otherwise print `mtu_probe_rejected reason=malformed request_bytes=…`.
2. If the write comes from the current connection, 0004 is subscribed, the gate is open and no probe is pending, record the requested length; the main loop sends the probe (see D, step 11). Otherwise print `mtu_probe_rejected reason=pending` or `reason=not_ready`.

**H. Disconnect and reconnect**

1. `onDisconnect` (only for the current connection ID, `main.cpp:147-161`) clears authentication, the subscriptions, the control queue, the command cache and the highest handled `id`, and the file. It resets the MTU to 23, marks advertising for restart when no bond erase is in progress, and prints `ble_disconnected`.
2. The next main-loop pass restarts advertising and prints `ble_advertising_restarted`.
3. No samples are produced while disconnected: `gloveRead()` is not called, `seq` does not advance, nothing is counted, and there is no offline buffer. `gloveUpdate()` keeps running every pass, so the glove module's filters and movement detector stay current. `boot_id` does not change; after reconnecting, sequence numbers continue from where they stopped. The rate keeps its pre-disconnect value until a restart or another rate change.
4. Seen downstream, a reconnect can still leave gaps in `seq`. On a BLE disconnect the laptop discards that glove's queued samples (`laptop/bridge.py:920`, `114-120`), and on a TLS reconnect samples already written but not acknowledged count as ambiguous drops and are not resent ([detail chapter 3](03-laptop-relay-and-tools.md)). The disconnected time itself shows only as a jump in `uptime_ms`, because the board makes no samples then (hand-off document section 7.2). An IDLE period of a gated glove looks the same downstream: a jump in `uptime_ms` with no `seq` gap, while the board's `idle` count grows.

**I. Bond erase (type `erase-bonds` plus Enter on serial, `main.cpp:334-367`, `509-518`)**

1. Connected or already erasing: print `erase_bonds_rejected …` and do nothing.
2. Otherwise enter the erase state: set `authenticated` to false, stop restarting advertising, stop advertising, list the bonds, call `esp_ble_remove_bond_device` for each one, print `erase_bonds_requested count=N`, and wait for the stack's completion callbacks (`gapCallback`).
3. When all completion callbacks have arrived, no bonds remain and there were no failures: leave the erase state, resume advertising and print `erase_bonds_complete remaining=0 remove_Windows_bond_then_pair_again`. When the board has no bonds, this path is taken too.
4. Failure paths: if listing the bonds fails, print `erase_bonds_failed return_code=… restart_required=1`. If a removal fails or bonds remain, print `erase_bonds_failed remaining=… failures=… restart_required=1`. In both cases the erase state is not cleared, authentication and advertising stay off, and the board must be restarted.
5. Serial input is handled line by line: `\r` is ignored; an empty line gets no response; a line longer than 31 characters, or any line other than `erase-bonds`, prints `serial_command_unknown supported=erase-bonds`.

## Why it is designed this way

1. **A fixed length (38 bytes in version 3), written byte by byte in little-endian order.** C++ and Python then get the same result from the same bytes, independent of struct alignment and host byte order. A fixed length plus a version number exposes a format mismatch; for the same reason the 38-byte real-data layout is a new version, 3. `serializePacket` takes an array of exactly 11 values, so a wrong channel count is a compile error rather than an out-of-bounds read (comment at `comms_packet.h:25-26`). Rejected: application-level fragmentation, CRC and compression, because BLE already provides link integrity. Source: `docs/archive/design/week7-selected-design-2026-09-06.md` item 3; `docs/archive/test-evidence/week7-packet-firmware-evidence.md`.
2. **If the MTU is too small, nothing is sent, and this is counted separately (`mtu_suppressed`).** The notification payload limit is MTU − 3, and a truncated packet is meaningless. Rejected: silent truncation, or fragmentation by the firmware itself. Source: selected design item 3.
3. **No offline backlog; no samples are generated while disconnected.** An old gesture sent late would be treated as a new live action. Rejected: buffering on the ESP and sending later. Source: selected design item 4; "Scope and acceptance" in `docs/archive/design/specs/2026-09-17-dual-esp-reception.md` ("No offline history or retransmission protocol").
4. **Allocate the sequence number first, then try to submit.** A sample whose submission fails still uses up a sequence number, so a loss cannot be hidden by reusing the number. Rejected: incrementing the sequence only after a successful submission. That was the old rule in selected design item 4, and the dual-board specification replaced it. Source: dual-board specification "Scope and acceptance". (A sample that the glove module cannot deliver, that it calls IDLE, or that scaling refuses is not a loss in transport and takes no number; see reasons 21 and 24.)
5. **A separate source statistics characteristic (36 bytes since 2026-10-15).** The laptop reads it once before subscribing and once after stopping, and reconciles over the range `[start.next_seq, end.next_seq)`, so the first and last samples can be checked too. A successful submission alone does not prove delivery. The `idle`, `unread` and `refused` totals and the gated flag let the laptop tell a still player from a lost link (reason 24). Source: dual-board specification "Scope and acceptance".
6. **SC, MITM and bonding; the passkey is shown only on the local serial port; the characteristics and CCCDs all require encryption with MITM; the application also gates on the authentication result.** These are two layers of protection. The attribute permissions block unencrypted access. The application gate blocks a "success" callback after a downgrade. Rejected: Just Works, automatic downgrade and automatic bond deletion. Source: selected design items 13 and 24.
7. **No `setStaticPIN()`.** This Arduino helper overwrites the authentication mode. The firmware calls `esp_ble_gap_set_security_param` for each parameter instead and checks every return value. Source: the comment at `main.cpp:245-246`; the firmware evidence document.
8. **No extra HMAC, HKDF or AES-GCM on top of BLE.** The authenticated BLE link plus the SSH and TLS legs after it already cover the whole path. Another key and nonce protocol that nobody has reviewed would only add burden. Rejected: the application-level encryption scheme in section 10.1 of the architecture draft. Source: selected design item 14; `docs/archive/design/architecture-and-interface-draft-v0.1.md` section 10.1.
9. **`esp_ble_gatts_send_indicate` sends to the current connection only.** `BLECharacteristic::notify()` broadcasts and returns no result, so it cannot support submission counts. `BLEServer::getGattsIf()` is private in Arduino 2.0.17, so the firmware takes the interface number from the `ESP_GATTS_REG_EVT` registration event. Source: the comments at `main.cpp:96-97` and `257-258`; the firmware evidence document.
10. **Write fields are read only for a real WRITE event with a matching handle.** The GATTS callback parameter is a union. The bytes of another event (for example EXEC_WRITE) must not be parsed as a write. The cost: prepared writes and execute writes are not supported. Source: selected design item 20.
11. **Policy logic lives in portable C++11 headers.** Serialization, security policy, event parsing, sample scaling, the per-tick sample policy, the send tick, the dummy IDLE/MOVING cycle and the control state machine can then be tested on the host without flashing a board. Source: dual-board specification "Interfaces and boundaries".
12. **Left and right identity is a compile-time constant, in two build environments.** The identity travels with the firmware and is not guessed at run time. Source: dual-board specification "Scope and acceptance".
13. **A board's physical identity is the Bluetooth address derived from the factory MAC, not the COM port number.** With one programming cable, two boards connected one after the other can get the same COM number. The firmware uses `static_assert(CONFIG_ESP32_UNIVERSAL_MAC_ADDRESSES == 4)` to guarantee that the "factory base plus 2" conversion holds. Source: the comments at `flash.py:69-71` and `107`; `main.cpp:610-612`. The same rule applies when one board is flashed by hand (decision D1 in hand-off document section 6.5).
14. **The control channel uses two separate protected characteristics and does not touch the sensor stream's sequence numbers.** Commands, rate changes and files are counted separately and do not affect throughput reconciliation. Files only go from the laptop into ESP memory; resuming after power loss is not supported. Source: "Contracts" in `docs/archive/design/plans/2026-09-28-co-features.md`; "Protected BLE controls" and "Files" in `docs/co-protocol-v3.md`.
15. **The callback only copies control frames into a 4-frame queue; the main loop handles one frame per pass.** The sensor send tick runs first, so bulk work cannot delay the timing. Source: the comment at `main.cpp:559-560`. The design records do not name a rejected alternative.
16. **The command cache holds 8 entries; `id` must increase within one connection; an old `id` pushed out of the cache is always rejected.** Resending the same command gets the same response, with no second transform. An old request cannot have a new effect. The firmware prevents repeats only within one connection; preventing repeated game effects across connections is the job of the command record on the Ultra96 (comment at `comms_control.h:53-54`). Source: "Contracts" in the CO features plan; `docs/co-protocol-v3.md`.
17. **The dummy data header is generated from editable JSON.** The laptop's simulated source and the firmware use the same data. Changing the data is a build step and does not change the wire format. Source: "Decisions" in the CO features plan.
18. **The unprotected build is a separate, explicitly named environment.** It is available when a comparison is needed, but the normal build is always protected. The diagnostic build states on serial that it cannot serve as protection evidence. Source: selected design item 13.
19. **`CORE_DEBUG_LEVEL=0`.** The Arduino BLE library prints the passkey at INFO level. With framework logs off, the only interactive output left is the firmware's own line. Source: `platformio.ini:9-11`; the firmware evidence document.
20. **Only version 3; the formula dummy went with versions 1 and 2; the statistics marker follows the version.** The owner's rule is that only the newest version is supported. The formula dummy (old version 1) could be told apart from table data only by its version byte, so it could not survive a single version; reproducible dummy data stays available with `-DCOMMS_FIXTURE_SEED`. The marker `LCS3` made the laptop refuse a board with version-2 firmware before it subscribes, with a clear message, instead of failing packet by packet; since 2026-10-15 the 36-byte length does this first, for the 24-byte `LCS3` build of 2026-10-14 too. Source: decisions D4 and D7 in hand-off document section 6.5.
21. **Scaling in a portable helper, with the out-of-range policy as a build flag; NaN and infinity always refused; no `seq` for a refused sample.** Either answer from Wen Ree (clamp or drop) becomes a build flag, not a code change. Rounding is done in `double`, where a `float` times an integer factor is exact, so the result does not depend on `float` rounding or the FPU rounding mode (comment at `comms_sample.h:48-49`). A refused sample takes no sequence number, so it never appears downstream as a false gap, only as a longer `uptime_ms` step. Since 2026-10-15 `prepareSample` calls `scaleSample` for every MOVING sample. Source: decision D13 in hand-off document section 6.5; the comment at `comms_sample.h:31-35`.
22. **The glove module sits behind four plain functions, with a built-in dummy of the same shape.** The main loop is the same for dummy and real data, so everything checked with the dummy (ticks, counters, `seq`, reconciliation) also covers the real path. The dummy hands over its rows as physical floats and goes through `prepareSample`, and a host test proves the bytes did not change. `COMMS_GLOVE_MODULE` selects the implementation at build time; nothing is guessed at run time. Source: the owner's request that the Communications firmware call Siqiang's functions (2026-10-15); `comms_glove.h:5-11`.
23. **The glove module is never called under the mutex, and a tick is committed only after a second check under it.** The BLE callbacks (connect, disconnect, MTU, authentication, CCCD, source statistics read, control and probe writes) all wait for `connectionStateMutex` with `portMAX_DELAY`. Siqiang gives up to about 10 to 20 ms for one call, which must not stall them. The second check means that once the laptop has turned notifications off, no counter and no `seq` can change, so the quiesced and final source statistics stay equal (the laptop refuses `source changed after notifications were quiesced`). The cost: a tick whose link changed during the read is lost and counted only on serial (`race_dropped`). Source: the comment at `main.cpp:399-403`.
24. **Gating at the source, by the glove owner's detector; an IDLE tick takes no `seq` but is counted.** Siqiang decided that the gloves send only while his detector says MOVING (2026-10-15), and the owner asked that the Communications firmware call that decision. Not sending IDLE samples saves radio time and keeps the 11-value packet. No `seq` for an IDLE tick means the pause never looks like a loss downstream. The `idle` count and the gated flag in the source statistics let the laptop expect silence while the player is still, and still judge whether the board kept ticking ([detail chapter 3](03-laptop-relay-and-tools.md)). Rejected: an IDLE/MOVING field in the packet, which would change the length, the MTU floor and `on_sample`. Source: Siqiang's answer of 2026-10-15 (hand-off document section 7.1).
25. **The send tick keeps its rate.** Restarting the interval from the pass that noticed the deadline lost about half a pass per tick on average; with a glove module that takes milliseconds per pass, the rate fell under 90 % of the setting from about 5 ms per pass (the comment in `host_sample.cpp`, `testSendTick`). `sendTickDue` advances the deadline by whole intervals, so 50 Hz stays 50 Hz while one pass is shorter than 20 ms, and a long stall drops ticks instead of sending a burst (reason 3: no backlog). Source: `comms_sample.h:67-72`.
26. **Every channel is set to NaN before `gloveRead()`.** A module that returns `true` but leaves a channel unwritten then has the sample refused (`refused`), instead of sending stack contents as data. Source: `main.cpp:406`.
27. **`uptime_ms` is taken after the read.** A module may take its measurement inside `gloveRead()`, and the call may take milliseconds; a time taken before the call could then be earlier than the measurement. Taken after `gloveRead()` and `gloveShouldSend()`, the time is never earlier than the sample. (Siqiang's `gloveRead()` copies the latest sample of `gloveUpdate()`, at most 100 ms old.) Source: `main.cpp:409`.
28. **Siqiang's module is built from copies under `firmware/esp32/lib/`, checked by a tool and a test.** `hardware/` is Siqiang's path, and Communications must not edit or move his files (`AGENTS.md`). A PlatformIO library under `lib/` builds them unchanged, and `lib_ignore` in `[env]` keeps them out of every environment except the two `-glove` ones. `tools/sync_glove_module.py --check`, `tests/test_glove_module_sync.py` and `flash.py --glove` refuse stale copies, so the gloves are never flashed with an old module. Source: `tools/sync_glove_module.py:1-17`; `firmware/esp32/lib/glove_sensor/README.md`.
29. **A failed `gloveBegin()` is tried again at boot, up to 3 times, 500 ms apart (decision D38, 2026-10-16).** In Siqiang's module one failed IMU read during the calibration, or a failed WHO_AM_I or register read, makes `gloveBegin()` return false (issue 3 under "Issues found in Siqiang's module"). With a single call, one transient I2C glitch at power-up left the glove sending nothing until the next power-up. How often Communications calls his function is a Communications integration measure; the root cause stays in his module. The cost: each try repeats his calibration (about 5 s, glove held still), so a glove whose calibration fails twice advertises up to about 10 to 11 s later than normal, and a board whose module fails at once (no sensor) pays about 1 s for the two pauses. It does not help issue 5 (a WHO_AM_I other than `0x70` fails every try). Calling his `gloveBegin()` again after `false` is safe: it resets its own state at the start (`glove_sensor.cpp:427-439`), and `Wire.begin()` on a bus that is already started returns true in the Arduino-ESP32 core 2.0.17 used here (see the contract table under "Glove module and movement gating"). The loop is the portable template `beginWithRetries`, so the host test checks the loop the board runs, and both numbers are build switches with `static_assert` bounds. Source: decision D38 in hand-off document section 6.5; `comms_glove.h:29-32`, `53-56`, `86-98`.

## Cautions and known limitations

- **What the default environments send is not sensor data.** With `firebeetle32`, `-left` and `-right` the 11 values come from `common/dummy_fixtures.json` (4 rows, already in wire units). The row is chosen at random, and the same row may repeat. Only the `-glove` environments send Siqiang's readings. A `-glove` build has run only on the right board without sensors (2026-10-16), where it sends nothing; no glove has been flashed.
- **Gating is verified on one board with the dummy only.** On 2026-10-16 the right board ran the gated dummy (3 s MOVING, 7 s IDLE) against a service on the laptop: the 36-byte source statistics, the gated flag, the `idle` count, and the new tick and loop all worked (the gated coverage rule, which only `demo.py run` applies (`laptop/dual_bridge.py`), has not run on hardware yet, because `tools.check_board` does not judge coverage) (see "Verifying gating on a board"). Not run yet: Siqiang's detector on a real glove, the gated firmware through the Ultra96 (the idle tests through the Ultra96 cover the service side; [detail chapter 4](04-ultra96-service-and-certificates.md)), and two boards together. Both boards now run the plain current build (the left board since 2026-10-17; status table below); the gated dummy has run on the right board only.
- **Editing the JSON does not change a board that is already flashed.** Regenerate the header, build and flash. `flash.py` rewrites the Git-tracked `comms_fixtures.h` every time.
- **A successful submission is not delivery.** `submitted` only means the stack accepted the submission. It is evidence level 1.
- **The two failure counters count different things.** The serial `submission_errors` counts failed submissions on every characteristic (counter, sensor, probe, control response). The source statistics `failures` counts sensor packets only. Use the source statistics for reconciliation.
- **The rate is not reset on disconnect.** `ControlEngine::disconnect()` does not change `rateHz_`. Only a restart or another rate-change command changes it.
- **The measured rates were taken with the old send tick.** Until 2026-10-15, when the send tick check passed, "last send" was set to the current time, and each pass also has `delay(1)`, so the period was rounded up to whole passes. A 70 Hz setting measured about 66 packets/s per board, which matched that code (this is an inference). A 50 Hz setting measured about 49.98 packets/s. The highest clean setting measured is 70 Hz (about 66 packets/s delivered), with the 32-byte version-2 dummy packet. With the 38-byte version-3 packet only one board at the 50 Hz setting has been measured: clean on 2026-10-14 with the old send tick, and clean on 2026-10-16 with `sendTickDue` (3022 ticks in 60.5 s of ticking, about 50 per second, with the dummy module's short passes); higher settings and two boards together have not. 75 Hz failed because the right board had 260 source submissions rejected by the stack, not because of downstream loss. 100 Hz also failed (`docs/archive/test-evidence/co-live-deployment-2026-09-28.md`). `sendTickDue` now keeps the set rate while a pass is shorter than the interval, so a setting above 50 Hz sends more than it did: a 70 Hz setting should now send about 70 packets/s, about what the failed 75 Hz setting sent before (about 71 packets/s; an inference from the code, not measured). Do not take the 70 Hz result as clean for the new firmware. At 50 Hz the change is small.
- **A glove whose calibration fails advertises later.** Since 2026-10-16 `setup()` repeats a failed `gloveBegin()` up to 3 times (decision D38), and each try of Siqiang's module calibrates again for about 5 s, glove held still. A glove whose calibration fails twice advertises up to about 10 to 11 s later than normal; if all three tries fail it prints `glove_begin ok=0 … attempts=3` and sends nothing, as before. Hold the glove still until `comms_ready` appears. A retry that succeeds on a real glove has not been seen on hardware; the host test covers that path.
- **Passes are longer with Siqiang's module.** His `gloveUpdate()` reads the IMU over I2C at most once per millisecond (400 kHz, 2 ms I2C timeout), runs the orientation filter, adds a sample to the movement detector every 20 ms and evaluates it every 200 ms. A pass is then longer than the about 1 ms of the dummy build (not measured). The send tick keeps 50 Hz while one pass stays below 20 ms; a pass longer than the interval drops ticks (at most one tick per pass).
- **The mutex is held in short sections now.** Since 2026-10-15 `connectionStateMutex` is never held during a glove module call (Workflow D). Control processing still runs under it, one frame per pass, including the SHA-256 of a received file at file end. Anything added under it in future must stay short, because the BLE callbacks wait for it.
- **A gated board is silent while the glove is still.** Nothing is sent and no `seq` is taken; only `idle` grows. The laptop reads the gated flag and judges the board by its ticks ([detail chapter 3](03-laptop-relay-and-tools.md)). The Ultra96 service lets an ingest connection wait up to `--ingest-idle-timeout` (default 600 s, 5 to 86400) for its next frame instead of the old 5 s. This is deployed on the Ultra96 since 2026-10-16 and verified there with synthetic samples, each test on one connection: after silences of 7, 30 and 120 s the next sample was accepted; in a second test the sample after 590 s was accepted, and after a further 620 s the board had closed the connection ([detail chapter 4](04-ultra96-service-and-certificates.md)). A gated board itself has not yet sent through the Ultra96. When all 8 client slots are taken, the ingest connection idle longest (at least 5 s) is closed to admit the new client (`idle_evicted`; `ultra96/server.py:46-47`, `236-250`); a live glove closed this way reconnects when it next sends and loses the frames then in flight ([detail chapter 4](04-ultra96-service-and-certificates.md)). The two gloves gate independently, so one can be silent while the other sends.
- **A received file stays in memory** until the next file begin, an abort or a disconnect. The firmware does not use the file content; it only checks the digest. After a digest mismatch (status 4), the incomplete file still holds the slot. Abort it, wait 30 seconds or disconnect before starting another file.
- **A changed GATT table needs re-pairing.** After the control characteristics were added on 28 September, a targeted bond recovery was done on the Windows side (deployment record). Neither version 3 nor gating changed the GATT table (gating changed only the length of the 0006 value), and reflashing the application does not erase the bonds: on 2026-10-14 Windows kept its authenticated bond with the right board through two reflashes, and on 2026-10-16 through four more (plain, gated dummy, `-glove`, plain).
- **Bond recovery is a manual procedure.** The firmware never deletes bonds automatically and never lowers the protection level.
- **The 0002 counter stream prints one serial line per notification.** Subscribe to it only for diagnosis.
- **The single-board diagnostic tools cannot choose a board.** `laptop.ble_counter_receiver` and `laptop.mtu_probe` scan by service UUID and connect to whichever board they find first. Both boards advertise the same name, so power only one board when using these tools. They also do not set a rate; the board keeps its last rate. `tools.check_board` is different: it connects by the board's address and sets the rate.
- **The platform version is not pinned.** `platformio.ini` says `platform = espressif32`. The verified combination is Espressif32 7.1.0 with Arduino-ESP32 2.0.17 (package version `3.20017.241212`), and this is also what is installed on this machine. In the local SDK, `ESP_GATT_MAX_MTU_SIZE` is 517, `ESP_GATT_DEF_BLE_MTU_SIZE` is 23 and `CONFIG_ESP32_UNIVERSAL_MAC_ADDRESSES` is 4.
- **`flash.py` works only on Windows.** A port name must be `COM` plus digits, and the interpreter path for `esptool` is `.platformio\penv\Scripts\python.exe`.
- **Reading the MAC resets the board.** `esptool read_mac` goes through the ROM. It does not flash and does not read the application's serial output.
- **The board connected first becomes LEFT (ID 1).** If the order is swapped on a reflash, the left and right identities swap, and the mapping is written in the new order. Label the two boards LEFT and RIGHT after flashing. When one board is flashed by hand, its factory MAC decides whether `-e firebeetle32-left` or `-e firebeetle32-right` is used, never the COM number.
- **Without a mapping file, the default addresses hard-coded in the code are used.** `DEFAULT_BOARDS` in `tools/demo_boards.py` holds the original operator's two boards. After changing boards, run `python flash.py` first.
- **The firmware does not report its own version or commit.** `comms_ready` carries only the device ID, packet length, packet version, rate, protection, control version, file limit and (since 2026-10-15) the glove module and the gated flag; a current board prints `packet_bytes=38 packet_version=3 … glove=dummy gated=0` (or `glove=external gated=1` for a `-glove` build). Without a serial port, tell a current board by its 36-byte source statistics. Older firmware, including the 24-byte `LCS3` build of 2026-10-14, makes the laptop report `source statistics must contain exactly 36 bytes; flash this board with the current firmware` (`laptop/source_audit.py:61-64`). The capture report's `workspace_source_sha256` covers the firmware sources (`firmware/esp32/platformio.ini`, `include/` and `src/`, and since `4c6ab4c` also `movement_model_params.h` and `lib/`, which hold the copies of Siqiang's module), but it describes the laptop's working copy and does not prove which version is flashed on the board (`laptop/reporting.py:13-38`).
- **The module files under `firmware/esp32/lib/glove_sensor/` and `firmware/esp32/movement_model_params.h` are copies.** Never edit them; a fix belongs in Siqiang's files under `hardware/`, made by Siqiang. After he pushes a change, merge the team main and run `python -m tools.sync_glove_module`; until then `tests/test_glove_module_sync.py` fails and `flash.py --glove` refuses to build.
- **`PLATFORMIO_BUILD_FLAGS` applies to every build in that terminal.** It is the way to add a switch such as `-DCOMMS_DUMMY_IDLE_MS=7000` or `-DCOMMS_GLOVE_SEND_ALL=1` without editing `platformio.ini` (see "Verifying gating on a board"). Remove it (`Remove-Item Env:PLATFORMIO_BUILD_FLAGS`) before any other build or `python flash.py`, or the next boards get the test switch too.
- **No Week 7 names remain in the firmware.** No TLS host name, no `Week7*` symbol and no dated folder appears in the firmware source. The control frame magic `B7` and the serial prefix `b07_` refer to the team number B07. The `W7` packet marker in `host_control.cpp:68` is a negative test that must be rejected.

**The two implementations.**

- **Built-in dummy (`COMMS_GLOVE_MODULE=0`, `src/dummy_glove.cpp`).** `gloveBegin()` returns true at once; `gloveUpdate()` does nothing; `gloveRead()` gives a random dummy row as physical floats; `gloveShouldSend()` returns `dummyMoving(millis(), COMMS_DUMMY_MOVING_MS, COMMS_DUMMY_IDLE_MS)` (`comms_dummy_gate.h:17-21`): always true by default, or a cycle from boot (MOVING, then IDLE) when `COMMS_DUMMY_IDLE_MS` is above 0. The cycle length is computed in 64 bits; when `millis()` wraps (every 49.7 days) the cycle starts again with MOVING.
- **Siqiang's module (`COMMS_GLOVE_MODULE=1`, the `-glove` environments).** His `glove_sensor.cpp` defines `gloveBegin`, `gloveUpdate` and `gloveRead` with the signatures of `comms_glove.h`, so `src/glove_module.cpp` defines only `gloveShouldSend()`: `gloveIsMoving()`, or always true with `COMMS_GLOVE_SEND_ALL=1` (`glove_module.cpp:10-18`). His detector keeps a window of 50 samples taken every 20 ms (1 s) and evaluates it every 200 ms with a logistic model; it reports MOVING after 2 consecutive windows above the threshold and IDLE after 3 below (`glove_sensor.cpp:44-50`, `360-422`). `gloveIsMoving()` is false until the first window has filled. His `gloveRead()` returns false, with `out` zeroed, when there is no valid sample younger than 100 ms (`glove_sensor.cpp:547-565`).
- **How his files reach the build.** They are copied unchanged, never referenced in `hardware/` (see the files table and design reason 28). `python -m tools.sync_glove_module` makes the copies; `--check`, `tests/test_glove_module_sync.py` and `flash.py --glove` refuse stale ones.

**What one send tick produces (`prepareSample`, `comms_sample.h:94-114`; `produceSample`, `main.cpp:399-431`).**

| Outcome | When | Counted in | `seq` | Sent |
|---|---|---|---|---|

| `SampleIdle` | Read succeeded, IDLE | `idle` | No | No |

A gated board (`kGloveGated`) says so in bit 0 of the source statistics flags and in `gated=1` on serial. The laptop then expects silence while the glove is IDLE and judges whether the board kept ticking from `next_seq` plus `idle` ([detail chapter 3](03-laptop-relay-and-tools.md)). Downstream, an IDLE period shows as a jump in `uptime_ms` with no `seq` gap, and the model receives only samples sent while MOVING. Samples taken before the detector says MOVING are not sent and cannot be sent later (see "Issues found in Siqiang's module", issue 4). On 2026-10-16 the gated dummy showed this on the right board: 900 of 3040 ticks sent, 2140 counted as idle, a longest receive silence of 7.03 s, and the check passed (see "Verifying gating on a board").

The technical constraints below come from the Communications firmware code itself. They apply to any module, and Siqiang's module meets them as far as the code shows (items 4 and 5 checked by reading; the timings not measured).

1. **Initialization must return.** `gloveBegin()` is the first call in `setup()`, and BLE starts only after its last try. If it does not return, `advertising->start()` and `bleReady = true` are never reached, the board never advertises and the main loop only idles (`main.cpp:441-450`, `493-494`, `503`). A long calibration delays advertising by its length: about 4 to 5 s with Siqiang's module (not measured), and since the retry of 2026-10-16 (decision D38) by up to three calibrations and two 500 ms pauses when tries fail. When his `gloveBegin()` fails before the calibration, it costs little: on the right board without sensors (2026-10-16), with one try (before the retry) `glove_begin ok=0` appeared 0.71 s into the serial log and `comms_ready` at 1.44 s; with the retry the third failed try ended at 1.71 s and `comms_ready` came at 2.44 s.
2. **No call may wait, apart from the calibration in `gloveBegin()`.** Since 2026-10-15 the glove module is never called under `connectionStateMutex`, so a slow call no longer stalls the BLE callbacks (design reason 23). It still delays everything else in that pass: serial input, the control queue (one frame per pass) and the MTU probe.
3. **Pass time and the rate.** The send tick is checked once per pass (`sendTickDue`), and each pass ends with `delay(1)`. The rate is kept as long as one pass is shorter than the interval (20 ms at 50 Hz); a longer pass sends at most one tick and drops the rest. Host-tested with simulated passes of 1 to 15 ms (±20 %) at 50 Hz: all 3000 ticks of 60 s kept (`host_sample.cpp`, `testSendTick`). On a board it was measured only with short passes (the dummy module, and the `-glove` build without sensors, whose `gloveUpdate()` returns at once): 50 ticks per second on 2026-10-16 (3022 in 60.5 s; 3040 in 60.8 s gated; 753 in 15.1 s). Not measured with Siqiang's module running on a glove.
4. **The serial port belongs to the Communications firmware.** The firmware calls `Serial.begin(115200)` itself, the main loop reads serial input to find `erase-bonds`, and the passkey is printed only on serial. So the module must not call `Serial.begin` again, must not read serial input, and must not print per sample. Siqiang's module has no `Serial` call.
5. **The radio belongs to the Communications firmware.** The firmware uses `BLEDevice` (BLE). For hardware access Siqiang's module uses only `Wire` (I2C) and the ADC (`analogRead`); it includes only `Arduino.h`, `Wire.h` and `math.h` besides its own headers, and defines no `setup()` or `loop()`, so it links into the Communications firmware. His earlier sketches (for example `hardware/gloves/29_sept/imu_v7.ino`) send over Bluetooth Classic `BluetoothSerial` and have their own `setup()` and `loop()`; they cannot be linked in.
6. **Identity and time are filled in by the Communications firmware.** Left and right identity comes from `COMMS_DEVICE_ID`, `seq` from `allocateSampleSequence` (only for a sample that is sent), and `uptime_ms` is `millis()` right after the read (`main.cpp:409`). The module does not provide these.
7. **Scaling is done in the Communications firmware, by `scaleSample` (`comms_sample.h:36-65`), called through `prepareSample` for every MOVING sample (built and host-tested under both policies).** It converts the 11 floats into `int16` with the factors in `kChannelScale` (the table under "Sensor packet"), rounding half away from zero in `double` (`comms_sample.h:48-51`). It refuses the whole sample and leaves the output untouched for a null pointer or for any NaN or infinity, under either policy; `prepareSample` counts that as `refused`. A value outside `int16` is clamped to the limit and counted per channel (`clamped`) by default; with `-DCOMMS_OUT_OF_RANGE_DROP=1` the whole sample is refused (`refused`) instead. Which policy V1 uses is still to be agreed with Wen Ree (see the version-3 section). An IDLE sample is never scaled, so its values are neither checked nor counted. On the Ultra96, Communications divides by the same factors to give the model physical floats (hand-off document section 7.2).
8. **A sample that is not delivered takes no sequence number.** At each send tick the order is: read one sample, ask whether to send, `prepareSample`, and only for `SampleSend`, after the second check under the mutex, `allocateSampleSequence`, `serializePacket` and submit. An unread, IDLE or refused sample sends nothing and takes no `seq`, so it never appears as a gap downstream, only as a longer `uptime_ms` step. A submission that fails after the number was allocated still uses up its number (design reason 4).

### Issues found in Siqiang's module (issues 1, 2 and 4 reported to the owner on 2026-10-15, issues 3 and 5 found on 2026-10-16, issue 6 seen on hardware on 2026-10-18; his files untouched)

Found by reading `hardware/gloves/integration_files/glove_sensor.cpp` (team commit `51593be`; unchanged at `79ac1f4`) and building it. The numbers are the same as in hand-off document section 7.1. 2. **Any failed IMU read, a non-finite sample, or more than 100 ms between two `gloveUpdate()` calls resets the whole movement detector.** `gloveUpdate()` then calls `resetMovementClassifier()` (`glove_sensor.cpp:486-497`, `533-537`). `gloveIsMoving()` then stays false until a new 1 s window has filled and a second evaluation 200 ms later agrees. By the code that is about 1.2 s or more (the figure reported to the owner was about 1.4 s), during which the glove sends nothing, even in the middle of a gesture; `gloveRead()` also returns false until a valid sample follows. In the Communications firmware `gloveUpdate()` runs every 1 to 2 ms, so in practice it is triggered by the first call after power-up, because BLE start-up runs between `gloveBegin()` and the first pass (harmless there, because the detector is still empty), by a transient I2C failure (his I2C timeout is 2 ms, `glove_sensor.cpp:42`, `445`) and, if it ever happens, by a non-finite sample from the orientation filter.
3. **One failed IMU read during the calibration makes `gloveBegin()` fail.** `calibrateGyroscope()` returns false as soon as any one of its 1000 reads fails (`glove_sensor.cpp:171`), and `gloveBegin()` then returns false (`glove_sensor.cpp:464-466`). Until 2026-10-16 the Communications firmware called `gloveBegin()` once at boot, so after one such glitch the glove started with `glove_begin ok=0`, counted every tick as `unread` and sent nothing until it was power-cycled. **Mitigated in Communications by the retry (decision D38); root cause still his (for his information).** `setup()` now calls `gloveBegin()` up to 3 times, 500 ms apart, so a glitch in one calibration costs one more calibration (about 5 s, glove held still) instead of the glove's data. Only a failed read in all three tries still ends in `glove_begin ok=0 module=external gated=1 attempts=3`. A real glove whose first try fails and a later try succeeds has not been seen on hardware; the host test covers that path.
4. **Samples before the MOVING decision are lost by design (for Wen Ree, hand-off document section 7.2).** MOVING needs 2 consecutive evaluations above the threshold, 200 ms apart, of a 1 s window that must first contain enough motion; IDLE needs 3 below (`glove_sensor.cpp:381-389`). So MOVING comes at best about 0.2 to 0.4 s after motion starts, later for gentle motion (about 0.4 s or more, as reported to the owner), and IDLE about 0.4 to 0.6 s after the window falls below the threshold. The exact lags need real data. Samples before the MOVING decision are not sent and cannot be sent later: the firmware keeps no backlog (design reason 3), and a catch-up burst would have to exceed the highest clean rate measured, about 66 packets/s per board. The two gloves gate independently, so the model may see one glove's samples without the other's.
5. **`gloveBegin()` accepts only one WHO_AM_I value.** It reads the IMU's WHO_AM_I register (`0x75`) and returns false unless the value is exactly `0x70` (`glove_sensor.cpp:24-25`, `447-449`). His tested sketch reads the same register but only prints a warning for another value and carries on (`hardware/gloves/model_threshold_variant_1/debug_esp32_ml_movement_detector_v1.ino:608-610`). So a glove whose IMU reports another value, for example a compatible MPU variant, works with his sketch but starts with `glove_begin ok=0` under the Communications firmware and sends nothing. The retry of decision D38 does not help: the value is the same at every try, so all three fail at once, in about 1 s with the two pauses, and the glove ends with `glove_begin ok=0 module=external gated=1 attempts=3`. The question for Siqiang: which WHO_AM_I value each glove prints (his sketch prints it at start-up).
6. **The gyro is read one value late, so gz is always 0 (found on the left glove on 2026-10-18; for the owner to report to Siqiang).** `hardware/gloves/integration_files/glove_sensor.cpp:153-154` skips the IMU's temperature with two `readInt16()` calls, 4 bytes, although the temperature is 2 bytes; his sketch skips it with two single `Wire.read()` calls (`hardware/gloves/model_threshold_variant_1/debug_esp32_ml_movement_detector_v1.ino:279-281`). So in the 14-byte burst from `ACCEL_XOUT_H` everything after it moves by one value: the module's gx holds the real gy, its gy holds the real gz, and its gz is read past the 14 bytes (`Wire.read()` then returns -1 for each byte, so the raw value is the constant -1), which the calibrated bias cancels to exactly 0. The Mahony fusion (yaw, pitch, roll) and his movement detector also get the shifted gyro. Seen on hardware: gz 0 in all 719 + 2024 samples of two runs with the module, including deliberate turns about the vertical axis, while his sketch, restored from the backup on the same glove, gave gz between about -250 and +250 deg/s (1347 distinct values in 1999 lines; evidence `.comms-local/checks/2026-10-18-left-glove/siqiang-sketch-serial.txt`). The fix is his: delete the second `(void)readInt16();` (line 154). Communications keeps the copies byte-identical (`tools/sync_glove_module.py`). **Fixed in the fork on 2026-10-18 at the owner's explicit request** ("发现了问题直接帮他改了把"; an exception to `AGENTS.md` rule 1 that the owner made for this one line): line 154 deleted in `hardware/gloves/integration_files/glove_sensor.cpp`, the copy synced with `python -m tools.sync_glove_module`, and the left glove reflashed. Verified on the left glove: gz between about -250 and +250 deg/s with 1497 distinct values in 1656 samples. Not in the team repo yet; Siqiang should be told, because his file in the fork now differs from his team copy (hand-off document section 6.2).

## How to run and verify

Run every command below from the repository root in Windows PowerShell.

**Flashing and pairing**

```powershell
python flash.py --ports            # list COM ports
python flash.py                    # generate the header, build, flash LEFT then RIGHT, save the mapping
python flash.py --glove            # the same for the real gloves: Siqiang's module, gated, 50 Hz

python flash.py --pair right
python -m tools.check_board left   # check each board alone after flashing
python -m tools.check_board right
```
