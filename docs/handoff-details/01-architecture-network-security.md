## Purpose and boundaries

The Communications subsystem does one thing: it sends each module's data out and makes sure the next module receives it accurately. Communications ends at the interface. It passes every result through unchanged: it never merges, splits, filters or reinterprets results. Who does what at each hand-over is the table in section 3.1 of the hand-off document.

Finished code is not finished integration. Every measured result so far used dummy data and dummy labels. Version 3 (38-byte packets) was measured only on the right board, against a service running on the laptop, with the firmware of 2026-10-14 (24-byte source statistics, no gating; section 6.1 of the hand-off document). The gated firmware and the `-glove` firmware have not run on any board. Nothing of version 3 has run on the Ultra96, on the phone, or with both gloves together. The Communications side of each teammate interface exists in code. Of the teammate sides, only Siqiang's glove module exists (team commit `51593be`, 2026-10-15); it is built into the `-glove` firmware environments and has not run on a board. Wen Ree's model module and Jie Ling's calling code do not exist yet (see "Current state of the three external interfaces" below).

This chapter describes branch `comms/protocol-v3`: protocol version 3 is the only version. The sensor packet marker is `LC` and its version byte is 3. The source statistics are 36 bytes with the marker `LCS3` (24 bytes until 2026-10-15). A glove sends a sample only while its glove module reports MOVING. The session ID defaults to `ltc-comms` everywhere. The local evidence and board-map folder is `.comms-local`. For what was removed and in which commit, see "History and removals" under "Caveats and known limitations".

**End-to-end topology (V1: one user, two gloves, one laptop, one Ultra96, one iPhone)**

```text
Left  FireBeetle ESP32 (device_id=1) ─┐ BLE GATT Notify, one 38-byte packet per sample sent
Right FireBeetle ESP32 (device_id=2) ─┴────────────► Windows laptop (BLE Central)
        (each glove sends only while its glove module reports MOVING; the two gloves gate independently)

Laptop ─TCP→ local 127.0.0.1:18889 ─SSH -L→ stujump:22 → Ultra96:22 → on-board 127.0.0.1:8888
        inside TLS: SENSOR_BATCH →    ← INGEST_ACK

Inside the board service: each new stream sample → model on_sample(...); the model's emit(...) → result queue

iPhone ─in-app SSH→ stujump:22 → Ultra96:22 → on-board 127.0.0.1:9999
        inside TLS: SUBSCRIBE →    ← SUBSCRIBED    ← GESTURE_RESULT

Inside the iPhone: Swift client ─C functions polled by the Unity main thread→ Unity
```

The VPN only provides network reachability. The code contains no VPN logic. With the VPN on, traffic still goes through `stujump`. The SSH jump host is how the Ultra96 is reached. Ports 8888 and 9999 are reachable only through SSH channels.

Operator access is not on the data path, and it also only dials out from the laptop. `python demo.py service` uses OpenSSH with the same two hops as the tunnel and an explicit `ProxyCommand` (`tools/demo_service.py:58-69`). `python -m tools.deploy_service` (added 2026-10-14) uses `paramiko`: it logs in to `stujump`, opens `direct-tcpip` to `Ultra96:22` and logs in there, then uses SFTP and one remote command (`tools/deploy_service.py:331-351,367-387`). Both check both host keys against the laptop's `known_hosts` and use passwords that the owner types.

The phone code has a `useJump` switch (`Configuration.swift:36`, `IntegrationController.swift:69-70`). When it is off, the app skips `stujump` and connects directly to `Ultra96:22`. This route was never verified on site. V1 does not use it, and it is not a fallback route. V1 uses only the jump host.

### Technical constraints on the teammate interfaces

The interface requirements for the three teammates (functions, fields, suggested function shapes, questions they must answer) live only in section 7 of the hand-off document. This chapter does not repeat them. Below are only the technical constraints that the code covered by this chapter imposes and that each teammate needs to know, and what now exists on the Communications side.

**Glove module (Siqiang).** Siqiang delivered the module on 2026-10-15 (team commit `51593be`, `hardware/gloves/integration_files/`); section 7.1 of the hand-off document records the interface. The firmware declares the four functions it calls in `comms_glove.h:39-55`: `bool gloveBegin()`, `void gloveUpdate()`, `bool gloveRead(float out[11])` and `bool gloveShouldSend()`. Siqiang's module defines the first three with exactly these signatures. `src/glove_module.cpp:10-18` defines `gloveShouldSend()` as his `gloveIsMoving()`, or as `true` with `-DCOMMS_GLOVE_SEND_ALL=1`. The firmware builds copies of his files, never the files in `hardware/` (see "Components and files"). At each send tick `produceSample` (`main.cpp:404-431`) calls `gloveRead`, then `gloveShouldSend` only after a successful read, then `prepareSample` (`comms_sample.h:94-114`), which scales the 11 floats with `scaleSample` (built, host-tested for both out-of-range policies). The constraints from networking, security and timing are:

- The module must not open any Bluetooth or Wi-Fi itself. The Communications firmware uses BLE, and it alone configures the whole BLE security policy (Secure Connections, MITM, bond, no notifications before authentication). The delivered module meets this: it uses only I2C at 400 kHz and two ADC pins (read in `glove_sensor.cpp`). His older reference firmware used `BluetoothSerial` (Bluetooth Classic). His 12th value (`SENS_GL_LEFT`/`SENS_GL_RIGHT`) and Bluetooth names (`SENSOR_GLOVE_LEFT`/`SENSOR_GLOVE_RIGHT`) were only for his PC (Siqiang, 2026-10-15); both boards advertise `LTC-COMMS`.
- The module must not read serial input, and must not print to serial for every sample. The Communications firmware accepts the `erase-bonds` command on the 115200 serial port (`main.cpp:378`), and the 6-digit passkey is printed only to this serial port (`main.cpp:177-181`). The delivered module does not use the serial port. The firmware itself prints `glove_begin ok=<0|1> module=<dummy|external> gated=<0|1>` once at start (`main.cpp:439-441`).
- The Communications firmware sets left or right at compile time (`COMMS_DEVICE_ID`, 1 left, 2 right, `main.cpp:26-28,35-36`). The module does not supply a left/right identifier; both gloves run the same module code.
- `gloveBegin` runs first in `setup()`, before BLE starts (`main.cpp:439`). It may block: Siqiang's calibration takes about 5.1 s, with the glove held still. The board advertises only after it returns. When it returns `false` (no sensor), the board still advertises, and every send tick counts as unread.
- `gloveUpdate` runs once per main-loop pass, outside the connection-state mutex, connected or not (`main.cpp:497`). `gloveRead` and `gloveShouldSend` run at a send tick, only while the laptop is connected and subscribed, also outside the mutex (`main.cpp:540-547`, `:404-412`). The BLE callbacks take that mutex; because the module runs outside it, a slow module call never delays them. Under the mutex the firmware then checks again that the laptop is still ready, and only then commits the tick (`main.cpp:414-430`). None of the functions may wait.
- The send rate holds while one main-loop pass (`gloveUpdate` plus about 1 ms) is shorter than the send interval (20 ms at 50 Hz). A slow pass delays one tick, not the rate; a longer pass skips ticks, and skipped ticks are never sent as a burst (`sendTickDue`, `comms_sample.h:67-78`). Siqiang says one call takes at most about 10 to 20 ms, usually far less. At 50 Hz a 20 ms call can therefore skip a tick.
- Only a sample that is sent takes a `seq` (`main.cpp:417-419`). A tick where `gloveRead` fails (unread), where the module reports IDLE (idle), or where `scaleSample` refuses the sample (refused: NaN or infinity always; a value outside int16 only with `-DCOMMS_OUT_OF_RANGE_DROP=1`) sends nothing and takes no `seq` (`comms_sample.h:80-114`). It shows only as a longer step in `uptime_ms`, not as a gap; an IDLE pause shows as a jump. `uptime_ms` is read after `gloveRead` (`main.cpp:409`). The idle, unread and refused totals travel in the 36-byte source statistics. Values clamped to int16 (the default policy) are counted only on the serial line (`comms_stats … clamped=`, `main.cpp:589-596`), together with `race_dropped`, the ticks whose link changed during the read.
- The movement decision comes late by design. `gloveIsMoving()` stays `false` until the module's classifier has filled its first 1 s window. The classifier evaluates a 50-sample window every 200 ms and reports MOVING after 2 windows above its threshold and IDLE after 3 below (`hardware/gloves/integration_files/glove_sensor.cpp:44-50`; the firmware copy has the same lines). So MOVING comes at least about 0.4 s after a motion starts, and IDLE about 0.6 s after it stops. Samples before the MOVING decision are not sent and cannot be sent later. This matters to Wen Ree's windows (see the model constraints below).
- For recording sessions, `-DCOMMS_GLOVE_SEND_ALL=1` sends IDLE samples too, and the source statistics then report an ungated source. Siqiang's Bluetooth Classic recording scripts cannot connect to the BLE firmware; he can flash his own sketch, or record through the chain (`python demo.py run`, then `python -m tools.export_capture`).

**Model entry and exit (Wen Ree).** Section 7.2 of the hand-off document gives the shape. The Communications side is built in `ultra96/model.py` and `ultra96/server.py`; Wen Ree's module does not exist yet, and the names are provisional until Wen Ree confirms. `start(emit)` is called once, before the listeners open (`ultra96/server.py:173-177`). The entry `on_sample(device_id, boot_id, seq, uptime_ms, values)` is called once for each newly accepted stream sample (only samples a glove sent while MOVING), with `values` as a tuple of 11 floats in physical units (int16 / scale; `common/sensor.py:92-98`, `ultra96/model.py:155`). The exit `emit(gesture, confidence, device_id, boot_id, seq)` is provided by Communications; the model calls it once per result, from any thread, with the identity of one sample the result used (usually the newest). The field name on the wire is `gesture`. The constraints from the code are:

- The board service is a single asyncio event loop. `on_sample` runs on that loop thread, before the sample's `INGEST_ACK` is written (`ultra96/server.py:327-339`). If it blocks, the ACKs for both gloves and the results for the phone are all delayed. The laptop waits at most 5 s after sending for each ACK (`laptop/bridge.py:608-616`), and sample freshness is 2 s. At 50 Hz, the 32-frame ACK window covers only 0.64 s of samples (`laptop/dual_bridge.py:450`). Calls longer than 5 ms are counted (`model_slow_calls`), and the slowest call is kept (`model_max_call_ms`; `ultra96/model.py:30,159-166`). Inference belongs on another thread or in another process.
- Exceptions from `on_sample`, including `SystemExit`, are counted (`model_errors`) and never close a connection; the ACK is still sent (`ultra96/model.py:150-158`). A `SystemExit` or other exception while importing the model or in `start(emit)` prints `{"event": "model_failed", …}` and the service exits nonzero without opening its ports (`ultra96/server.py:519-544`, `ultra96/model.py:133-137`). An `async def` `start` or `on_sample` is refused when the model loads (`ultra96/model.py:66-68`).
- The result queue is an `asyncio.Queue`, and subscriber state has no lock (`ultra96/server.py:61,134,341-346`). Only the service's event-loop thread may touch them. `emit` is the hand-over: it checks the arguments at once (label rule, confidence rule, `device_id` 1 or 2, `boot_id` and `seq` uint32; numpy-style numbers are converted; `ultra96/model.py:84-100`) and, from another thread, moves the result onto the loop with `loop.call_soon_threadsafe` (`:168-187`). It returns `True` when the arguments are valid and the service is running, `False` otherwise. `True` does not mean the result was sent.
- On the loop the service then refuses a result whose `(device_id, boot_id)` it has not accepted, or whose `seq` is above the highest accepted there (`model_results_rejected`), and a second result for one sample (`model_results_duplicate`, the last 4096 `result_id` values are kept; `ultra96/server.py:348-366`). A `seq` inside a gap (never accepted, but below the highest accepted `seq`) is not detected. Every refusal is counted and logs a warning at most once a second per kind (`ultra96/model.py:143-148`). After the service stops, `emit` returns `False` (`model_results_late`).
- Only one task may write frames on a connection (the convention in `common/wire.py:86-89`). Only the existing sender task (`ultra96/server.py:463-484`) writes results to the phone.
- The field set of `GESTURE_RESULT` is matched exactly in four places: the board, the iPhone and the two reference receivers. All four also require `device_id` to be 1 or 2, and `result_id` to equal the result's own `device_id:boot_id:seq` (prefixed `cmd:` for commands). So the correlation data can only be the identity of one sample. It cannot be an array or a nested object. Each result must point to a different sample.
- Commands never reach the model. The service answers each new command itself with one `cmd:` echo result with a dummy label (`ultra96/server.py:331-336`): command values are transformed dummy rows, and their sequence numbers come from the command space.
- The two gloves' samples arrive on two independent connections, with no pairing and no alignment. Communications does not retransmit. Missing samples are not filled in; they show as gaps in `seq`. Reconnects can leave such gaps. On a BLE disconnect the laptop discards that glove's queued samples (`laptop/bridge.py:114-121,920`; counted in `callback_generation_dropped`). On a TLS reconnect, samples already written but not acknowledged count as `ambiguous_dropped` and are not resent (`laptop/bridge.py:465-472,501`). While a glove is disconnected it makes no samples and `seq` does not advance (a sample is produced only while the laptop is connected and subscribed, `main.cpp:540-547`), so the disconnected time shows only as a jump in `uptime_ms`.
- A glove sends only while its module reports MOVING. While the player is still, that glove sends nothing, `seq` does not advance, and the pause shows only as a jump in `uptime_ms`. The two gloves gate independently, so one glove can be silent while the other sends, and samples from the two gloves need not cover the same time. The first part of each motion (at least about 0.4 s) is never sent. A gated glove that has sent nothing for a while is still connected: the board keeps its ingest connection open for up to 600 s by default. Building windows across these pauses, and deciding what a pause means, is Wen Ree's.
- The board does not resend results either. A result waits on the board for at most 2 s (queue plus write into the phone's connection). That limits waiting on the board only; it is not an end-to-end latency bound and not a promise that the phone receives the result (section 7.2 of the hand-off document).
- The model runs inside the service process: the ordinary user `xilinx`, `/usr/bin/python3` (3.10), no sudo. Everything the model imports must load under that interpreter and user. `--model-path DIR` is put first on the import path before the import (`ultra96/model.py:59-61`).

**Game-side calls (Jie Ling).** The signatures, semantics and C# declarations of the C functions are in sections 4.6 and 7.3 of the hand-off document. The constraints from the code are:

- The phone opens no listening port. Results come in only through the bridge functions: `CommsStart`, `CommsCopyDisplay` and `CommsStop` (in the source since 2026-10-08; the installed build has them only as `Week7Start`, `Week7CopyDisplay` and `Week7Stop`), and `CommsNextResult` (in the source; compiled and tested on Linux and macOS, and present in the unsigned iPhone build of 2026-10-16, which does not call it; not installed). Nothing may depend on port 5005 any more.
- The symbols come from the static library `CommsNative`, which must be linked into `UnityFramework`. Proposed (2026-10-14, final when Jie Ling confirms): Jie Ling makes that link on their own Mac, following the owner's short steps (add the local Swift package `ios-visualizer/CommsNative` and link it into `UnityFramework`), then builds and installs the app. Before the link, the Xcode build reports `Undefined symbol: _CommsStart` and similar; this is expected. Whether `configure_xcode.py` works on a new export is unverified (section 13 of the hand-off document). `CommsCopyDisplay` returns the UTF-8 byte count, excluding the terminating 0. The caller allocates the buffer; Week 7 uses 2048 bytes (`ios-visualizer/tools/patch_export.py:112-113`). The C# declarations in section 7.3 of the hand-off document are derived from the `@_cdecl` signatures and have not been compiled in Unity. The symbols exist only in the iOS build (`DllImport("__Internal")`). Calls in the Unity Editor or on other platforms throw, so calls go inside `#if UNITY_IOS && !UNITY_EDITOR`. Section 7.3 of the hand-off document settles this. It is not a question for Jie Ling.
- Call `CommsStop` only when the app no longer uses Communications. Do not call it on a scene change or when the app goes to the background. It sets the status to `Stopped` at once. Then it stops the client, clears the passwords, removes the foreground and background notification observers, closes the setup form and removes the button (`DisplayMailbox.swift:76-83`, `IntegrationController.swift:91-108`). After that, `CommsStart` must be called again, and the user must enter the passwords again. So the component that calls it must survive across scenes. The Week 7 export calls `Week7Stop` when its object is destroyed only because that object lives until the app ends.
- The app works only in the foreground. Locking the screen or switching to the background disconnects at once and clears the passwords (`IntegrationController.swift:27-29`).
- The top-right corner of the screen must stay free for the native `Communications Connect` button (`IntegrationController.swift:42-58`). It is the only way to connect.
- The display text keeps only the latest result. In the source, line 3 shows the received confidence (`DisplayMailbox.swift:14-18`, `GestureResult.confidence` in `Protocol.swift:11`); the installed Week 7 build still shows a hard-coded `confidence 1.0`. If several results arrive between two polls, the game sees only the last one; `Received` still counts all of them. So the text is a status display, not a game input. Line 2 of the text is the status; `Subscribed` means only that the subscription handshake with the Ultra96 succeeded, and does not prove that results are flowing.
- `int32_t CommsNextResult(char* buffer, int32_t capacity)` (`DisplayMailbox.swift:27-47,70-74`; compiled and tested on Linux and macOS, built for iOS on 2026-10-16, not installed; limits provisional) takes out the oldest waiting result as one compact JSON object, `{"result_id":"…","gesture":"…","confidence":…,"device_id":…}` (`Protocol.swift:22-24`), with a terminating 0. It returns the bytes written, 0 when nothing is waiting, or minus (bytes + 1) when the buffer is null or smaller than the bytes plus the 0; then it writes nothing and keeps the result (`DisplayState.swift:154-164`). The game calls it in a loop each frame while it returns a positive number, with a 512-byte buffer. What it promises: results wait in arrival order, deduplicated by `result_id`, and each result that is not dropped can be taken out at most once. It does not promise that every result is delivered: results lost before the phone never arrive, and the queue drops results and counts each drop. At most 32 results wait; when full, the oldest is dropped (`pendingDropped`); a result still waiting 2 s after it reached the phone is dropped (`pendingExpired`; `DisplayState.swift:28-29,105-110,168-173`). Expiry also runs when only `CommsCopyDisplay` is polled (`DisplayState.swift:137-148`). The queue and both counters are cleared when a new Connect starts (`DisplayState.swift:51-69`); the queue is emptied without counting when the session stops (Disconnect, the app becoming inactive, `CommsStop`; `:71-82`); an automatic reconnect keeps it (`:115-135`). The confidence is written as Swift prints a `Double`, unrounded (a numpy float32 0.93 arrives as `0.9300000071525574`; decision D17 in section 6.5 of the hand-off document). Until a game build that calls it is installed (the rebuilt Week 7 export of 2026-10-16 contains it but does not call it, and is not installed), the game can show the text but cannot drive actions reliably from it.

**Message overview** (frame: a 4-byte big-endian length plus a UTF-8 JSON object; body 1 to 16384 bytes; the field set must match exactly; there are no error messages; on any error the connection is closed)

| `type` | `v` | On-board port | Direction | Fields besides `v`, `type`, `session_id` |
|---|---|---|---|---|
| `SENSOR_BATCH` | 3 | 8888 | Laptop to board | `device_id`, `boot_id`, `seq`, `uptime_ms`, `values` (exactly 11 int16), `request_id` |
| `INGEST_ACK` | 3 | 8888 | Board to laptop | `device_id`, `boot_id`, `seq`, `status` (`accepted` or `duplicate`), `request_id` |
| `SUBSCRIBE` | 1 | 9999 | Phone to board | None |
| `SUBSCRIBED` | 1 | 9999 | Board to phone | None |
| `GESTURE_RESULT` | 3 | 9999 | Board to phone | `device_id`, `boot_id`, `seq`, `request_id`, `result_id`, `gesture`, `confidence` (10 keys in all) |

Rules for a result, the same on every peer (`ultra96/protocol.py:31-40,93-99`, `Protocol.swift:49-87`, `phone/receiver.py:118-148`, `phone/unity/CommsPhoneCore.cs:37,47-73`):

- `gesture`: a string of 1 to 32 characters, each from `A–Z a–z 0–9 _ -`. The six model classes (`PICKUPHOLD`, `PLACEDOWN`, `CHOP`, `WASH`, `THROW`, `FIREEXT`) fit. Communications does not know the label set; Wen Ree and Jie Ling agree it.
- `confidence`: a JSON number (not a boolean), finite, from 0 to 1; integers 0 and 1 are allowed.
- `device_id` 1 or 2; `boot_id` and `seq` uint32; `request_id` `null` or equal to `seq`; `result_id` equal to the result's own identity.
- The board checks a model result with the same rules before it is queued (`ultra96/model.py:84-100`, `ultra96/server.py:369`). A result the phone rejects is a terminal error on the phone: the session ends and the passwords are cleared (`CommsClient.swift:186-206`). So the board refuses an invalid model result rather than send it.
- In an adversarial review on 2026-10-14, 11,421 result bodies were validated identically by the board's rules, the Python receiver and a compiled C# harness of the changed C# part (section 6.2 of the hand-off document). The Swift rules were then checked only through a Python mirror of its JSON parser running the Swift test vectors. On 2026-10-15 the Swift package itself was compiled on Linux in a Swift 6.1 container, and its tests, `ProtocolTests` among them, passed; on 2026-10-16 they passed on macOS too.

**BLE sensor packet, 38 bytes** (Python format `<2sBBIII11h`; needs an ATT MTU of at least 41)

| Offset | Length | Field | Type | Value |
|---|---|---|---|---|
| 0 | 2 | Marker | ASCII | `LC` (`4C 43`). Only this one is accepted |
| 2 | 1 | Version | uint8 | 3. Only this one is accepted |
| 3 | 1 | `device_id` | uint8 | 1 or 2 |
| 4 | 4 | `boot_id` | uint32 little-endian | 0 to 4294967295 |
| 8 | 4 | `seq` | uint32 little-endian | 0 to 4294967295 |
| 12 | 4 | `uptime_ms` | uint32 little-endian | 0 to 4294967295 |
| 16 | 22 | `values[0..10]` | 11 int16 little-endian | −32768 to 32767 |

Channel order, units and scales (physical value = int16 / scale; `common/sensor.py:15-18`, `comms_sample.h:22-24`; the order and units come from `imu_v7.ino` and match the delivered module's `hardware/gloves/integration_files/glove_sensor.h:13-17`; the representable ranges are int16 arithmetic):

| Index | Field | Unit from the sensor module | Transmission scale | int16 representable range | Resolution |
|---|---|---|---|---|---|
| 0–2 | `ax`, `ay`, `az` | g, gravity removed | ×10000 | ±3.2767 g | 0.0001 g |
| 3–5 | `gx`, `gy`, `gz` | °/s, bias removed | ×100 | ±327.67 °/s | 0.01 °/s |
| 6–8 | `yaw`, `pitch`, `roll` | ° | ×100 | ±327.67° | 0.01° |
| 9–10 | `flex1`, `flex2` | normalised 0.0–1.0 | ×10000 | up to 3.2767 | 0.0001 |

- 38 = the 16-byte header + 11 × 2 bytes. The IDLE/MOVING question is answered (Siqiang, 2026-10-15): the state does not travel in the packet; the glove sends only while MOVING. So no field is added, and the 11-value layout stays. It is still provisional only until Wen Ree agrees to it. **The scales are provisional** until they are checked against real samples from the gloves. Section 12.6 of the hand-off document lists the files that change together if the layout ever changes.
- A 38-byte notification needs an ATT MTU of at least 41 (`comms_security.h:21-22`, `common/sensor.py:22`, `laptop/bridge.py:722-723`). The negotiated MTU measured on the boards is 517.
- Two gloves at 50 Hz would carry 38 × 50 × 2 = 30.4 kbps at the application layer. Verified on 2026-10-14 for one board only: the right board at 50 Hz for 65 s with 38-byte packets, against a service on the laptop, was clean (2934 generated = received = acknowledged; section 6.1 of the hand-off document). Two boards together, and real sensor data, have not been measured. With gating the average rate is lower, because a still glove sends nothing; the peak rate while both gloves move is unchanged.
- On the Ultra96, Communications decodes the int16 values and divides each by its scale before calling `on_sample` (`common/sensor.py:92-98`, `ultra96/model.py:155`). Restoring cannot recover precision dropped when packing. Any normalisation is Wen Ree's.
- In the firmware, `scaleSample` (`comms_sample.h:36-65`; built, host-tested; called through `prepareSample` since 2026-10-15) multiplies in `double` and rounds half away from zero. An IDLE sample is never scaled, so its values are neither checked nor counted.
- Out-of-range values: to be agreed with Wen Ree (section 8, step 1 and section 13 of the hand-off document). The firmware supports both answers as a build flag: clamp to the int16 limit and count it (the default, `COMMS_OUT_OF_RANGE_DROP` 0), or refuse that one sample (`-DCOMMS_OUT_OF_RANGE_DROP=1`). Either way it never drops a connection or a whole gesture. In normal use every value is expected to fit, but that is not guaranteed: the final value depends on the module's processing (for example the gyro calibration bias is subtracted), not only on the raw sensor range. The delivered module sets the sensor to ±2 g and ±250 °/s (`hardware/gloves/integration_files/glove_sensor.cpp:27-28`), so after gravity and bias removal every channel should stay inside the int16 range; this is read from the code, not measured. Clamped values are counted on the serial line (`clamped=`), refused samples in the source statistics (`refused`). A clamped value cannot be told apart from a real value at the limit (3.2767 g can be either); if the model needs to know which samples were clamped, a per-sample flag is needed, which changes the packet and `on_sample`. Neither option guarantees that a gesture is still recognised.
- Golden vectors: `tests/fixtures/comms-golden.json` holds two hand-specified 38-byte packets (a dummy-table row and a boundary packet with int16 and uint32 extremes); `comms-dummy.bin` and `comms-boundaries.bin` are their raw bytes, and `firmware/esp32/test/host_packet.cpp` prints the same hex.

**Source statistics, 36 bytes** (`<4sBB2xIIIIIII>`; `comms_source_stats.h:11-65`, `laptop/source_audit.py:14-20,55-78`; 24 bytes until 2026-10-15). All counters are uint32 totals since boot; the laptop reports differences between two reads of the same boot.

| Offset | Length | Field | Meaning |
|---|---|---|---|
| 0 | 4 | Marker | `LCS3` |
| 4 | 1 | `device_id` | 1 or 2 |
| 5 | 1 | Flags | Bit 0: a gated source, which skips send ticks while the glove is IDLE. Other bits must be 0. |
| 6 | 2 | Reserved | Must be 0 |
| 8 | 4 | `boot_id` | As in the packets |
| 12 | 4 | `next_seq` | The next `seq` to assign; the difference is `generated` |
| 16 | 4 | `submitted` | Notifications ESP-IDF accepted |
| 20 | 4 | `failures` | Submissions that failed (their `seq` is not reused) |
| 24 | 4 | `idle` | Send ticks the glove module called IDLE (`source_idle`) |
| 28 | 4 | `unread` | Send ticks where `gloveRead` returned `false` (`source_unread`) |
| 32 | 4 | `refused` | Send ticks whose sample `scaleSample` refused (`source_refused`) |

The laptop reads them once before subscribing and once after stopping, for the reconciliation "generated on the board = received by the laptop = acknowledged by the Ultra96". `source_ticks` = generated + idle + unread + refused counts every send tick while the laptop listened. Idle ticks never affect `clean`. The firmware counts a tick only if the laptop is still subscribed when it commits it, so the statistics stop changing once notifications are off. The bridge checks that.

**BLE control frame** (14-byte header, marker `B7`, control version 1): opcode, `device_id`, status, `id`, `offset`, then at most 180 bytes of payload; a frame is at most 194 bytes (`comms_control.h:11-13`, `common/control.py:14-15`). The control channel needs an ATT MTU of at least 64 (`comms_control.h:31`). A command carries one whole version-3 packet (`LC`, version 3, this board's `device_id` and `boot_id`, `seq` equal to the command `id`; `comms_control.h:129-133`), so a command frame and its answer are 52 bytes. The answer adds 1 to each of the 11 values (32767 wraps to −32768) and puts the board's own clock in `uptime_ms` (`comms_control.h:143-159`).

TLS authenticates only the server. The board does not verify client certificates. Anyone who can log in to the Ultra96 is inside the trust boundary. `session_id` is not an access credential.

The model is inside the same boundary. `--model MODULE` imports that module into the service process, with the service's user and rights and no sandbox; `--model-path` puts its folder first on the import path (`ultra96/model.py:53-69`). The report's `received` and `callback_received` differ when the queue drops packets.

Level 4 events are written first to `events.partial.jsonl`. Only when the service shuts down cleanly is the file renamed to `events.jsonl`, and `status.json` written (`ultra96/diagnostics.py:63-66,325`). ## Workflow

**Normal path**

Preconditions: the VPN is connected; the board service is already running; the board service, the firmware on both boards and the phone app are all built from the current source (for the current deployment state, see section 6.3 of the hand-off document). As of 2026-10-15 this holds for no end: no board has the current firmware (36-byte statistics, gating), and the Ultra96 and the phone still run version 2.

1. The board service runs. `tools.deploy_service` starts it in the background in its own session, and `demo.py service --start` starts it in the foreground of an SSH session. Either way the command is `/usr/bin/python3 -u -m ultra96.server --cert <BOARD_ROOT>/tls/server-cert.pem --key <BOARD_ROOT>/tls/server-key.pem --session-id ltc-comms`, with the ports 8888 and 9999, an optional `--event-log-dir <new folder>` and an optional `--model MODULE --model-path DIR` (`tools/deploy_service.py:166-173`, `tools/demo_service.py:98`). The service loads the model and calls its `start(emit)` once, then opens two listeners on `127.0.0.1` (`ultra96/server.py:173-194`). It prints `{"event": "model_ready", "model": "dummy", "seconds": …}` (or the module name), then `{"event": "listening", "host": "127.0.0.1", "tls": true, "ingest_port": 8888, "gateway_port": 9999}` (`ultra96/server.py:550-560`). Neither start command passes `--ingest-idle-timeout`, so the 600 s default applies.
2. The phone subscribes. The user taps `Communications Connect`. The app connects to `stujump:22`, compares the host public key and logs in with a password. It opens `direct-tcpip` to `Ultra96:22`, compares that public key and logs in. It then opens `direct-tcpip` to `127.0.0.1:9999`. It runs the TLS handshake with server name `ultra96.week7.internal`. After the handshake it sends `SUBSCRIBE` (`v` 1). The whole process is limited to 10 s. After `SUBSCRIBE` is sent, the phone starts a separate 5 s timer for `SUBSCRIBED` (`Subscriber.swift:32,60-66`). If `SUBSCRIBED` has not arrived in full within 5 s, the phone records `frame deadline exceeded` and retries after back-off. This 5 s timer and the 10 s connection deadline run at the same time.
3. The board reads `SUBSCRIBE` within 5 s, checks `session_id`, adds 1 to the subscriber number, closes the old subscriber and replies `SUBSCRIBED` (`ultra96/server.py:406-428`). The phone status becomes `Subscribed` (`CommsClient.swift:146`). This means only that the subscription handshake with the Ultra96 succeeded. It does not prove that results are flowing.
4. The laptop opens the tunnel: `python demo.py tunnel`. Local `127.0.0.1:18889` forwards to on-board `127.0.0.1:8888`.
5. The laptop starts the capture: `python demo.py run`. For each glove: scan (limit 8 s), connect (limit 20 s), confirm an MTU of at least 41, confirm the Windows bond is "encrypted and authenticated", read the starting source statistics (exactly 36 bytes, marker `LCS3`, with the gated flag), subscribe to sensor notifications. Both gloves must be ready within 30 s (`laptop/dual_bridge.py:454`).
6. Before this, at power-up, each board called `gloveBegin` before starting BLE (about 5.1 s of calibration with Siqiang's module, glove held still), and it calls `gloveUpdate` on every main-loop pass. Every `1000000 / rate_hz` microseconds a send tick falls due (`main.cpp:524-528`), and the ESP32 checks under the connection-state mutex: connected, subscribed, authenticated, MTU at least 41 (`main.cpp:540-543`). If all pass, outside the mutex it calls `gloveRead`, then `gloveShouldSend`, then `prepareSample` (`main.cpp:404-412`). Back under the mutex it checks again that the laptop is still ready, then counts the tick (`main.cpp:414-416`). Only for a sample to send does it assign `seq`, pack 38 bytes, submit the notification and record `submitted` or `failures` (`main.cpp:417-425`). An unread, IDLE or refused tick sends nothing and only increases its counter. A notification needs no confirmation from the peer.
7. The laptop's BLE callback records the arrival time on the monotonic clock and copies the bytes into that device's bounded queue. It also decodes the packet once for the goodput statistics, hands a `sensor` or `sensor_invalid` record to the evidence thread, and updates the callback and silence counters. It does no network operations.
8. The writer task takes one packet: decodes it (marker `LC`, version 3, exactly 38 bytes), checks `device_id`, checks for gaps, duplicates and reordering, checks the connection generation, checks freshness.
9. On the first send it opens a TLS connection to `127.0.0.1:18889`, with a 5 s handshake limit (`laptop/bridge.py:355-359`). It checks the generation and freshness once more. It writes `SENSOR_BATCH`; the write timeout is the smaller of 5 s and the remaining freshness.
10. The board reads the frame, validates the fields (version 3, 11 values, the `request_id` rule) and `session_id`, and deduplicates. Between frames it waits up to the ingest idle limit (600 s by default) for the next one to begin (`ultra96/server.py:311-315`), so a glove that is silent while the player is still keeps its connection. A new stream sample goes to the model: `on_sample` runs on the event loop with 11 physical floats (`ultra96/server.py:327-330`). The built-in dummy model calls `emit` at once on the same thread, so its result is checked and queued before the ACK; a real model may call `emit` later, from any thread, and its result then goes through the identity and duplicate checks on the loop (`ultra96/server.py:348-372`). A new command does not reach the model; the service queues one `cmd:` echo result itself (`:331-336`). Either way the board then replies `INGEST_ACK` with `status` `accepted` (`:337-339`). A duplicate input gets only `duplicate`; it reaches neither the model nor the phone. With no subscriber, a result is dropped at once.
11. The laptop checks the ACKs in send order: `v`, `type`, `session_id`, `device_id`, `boot_id`, `seq` and `request_id` (`laptop/bridge.py:381-391`). The ACK deadline for each frame is 5 s after it was sent. If the check passes, `acked` increases by 1.
12. The board sender task takes a result. Results that are already 2 s old are dropped. The rest are written to the subscriber within their remaining freshness. This 2 s limit covers only waiting on the board. Bytes already handed to TCP/TLS cannot be recalled, and the board does not learn whether the phone received them.
13. The phone assembles the bytes into complete frames and validates version 3, the 10 keys, `session_id`, `result_id`, the label rule and the confidence rule (`Protocol.swift:49-74`; the installed Week 7 build checks the version-2 rules instead). The display state then checks the session generation and deduplicates. If all pass, `Received` increases by 1 and the result is saved as the latest result; in the source it also joins the queue behind `CommsNextResult` (compiled and tested on Linux and macOS, built for iOS on 2026-10-16, not installed). The phone's own 2 s display window starts when it receives the result.
14. The Unity main thread polls the display text every frame. In the Week 7 export the call is `Week7CopyDisplay(buffer, 2048)`; new game code calls `CommsCopyDisplay`; both are the same implementation. The text is copied only when it has changed. The Week 7 export writes it into the existing text label. The text holds only the latest result, so results that arrive between two polls can be overwritten. It is a status display, not a game input. `CommsNextResult` hands out results one at a time, each result that is not dropped at most once (section 7.3 of the hand-off document); it is in the source, compiled and tested on Linux and macOS, built into an unsigned iPhone app of the Week 7 export on 2026-10-16 that does not call it, not installed.
15. Normal end: the laptop stops notifications, reads the final source statistics, drains the queue and the outstanding ACKs, closes TLS, and writes `report.json`. The report says per board whether it was gated and how many ticks it skipped. For a gated board, coverage counts generated plus idle ticks against the time its notifications were on, and long silences are not judged once it reported idle ticks (`laptop/dual_bridge.py:391-416`; see "Gated coverage" under "How to run and verify"). The board service, when it stops, prints its counters, including the model counters and `idle_evicted`, in the `stopped` line.

In step 10 the result is queued first and the ACK is sent after it (for the dummy model). The two travel on different connections. Their arrival order is not guaranteed.

The text in step 14 has four lines (`DisplayMailbox.swift:14-18`, the source since 2026-10-14):

```text
Communications
<status>
<gesture>  |  <result_id>  |  confidence <the received confidence>      (reads No live result when there is no current result)
Received: <N>
```

The installed Week 7 build was made from the earlier `Week7Native` source, which shows `Week 7 • DUMMY inference` on line 1 and a hard-coded `confidence 1.0` on line 3 (the screen itself was not checked; chapter 5).

| The phone finds a host public key mismatch, a rejected password, a CA/certificate/host name/validity check failure, or a protocol error (including a result that fails validation, such as a version-3 result reaching the installed Week 7 build) | Terminal: no automatic retry; the passwords are cleared (`CommsClient.swift:186-206`) | Status `Disconnected: <reason>; correct setup and reconnect`. For TLS and protocol failures the reason text is `SSH, TLS or protocol verification failed` |
| The phone connection closes, the 10 s deadline passes, a partial frame, or `SUBSCRIBED` takes more than 5 s | Reconnects after back-off and subscribes again. Each reconnection logs in to both SSH hops with the passwords again, with no limit on the number of attempts. | Status `Disconnected: <reason>; retrying`, where the reason is `connection closed`, `connection deadline exceeded` or `frame deadline exceeded` |
| The phone locks or the app goes to the background | Disconnects at once and clears the passwords. In the source, the `CommsNextResult` queue is emptied. After returning to the foreground, the user must tap Connect again. | Status `Paused — return and connect again` |
| A ninth connection reaches the board | Closed at once, unless an ingest connection can be closed instead (see "All 8 board connection slots" above) | `client_limit` |
| A board listener task dies | The process exits with a non-zero code | Log `listener task failed` (`ultra96/server.py:263`) |
| `tools.deploy_service` fails after it stopped the old service | It stops the new service, restores the previous certificate pair, and restarts the previous code from its rollback copy (`tools/deploy_service.py:259-284`) | The final record with status `rolled_back` or `rollback_failed_nothing_running`, in `BOARD_ROOT/evidence/active-deployment.json` and printed. Two other final statuses are saved and printed the same way: `failed_old_still_running` means the running process changed just before the stop (`tools/deploy_service.py:246-247`); `failed_nothing_running` means a first start, with no old service running, failed. A refusal in the checks before the stop (`tools/deploy_service.py:135-164`, before the `try` at `:244`) leaves the running service and the certificate untouched, prints the error and writes no record, neither on the board nor under `.comms-local/deployments/` |

## Why it is designed this way

The design records cited in this section are all under `docs/archive/`, which exists only on the fork. The text uses short names. "Selected design" is `docs/archive/design/week7-selected-design-2026-09-06.md` (cited by item number). "Architecture draft" is `docs/archive/design/architecture-and-interface-draft-v0.1.md` (cited by section number). "Dual-ESP spec" is `docs/archive/design/specs/2026-09-17-dual-esp-reception.md`. "iOS design spec" is `docs/archive/design/specs/2026-09-14-ios-visualizer-design.md`. The decisions of the evening of 2026-10-14 (D1 to D19) are recorded with their reasons and status in section 6.5 of the hand-off document. Rejected approaches are listed only as history. They are not fallback options.

1. **Every client dials out; services bind only to loopback; access goes through SSH channels.** Reason: behind the NUS firewall, outsiders can reach the Ultra96 only through the VPN and `stujump`, by SSH on port 22. The laptop and the phone are not on the allowlist, so nobody can connect in to them. Rejected: the phone as a server waiting for connections (the teammate's original port 5005 approach); the laptop connecting directly to the phone; opening Ultra96 application ports to the outside; SSH reverse forwarding `-R`; the laptop relaying results. Records: Architecture draft sections 3 and 6; Selected design item 12.
2. **The phone connects to the board itself, not through the laptop.** Reason: the phone owns its whole route, so results do not depend on the laptop being online. The laptop is only the input relay. Records: Architecture draft sections 3 and 5; the Selected approach section of the iOS design spec.
3. **TLS inside SSH, with a fixed host name.** Reason: SSH makes the board reachable. TLS, with a dedicated CA and a fixed name, confirms that the client reached the right service, and the check is not relaxed even for `127.0.0.1`. Rejected: plaintext inside the tunnel; skipping the host-name check; mutual certificates (SSH already authenticates access). Records: Selected design item 11; Architecture draft sections 10.2 and 10.3.
4. **Input and results use two ports and two connections. ACKs go only to the laptop; results go only to the subscriber.** Reason: the phone fetches its own results; the laptop is not a result relay. Rejected: the laptop relaying `GESTURE_RESULT`. Records: Selected design items 7 and 9; Architecture draft section 3.
5. **No retransmission and no replay; bounded queues; 2 s freshness.** Reason: a stale gesture that is resent would be treated as a new game action. Bounded queues stop a disconnection from piling up data without limit. Rejected: offline buffering on the ESP32; automatic resend after a failure; replaying history to a late subscriber. Each 2 s limit bounds waiting in one segment only (the laptop queue, the board queue plus the write into the phone's connection, the phone's display window counted from receipt, and the `CommsNextResult` queue counted from receipt). None of them is an end-to-end latency bound, and the board's limit is not a promise that the phone receives a result. Records: Selected design items 4, 9 and 10; Architecture draft section 11; Dual-ESP spec.
6. **One independent channel per board.** Reason: if one board loses power or hangs, the other continues. In the power-loss test on 2026-09-28, while the right board was powered off and recovering, all 111 packets from the left board were ACKed. Records: Dual-ESP spec; the Physical power loss section of `docs/archive/test-evidence/co-live-deployment-2026-09-28.md`.
7. **One subscriber; a newcomer replaces the old one.** Reason: V1 has one phone, and the result stream always has exactly one owner. V1 does not support multiple phones or per-user routing; the Architecture draft lists that as a later extension goal. Records: Selected design item 9; Architecture draft section 13.
8. **4-byte big-endian length prefix plus strict JSON; close the connection on any error, with no resynchronisation.** Reason: TCP has no message boundaries. After a bad frame, the next frame cannot be found reliably. Rejected: newline delimiting; WS/WSS; guessing the alignment after an error. Records: Selected design items 5 and 15.
9. **BLE uses Secure Connections + passkey + bond, with no extra application-layer encryption.** Reason: an authenticated BLE link plus SSH/TLS already covers the whole path. Adding HMAC/HKDF/AES-GCM would bring in a key and nonce protocol that nobody has reviewed. Rejected: application-layer HMAC/AES-GCM; automatic downgrade. Records: Selected design items 13 and 14.
10. **BLE, not Bluetooth Classic.** Reason: this choice was made and tested long ago. Settings of 50 Hz and 70 Hz both ran clean in the 2026-09-28 tests, with the 32-byte dummy packet. "70 Hz passed" means the 70 Hz setting, which delivered about 66 packets/s per board. With the 38-byte version-3 packet, one board at 50 Hz ran clean for 65 s on 2026-10-14, against a service on the laptop. Two boards together with 38-byte packets, and real sensor data, have not been measured. Records: `docs/archive/test-evidence/co-live-deployment-2026-09-28.md`; section 5, item 15 and section 6.1 of the hand-off document.
11. **The laptop's OpenSSH commands use an explicit `ProxyCommand`, not `-J`.** Reason: strict host-key checking, timeouts and `BatchMode` can then apply to each hop separately. Rejected: `-J`. `tools.deploy_service` does not use OpenSSH; it uses `paramiko`, which opens the second hop as a `direct-tcpip` channel through the first, with strict `known_hosts` checking on each hop. Records: Selected design item 18.
12. **The phone uses in-app SSH (`direct-tcpip`) and opens no port on the phone.** Reason: the phone owns its whole route and does not depend on the laptop. Rejected: a TLS server listening on port 5005 on the phone (it requires others to connect in to the phone); iSH/Termux foreground forwarding; changing only the standalone C# script (that cannot change the already-exported app). Records: the Selected approach section of the iOS design spec.
13. **Host public keys and the CA fingerprint are pinned in source; no trust on first use.** Reason: on the phone there is no step where a person checks `known_hosts`. Cost: replacing the board or the CA requires a source change and an app rebuild. Renewing only the server certificate from the same CA (`--renew-server-from`) changes nothing in the app. Records: the Security and setup section of the iOS design spec.
14. **Passwords live only in memory; leaving the foreground disconnects.** Reason: the on-site route uses password authentication. Keeping passwords off disk means there is no credential file to manage. It also avoids depending on iOS background survival, which has not been verified. `tools.deploy_service` follows the same rule on the laptop: it asks for both passwords each run and stores nothing. Records: the Security and setup and the Protocol and lifecycle sections of the iOS design spec.
15. **The `device_id` + `boot_id` + `seq` triple; `seq` is assigned before submission; separate read-only source statistics.** Reason: after a reboot the sequence restarts at zero without being confused with old data. A failed submission does not hide a gap. Losses at the start and end of a capture can also be reconciled. A send tick that the glove module does not deliver, that it calls IDLE, or that `scaleSample` refuses takes no `seq`: it was never generated, so it must not look like a sample lost on the way (decision D13, extended to IDLE on 2026-10-15; built). Records: Selected design item 4; Dual-ESP spec. Selected design item 4 said at the time "increment only on a successful submission". The current code assigns `seq` before submission. Follow the Dual-ESP spec and the code.
16. **ACK window 32.** Reason: on the remote route, a single ACK wait measured about 2.4 s. Waiting for each ACK in turn would push later samples past the 2 s freshness. Freshness itself is not relaxed. Stop-and-wait remains available as window 1. Records: the "Implementation notes — bounded ACK window, 2026-09-19" section of the Dual-ESP spec; the measured numbers are in section 5, item 6 of the hand-off document.
17. **`session_id` is configuration, not a secret.** Reason: SSH handles access control. Records: Selected design item 6.
18. **Evidence is graded, and the levels do not substitute for each other.** Reason: ACKs and phone results travel on two independent connections. In a 60 s run on 2026-09-21, all 1203 inputs were ACKed, but the phone received only 1094, which is 109 fewer. The cause is still unknown. With a real model the gap between the levels grows: one input no longer means one result, so level 3a counts what the model did separately. Records: Selected design items 16 and 27; section 7 of `docs/archive/reports/week7-system-technical-report.md`; `docs/archive/test-evidence/dual-esp-iphone-test-2026-09-21.md`; `docs/archive/test-evidence/phone-recovery-test-2026-09-21.md`.
19. **The board runs one process, uses only the standard library, is deployed in the user's own folder, installs no system service and uses no sudo.** Reason: the board is shared, so nobody else's environment is touched. `demo.py service --start` starts the service only when both ports are free, and it never stops or kills an existing process (`tools/demo_service.py:79-97`). `tools.deploy_service` stops only this user's own `ultra96.server` under `BOARD_ROOT` that owns exactly `127.0.0.1:8888` and `:9999`, after checking that, and refuses when another process holds either port (`tools/deploy_service.py:61-74,135-142`). Records: Selected design items 7 and 26.
20. **Only one protocol version at a time; the statistics marker follows it; the subscription envelopes stay at 1.** Reason: the owner's rule of 2026-10-14. Each component accepts only version 3, so there is no mixed state to reason about. The formula dummy was identified only by its version byte, so it could not survive a single version. The source-statistics marker moved to `LCS3` so that a board with old firmware is refused at start-up with a clear message instead of failing packet by packet. `SUBSCRIBE` and `SUBSCRIBED` never carried the packet version and did not change, so moving them would only break subscription. `request_id` stays in every data message (null when unused), so the exact field sets change only in `v`. Records: section 6.5 of the hand-off document, D4 to D7.
21. **int16 fixed-point on the wire, physical floats at the model.** Reason: the owner's direction of 2026-10-14 (transport stays int16; the model gets physical floats). The 16-byte header stays as it was, and a sample stays one 38-byte notification. The scales keep 4 decimal places for acceleration and flex and 2 for angular rate and angles. A Communications-side check (section 2.3 of the hand-off document) found that converting the 11 values to int16 with these scales and back did not change the predictions of a NumPy reproduction of the model. The out-of-range policy is a build flag (`COMMS_OUT_OF_RANGE_DROP`), so either answer from Wen Ree needs no code change. Records: section 6.5 of the hand-off document, D3 and D13; `docs/co-protocol-v3.md`.
22. **Communications checks the shape of a result, not its meaning.** Reason: Communications carries labels without knowing the set, which Wen Ree and Jie Ling agree. One rule (1 to 32 characters of `A–Z a–z 0–9 _ -`; confidence a finite number from 0 to 1) is checked identically on every peer. The board checks before sending, because a result the phone rejects ends the phone session and clears its passwords. Confidence is passed on unrounded, because rounding would change the model's output. Records: section 6.5 of the hand-off document, D8 and D17.
23. **The model runs behind a narrow, counted interface.** Reason: `on_sample` runs on the service's single event loop before the ACK, so it must return at once; slow calls and exceptions (including `SystemExit`, which Wen Ree's existing scripts use to report missing files) are counted instead of being allowed to close connections or stop the service. `emit` may be called from any thread and moves the result onto the event loop, because the result queue has no lock. It accepts numpy-style numbers, because model code commonly produces them. `async def` functions are refused at load, because they would silently never run. Commands never reach the model: their values are transformed dummy rows and their sequence numbers come from the command space, so they would corrupt the model's windows. The built-in dummy model keeps one result per input, so every existing acceptance check stays valid until the real result rate is known. Leftover non-daemon model threads cannot keep a stopped service alive. Records: section 6.5 of the hand-off document, D9 to D12 and D18; section 7.2 of the hand-off document.
24. **Per-result delivery on the phone uses the same bounds as the board.** Reason: the game's actions are one-shot, so it needs results one at a time, not a display that the next result overwrites. The queue is bounded like the board's (32 waiting, 2 s) so that results nobody takes out do not pile up. It is emptied when a session ends, because those results belong to a session that no longer exists, and kept across an automatic reconnect, which is the same session. The limits are provisional until Wen Ree says how often results come. Records: section 6.5 of the hand-off document, D14; section 7.3 of the hand-off document.
25. **Deploying is one checked step with rollback.** Reason: the redeploy is priority 1, and the board is shared and has no service manager. `tools.deploy_service` (the tracked successor of the untracked `.week7-local/co_deploy.py`) makes every check that needs no change on the board first: the new code compiles, the certificate and key match and do not expire within an hour, and the running process is this user's and owns exactly the two ports. Only then does it stop the old process, waiting until it has really exited (a model thread can keep a process alive after its ports close) and sending SIGKILL only to the same process. Any later failure restores the old certificate and restarts the old code. `demo.py service --start` follows the newest deployment record, folder and model, so a restart after a reboot does not silently run old code or the dummy model. Records: section 6.5 of the hand-off document, D15, D16 and D19.
26. **Each board is checked on its own after flashing, without the Ultra96.** Reason: the laptop has one programming cable, and a check that needs the Ultra96, the SSH route and the phone would mix board faults with route faults. `tools.check_board` connects by the board's address over the real protected BLE path and runs everything else on the laptop with throwaway certificates. Records: section 6.5 of the hand-off document, D1 and D16.
27. **A glove sends only while its glove module reports MOVING; the state does not travel in the packet.** Reason: Siqiang's answer of 2026-10-15. The final gloves should send nothing while IDLE, and he wraps his decision in a function returning a bool; the owner asked that the Communications firmware call it for each sample. Keeping the decision out of the packet keeps the 38-byte layout, the MTU floor, the command frame and `on_sample` unchanged, and a still player costs no radio time. The cost: the model never sees the first part of a motion (at least about 0.4 s) or anything while IDLE. `-DCOMMS_GLOVE_SEND_ALL=1` exists for recording sessions, which need IDLE data too. Built; not run on a board. Records: section 7.1 of the hand-off document; `comms_glove.h:5-28`.
28. **Skipped send ticks take no `seq` and are counted at the source.** Reason: a `seq` gap must keep meaning "lost on the way", so the laptop's gap detection and the reconciliation generated = received = ACKed still hold on a gated board. Counting the idle, unread and refused ticks shows that a silent board was still ticking. The coverage rule for a gated board uses that: generated plus idle must reach 90% of the ticks expected while its notifications were on, and silence is not judged once it reported idle ticks. The statistics grew to 36 bytes under the same marker `LCS3`, because the 24-byte `LCS3` never left the right board; a 24-byte value is refused with an instruction to reflash. Clamped values stay on the serial line, because they belong to samples that were sent. Records: `laptop/dual_bridge.py:391-416`; `laptop/source_audit.py:55-78`.
29. **The glove module never runs under the connection-state mutex, and the send tick keeps its rate.** Reason: the BLE callbacks take that mutex, so a module call of 10 to 20 ms must not hold it. The firmware reads the module outside the mutex and commits the tick only if the laptop is still ready, so the source statistics stop changing once notifications are off; the laptop's quiesce check relies on that. The send deadline advances by whole intervals, so a slow pass delays one tick without lowering the rate, and a long stall drops ticks instead of sending a burst. `gloveBegin` runs before BLE starts, so no connection disturbs the calibration (glove held still), and a board without a sensor still advertises and can be checked. Records: `comms_sample.h:67-78`; `main.cpp:399-431`.
30. **The board keeps a silent ingest connection open for 600 s, and frees slots from the one that has waited longest.** Reason: a gated glove is silent while the player is still. Under the old 5 s limit the board closed that connection, and the first frames after each pause were lost as ambiguous during the TLS reconnect. 600 s covers any pause in a game. Once a frame begins, it must still arrive within 5 s, so a broken stream is still caught. Silent connections now live long, and the SSH tunnel's `sshd` can hold the socket of a laptop that vanished for many minutes. So a full board (8 slots) closes the ingest connection that has waited longest, at least 5 s (the old limit), to admit a new client; a streaming connection is never closed for this. The phone side is unchanged. Records: `ultra96/server.py:33-47`.
31. **Siqiang's module is built from identical copies, never edited, and only in separate `-glove` environments.** Reason: `hardware/` is Siqiang's, and Communications must not change it (`AGENTS.md`). His `#include "../../../movement_model_params.h"` resolves only in a PlatformIO library layout. So `tools/sync_glove_module.py` copies his files into `firmware/esp32/lib/glove_sensor/src/` and the weights header to the firmware root. `tests/test_glove_module_sync.py` fails while a copy differs, so a change in the team repo cannot be missed, and `flash.py --glove` refuses stale copies. The default environments keep the dummy module, so every check without sensors still works. The `-glove` environments start at 50 Hz, the model's rate. Records: `tools/sync_glove_module.py:1-16`; `firmware/esp32/lib/glove_sensor/README.md`.

**Certificates**

- The server certificate is valid for only 30 days. Only the copy kept on the laptop was checked: it expired at `2026-10-06 15:11:29 UTC`. That copy is the certificate deployed to the board in September. The 2026-09-28 deployment reused the existing TLS files (`docs/archive/test-evidence/co-live-deployment-2026-09-28.md`), and the repository has no record of a certificate change after that. Nobody has checked the board's actual state, so the board's certificate is not verified as expired.
- If the board still has this certificate: the service starts normally, but every laptop TLS handshake fails. Only `transport_errors` increases, and no ACK arrives. The iPhone shows `Disconnected: SSH, TLS or protocol verification failed; correct setup and reconnect` and does not retry automatically.
- A renewed pair was made on 2026-10-14 with `--renew-server-from` from the existing CA, into `~/.codex/private/cg4002-comms-server-20261014/` (outside the repository). Verified locally: CN and SAN `ultra96.week7.internal`, issuer `Week 7 Development CA`, valid 2026-10-14 14:22:35 to 2026-11-13 14:27:35 UTC, it chains to the CA, the key matches, and a local TLS 1.3 handshake with `SUBSCRIBE`/`SUBSCRIBED` worked. **It is not on the board.** `python -m tools.deploy_service --server-cert-dir <that folder>` installs it together with the version-3 service: it checks that the pair matches and has more than an hour left before anything changes, backs up the old pair to `BOARD_ROOT/tls/backup-<stamp>/`, and installs the new one with the key at mode 600 (`tools/deploy_service.py:147-154,210-221`). Without `--server-cert-dir` it keeps the board's certificate and refuses to deploy if that one expires within an hour.
- The renewed certificate expires before the final demo around Week 13; renew again in early November.
- How to check: with the tunnel open, run `openssl s_client -connect 127.0.0.1:18889 -servername ultra96.week7.internal` on the laptop; or run `openssl x509 -in <deployment folder>/tls/server-cert.pem -noout -dates` on the board.

It reads `ca-cert.pem` and `ca-key.pem` from `CA_DIR` and confirms that the private key belongs to that CA certificate. It refuses when the CA has less than 30 days of validity left. In a new, empty folder (which must be outside any Git repository) it writes a new `server-key.pem`, a 30-day `server-cert.pem` and a copy of `ca-cert.pem`. The CA itself does not change, so neither the CA fingerprint in the phone source nor the laptop's `--ca` needs to change. The full steps are in section 6.3 of the hand-off document. Tests: `test_renewed_server_certificate_keeps_the_ca_and_is_trusted_by_existing_clients` and `test_renewal_refuses_a_mismatched_key_an_occupied_folder_and_git` in `tests/test_transport.py`.

**Laptop SSH prerequisites**

- Both hops use `StrictHostKeyChecking=yes` (`tools/ssh_tunnel.py:26-28`). `tools.deploy_service` loads `~/.ssh/known_hosts` with `paramiko`'s `RejectPolicy` for both hops (`tools/deploy_service.py:334-336`). No code in the repository writes `known_hosts`. On a different laptop, `demo.py tunnel`, `demo.py service` and `tools.deploy_service` all fail at once with a host-key error until both hosts' public keys are in the local `known_hosts`. The two ed25519 public keys to check against are in the phone source, `Configuration.swift:17-18`.
- The tunnel command calls a program named `ssh` directly (`tools/ssh_tunnel.py:29,33`). The OpenSSH client must be on `PATH`.
- `tools.deploy_service` needs `paramiko`, which `requirements-dev.txt` lists since 2026-10-14 (`paramiko>=2.8,<4`). On the owner's laptop it comes with Anaconda (2.8.1, checked 2026-10-14). The dry run does not import it (`tools/deploy_service.py:332,364-366`). Its SSH half has never connected: the WSL test covered only the board-side program (section 6.1 of the hand-off document). It logs in with passwords only (`look_for_keys=False`, `allow_agent=False`, `tools/deploy_service.py:338-346`).
- Each endpoint must match `user@host`. User names allow only letters, digits, underscore and dot; a user name with a hyphen is rejected. Host names allow hyphens (`tools/ssh_tunnel.py:20-22`).
- Timeouts for the interactive command: `ConnectTimeout=20` on the proxy hop and `ConnectTimeout=60` on the target hop, which leaves time to type the password. In supervised mode both hops use 10 (`tools/ssh_tunnel.py:30,35`). Both hops set `ServerAliveInterval=15` and `ServerAliveCountMax=3`.
- `demo.py tunnel` starts one ssh child process and does not restart it after it exits (`demo.py:119-130`). `python -m tools.ssh_tunnel --run` does restart it, with a back-off that doubles from 0.5 s to 5 s and never resets (`tools/ssh_tunnel.py:52-80`). It forces `BatchMode=yes`, so it works only with key or agent authentication; passwords cannot be typed.
- The `--jump` and `--target` defaults of `demo.py tunnel` are the original operator's accounts (`demo.py:40-41`). Anyone else must pass them explicitly. The account, host and board path for `demo.py service` are hard-coded in `tools/demo_service.py:13,16,60-61`, and its command line has only `--start` and `--session-id`. Anyone else must change the source to use it. `tools.deploy_service` defaults to the same accounts and takes `--jump-user` and `--board-user` (`tools/deploy_service.py:428-429`); its board folder is the same `BOARD_ROOT`.

**Phone**

- The jump host, the board host name, the host public keys, the CA fingerprint and the session ID are all compiled into the app. The laptop's `--jump`, `--target`, `--ca` and `--session-id` do not affect the phone.
- The installed app is the Week 7 build: session `week7-demo`, version-2 results, the four dummy labels at confidence 1.0. It cannot read version-3 results. The version-3 Swift changes (validation, `confidence`, `CommsNextResult`, the display texts) were compiled and tested on Linux on 2026-10-15, in a Swift 6.1 container (72 tests, 0 failures). Not compiled or run there: the `#if os(iOS)` code (including `IntegrationController.swift` and `SetupViewController.swift`) and `PythonBoardTests`. On 2026-10-16, on the owner's Mac (Xcode 26.2, Swift 6.2.3): `swift test` on macOS passed 73 tests, `PythonBoardTests` included; the preview app built for the iOS Simulator, which compiled the `#if os(iOS)` code for iOS for the first time since the changes of 2026-10-14 (the `Week7Native` copy of that code was built for iOS and installed on 2026-09-28), and passed 34 transport tests and 1 UI test; and the Week 7 Unity export built with the package as an unsigned iPhone app (`CODE_SIGNING_ALLOWED=NO`, generic iOS device). Signing and installing are next, and are the owner's: the owner chooses a team in Xcode and runs the `Unity-iPhone` scheme on the iPhone, which rebuilds the app signed; the unsigned build is not installed as it is (section 6.3 of the hand-off document). Until then the installed app stays the Week 7 build.
- The app must stay in the foreground. Locking the screen or switching to the background disconnects and clears the passwords.
- The phone has no SSH keep-alive or heartbeat. When the network fails silently, the phone notices only when the operating system reports an error.
- Automatic retry on the phone means logging in to the jump host and the board again with the passwords, after a delay that starts at 0.5 s and doubles up to 5 s (reset after a result arrives), with no limit on attempts. The phone treats a service that is not running, a session mismatch and being replaced by another subscriber all as a closed connection, and retries. When the service is not ready, tap Disconnect first.
- One Connect is one counting session. Tapping Connect again resets `Received` to zero; in the source it also empties the `CommsNextResult` queue and resets its two drop counters.

**Board**

- There is only one subscriber at a time. Running `laptop/phone_simulator.py` or a remote rehearsal replaces the phone.
- Results produced while there is no subscriber are dropped and never resent later. So get the phone to `Subscribed` before starting a capture.
- Deduplication state is only in memory. After a service restart, old inputs may be accepted again.
- At most 128 `(device_id, boot_id)` pairs per process. Each glove reboot uses one. Once they are used up, new boots are rejected and the service must be restarted. The reason for the rejection is not logged. The operator sees only that a freshly powered glove never connects, while the laptop's `ack_errors` and `transport_errors` keep growing.
- The current service closes an ingest connection when no frame begins within 600 s (`--ingest-idle-timeout`; built, not yet deployed). The deployed September snapshot still closes it after 5 s idle. The 2026-09-28 power-loss test recorded the consequence of that: the first sample after the affected glove reconnected got no ACK and was counted as one ambiguous drop. With gating, a 5 s limit would cost that after every pause longer than 5 s.
- With all 8 slots taken, the board closes the ingest connection that has waited longest (at least 5 s). If that was a live glove that was only still, the glove loses its next frame as ambiguous when it moves again, as under the old limit. In V1 (two gloves, one phone, an operator tool now and then) 8 slots are not expected to fill; stale connections held by `sshd` after a laptop vanished are the expected case.
- The service is not a system service and has no automatic restart. How it runs depends on how it was started. Started with `demo.py service --start`, it runs in the foreground of an SSH session (`ssh -tt`, `tools/demo_service.py:58-69,98`); closing that terminal, the laptop sleeping or the VPN dropping makes it exit. Started with `tools.deploy_service`, it runs in the background in its own session (`start_new_session=True`, `tools/deploy_service.py:106-109`), with its output in `BOARD_ROOT/evidence/server-co-<stamp>.log`, its PID in `BOARD_ROOT/evidence/server.pid` and the deployment record in `BOARD_ROOT/evidence/active-deployment.json` (`tools/deploy_service.py:232-238,254`). The process recorded on the board on 2026-09-28 was started the same background way by the untracked `.week7-local/co_deploy.py` (`subprocess.Popen(..., start_new_session=True)`, `.week7-local/co_deploy.py:85`), with `--session-id week7-demo` and an `--event-log-dir` under `BOARD_ROOT/evidence/`; its output goes to a log file under `BOARD_ROOT/evidence/`, and its PID is in `BOARD_ROOT/evidence/server.pid` (`.week7-local/co_deploy.py:107,111`). That process does not depend on any SSH session and may still be running. `tools.deploy_service` finds it itself through `/proc` (this user's `ultra96.server` under `BOARD_ROOT`, owning exactly the two ports) and replaces it. `python demo.py service` shows it read-only (`ss -ltnp`, the user's processes and each server's working folder; `tools/demo_service.py:114-121`). `demo.py service --start` refuses to start while either port is in use, and it never stops an existing process.
- The board service logs one INFO line for every accepted input (`ultra96/server.py:325-326`). With both gloves moving at 50 Hz, that is about 100 lines per second; a gated glove adds none while it is still. On the `demo.py service --start` path they all go through the foreground SSH terminal. A background service writes them to its log file under `BOARD_ROOT/evidence/`.
- `demo.py service --start` starts from the folder, `--model` and `--model-path` of the service that the newest local deployment record (`.comms-local/deployments/deployment-*.json`, written by `tools.deploy_service`) left running, after validating them (`tools/demo_service.py:27-55,72-98`). With no usable record it falls back to the 2026-09-28 snapshot `BOARD_SOURCE` and the dummy model. A deployment made by hand or from another laptop leaves no local record, so `--start` would then start the old code. No deployment record exists yet (`.comms-local/deployments/` does not exist on 2026-10-15).
- The session ID for `demo.py service --start` comes from `--session-id`, then the environment variable `LTC_COMMS_SESSION`, and is `ltc-comms` when neither is set (`demo.py:70-71,298`; `tools/demo_service.py:72-73,98`). It is printed before the start, with the folder and the model (`tools/demo_service.py:106-109`). `tools.deploy_service` uses `--session-id`, default `ltc-comms` (`tools/deploy_service.py:422`).

  1. `glove_sensor.cpp:4` includes `"../../../movement_model_params.h"`. From `hardware/gloves/integration_files/` that path resolves to the repository root, where no such file exists, so the file does not compile where it lives. **Model on the board**

- The model's `on_sample` runs on the service's only event loop, before the ACK. A model that does its inference inside `on_sample` holds up the ACKs of both gloves (the laptop waits at most 5 s; sample freshness is 2 s). The counters `model_slow_calls` and `model_max_call_ms` in the `stopped` line show it. On the right board on 2026-10-14 the dummy model's slowest call was 0.39 ms.
- The model runs inside the service process as `xilinx` with `/usr/bin/python3`, without sudo. `fpga/README_FPGA_PYNQ.md` says the overlay is loaded with sudo and the pynq-venv Python. If the model can only run that way, it is a separate process, and Communications defines a format for passing the same fields between the two processes on the board. That is the owner's work and is not built.
- A model whose threads are not daemon threads no longer keeps a stopped service alive (`exit_with_model_threads`), but its threads end abruptly then.
- `emit` returning `True` means only that the arguments were valid and the service was running. The identity and duplicate checks come afterwards, and with no subscriber the result is dropped.
- The one-input-one-result criteria (`Phone expected increase` in `demo.py`, `tools/rehearse_comms.py`, `tools/rehearse_remote_comms.py`, `tools.check_board`) hold only while the board runs the built-in dummy model (`demo.py:215-217`). They are redefined once Wen Ree says how often results come (section 8, step 6 of the hand-off document).
- With gating, the model receives samples only while a glove moves, starting at least about 0.4 s into each motion, and each glove on its own. A model that expects a continuous 50 Hz stream from both gloves has to handle pauses and one-sided streams. That is Wen Ree's; Communications passes every sent sample through unchanged.

**End to end**

- No timestamp runs through the whole path. The 2 s freshness is each segment's own holding time, not end-to-end latency. On the board it limits how long a result waits in the queue and in the write into the phone's connection (`get_timed`, `_send_results` in `ultra96/server.py`); it says nothing about whether or when the phone receives the result. The phone has its own 2 s display window, counted from when it received a result.
- There is no guarantee of absolutely zero loss. Conclusions can only be drawn from the reconciliation of a specific capture. Reconnects can leave `seq` gaps (see "Technical constraints on the teammate interfaces" above). IDLE pauses leave no `seq` gap, only `uptime_ms` jumps.
- The phone status `Subscribed` means only that the subscription handshake with the Ultra96 succeeded. It does not prove that results are flowing.
- In the version-3 code, any label of 1 to 32 characters from `A–Z a–z 0–9 _ -` and any confidence from 0 to 1 pass on all four peers. What is deployed is still version 2: the September board service and the installed phone app accept only `REST`, `FIST`, `OPEN`, `POINT` at confidence 1.0. Until the redeploy and the installation of a phone app built from the current source (section 6.3 of the hand-off document; the unsigned build of 2026-10-16 is not installed), a real model label, or any version-3 result, makes the installed app disconnect with a terminal error.
- A leftover `LTC_COMMS_SESSION` in the terminal affects `demo.py run`, `live` and `service --start` together, but not the phone. Documents from the transition period told operators to set `LTC_COMMS_SESSION=week7-demo`. If it is left over, the laptop and a newly started service both use `week7-demo`, and `CAPTURE PASSED` appears as usual, while the phone stays at `Disconnected: connection closed; retrying`.
- `demo.py` uses local port 18889. Running `laptop.dual_bridge` or `tools.ssh_tunnel` directly defaults to 18888. The tunnel and the capture must use the same port.
- Both boards advertise the same name. They are told apart by Bluetooth address and by the `device_id` in the packet.
- The laptop side supports only Windows (pairing uses WinRT; `flash.py` assumes `COMx` serial ports and PlatformIO's Windows paths).
- Do not run `python -m pytest` without paths from the repository root. It collects `fpga/hls/export_conv1d_test.py`, which rewrites a tracked file as soon as it is imported.
