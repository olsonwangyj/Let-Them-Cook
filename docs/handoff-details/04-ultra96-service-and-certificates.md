## Role and boundaries

- The Ultra96 service is a Python asyncio process that uses only the standard library. Its entry point is `python3 -m ultra96.server` (`main` in `ultra96/server.py`). A model module loaded with `--model` runs inside the same process (see "The model interface").
- It opens only two TLS listeners, both on the board's loopback address: the ingest port `127.0.0.1:8888` and the gateway port `127.0.0.1:9999`.
- The ingest port receives `SENSOR_BATCH` (version 3) from the laptop and answers each one with an `INGEST_ACK` (version 3). Between frames an ingest connection may stay quiet for up to the ingest idle limit, 600 s by default, because a gated glove sends nothing while the player is still (see "Limits and timeouts").
- The gateway port receives `SUBSCRIBE` (version 1) from the phone and answers `SUBSCRIBED` (version 1). After that it only pushes `GESTURE_RESULT` (version 3) to the phone. In the code of 2026-10-18 (`2b3be2b`; deployed on the Ultra96 since 2026-10-19) the gateway also accepts `MONITOR` (version 1) as the first frame, from the laptop's read-only board view; it answers `MONITORING` and then only pushes `MONITOR_UPDATE` (version 1). A monitor never becomes or replaces the subscriber (see "The board monitor").
- Both ports are reachable only through SSH. The laptop first logs in over SSH to port 22 of the jump host `stujump`. It then logs in through the jump host to port 22 of the Ultra96. Finally an SSH local forward reaches port 8888 on the board. The iPhone makes the same two hops inside the app and ends at port 9999 on the board. The two routes are independent of each other. Since the code of 2026-10-18, `python demo.py start` and `python demo.py tunnel` add a second local forward to the same laptop login, local 19999 to port 9999 on the board, for the board view (hand-off 6.5, D40). The route itself is unchanged. The laptop still receives no `GESTURE_RESULT` and forwards no result; since the redeploy of 2026-10-19 the service on the Ultra96 has the board monitor, through which the laptop sees the results as the monitor's events (first seen there on 2026-10-19 at 02:56 (+08:00), when the board view of the first `python demo.py start` connected; that run found no gloves).
- The service never connects out. The code has only the two listeners and no logic that opens a connection to the phone or the laptop.
- Communications' responsibility here ends at these interfaces: samples are received accurately (proven by the ACK); each newly accepted stream sample is decoded into 11 physical floats and handed to the model's `on_sample`; the model's results come back through the thread-safe `emit`; each result is written accurately to the subscriber. The board side of this is built on the branch (hand-off 6.5, D9), and deployed on the Ultra96 since 2026-10-16 with the built-in dummy model (redeployed on 2026-10-19 from `2b3be2b`, still with the dummy model). Wen Ree's model module does not exist yet, and the function names stay provisional until Wen Ree confirms in-process use (hand-off 7.2). The service never merges, splits, filters, renames or reinterprets results. It refuses only a result that the phone would refuse or misread (an invalid label or confidence; a glove power-up the service has not seen, or a `seq` above the highest it accepted for that power-up; a second result for one sample), and it counts each refusal. A `seq` inside a gap is not detected.
- The following belong neither to this service nor to Communications: pairing the left and right gloves, building model windows, deciding gesture or idle, model accuracy, and mapping labels to game actions. They belong to Wen Ree and Jie Ling. Which samples are sent at all is decided on the glove, by Siqiang's movement detector, which the Communications firmware calls (hand-off 7.1; [detail chapter 2](02-firmware.md)). Wen Ree and Jie Ling also agree between themselves the label names, how often a label is produced, and whether several identical labels in a row (for example several `CHOP`) mean one action or several (hand-off 3.1).
- Results in the version-3 code: without `--model`, the service runs its built-in dummy model, which answers each accepted stream sample with one random `REST`, `FIST`, `OPEN` or `POINT` at confidence 1.0. Each new command gets one echo result from the service itself, never from the model. Wen Ree's module plugs in at `ultra96/model.py` and the call at `ultra96/server.py:339-342`; the requirements are in hand-off 7.2. The dates asked of Wen Ree, proposals until Wen Ree confirms them, are a first connectable version pushed to the team repo by Fri 10-16 and the real model by Sun 10-18 (hand-off 6.4).
- Evidence levels follow section 4.7 of the hand-off document. `INGEST_ACK` is level 3: the board service validated and accepted this input and, for a stream sample, the model's `on_sample` has returned. It does not prove that the model produced a result or that the phone received anything. Level 3a is the counters `model_samples` and `model_results` in the `stopped` line and the events `model_result` and `model_result_refused` in the event log: how many samples went to the model and how many of its results the board accepted for sending. `result_write_complete` in the event log is level 4. It proves only that the board wrote the result into the connection; the event always carries `phone_receipt_confirmed=false`. `Received` on the phone screen is level 5. `CAPTURE PASSED` printed by `demo.py` is level 3. The phone status `Subscribed` is none of these: it means only that the `SUBSCRIBE`/`SUBSCRIBED` handshake with this service succeeded. The board monitor of the code of 2026-10-18 (deployed on the Ultra96 since 2026-10-19) shows two of these levels while the service runs, per glove: `results` and `refused` are level 3a, and `sent` is level 4, the `result_write_complete` point, still not a phone receipt (see "The board monitor").
- Certificates: the local tool `tools/generate_comms_pki.py` generates a new CA and server certificate, or renews only the server certificate from the existing CA. The service loads only the server certificate and private key. The laptop and the phone get only the CA certificate. A renewed server certificate exists on the owner's laptop since 2026-10-14, and is installed on the board since 2026-10-16; the redeploy of 2026-10-19 kept it (see "Certificates").

## Data formats and constants

### Frame format (same on both ports, `common/wire.py`)

| Offset | Length | Type | Content |
|---:|---:|---|---|
| 0 | 4 | uint32, big-endian (`struct` format `!I`) | Body length N in bytes, not counting these 4 bytes |
| 4 | N | UTF-8 | One JSON object, compact separators, `ensure_ascii=False` |

- N ranges from 1 to 16384 (`MAX_FRAME_SIZE`, `common/wire.py:7`). The stream buffer limit is 16388 (`STREAM_LIMIT`, `common/wire.py:8`).
- There is no newline delimiter, no BOM and no error frame.
- On read, these are rejected: length 0 or above 16384, an incomplete header, an incomplete body, invalid UTF-8, invalid JSON, duplicate keys at any level, `NaN` and `Infinity`, floats that overflow to infinity (such as `1e999`), and a top level that is not an object.
- On write, `encode_frame` rejects the same things: a non-object, values that cannot be encoded, non-finite numbers, and a body over 16384 bytes (`common/wire.py:35-46`).
- A clean disconnect (EOF) between frames is a normal end and is not counted in `rejected`. A disconnect halfway through a header is an error (`common/wire.py:58-63`).
- Without `idle_timeout`, the header and the body of one frame share one deadline, 5.0 s by default (`common/wire.py:49`, `:79-80`). With `idle_timeout`, the first header byte may take up to `idle_timeout` seconds; from that byte on, the rest of the header and the body share the 5.0 s deadline (`:81-83`). Only the ingest port passes `idle_timeout` (`ultra96/server.py:326`). The gateway reads its first frame, `SUBSCRIBE` (or, in the code of 2026-10-18, `MONITOR`), with the single 5.0 s deadline (`:424`). Writing one frame also has a 5.0 s default deadline (`common/wire.py:86-89`).
- `write_frame` assumes that only one task writes on each connection (the docstring at `common/wire.py:87`). On the service, the only task that writes results to the phone is the send task `_send_results`. On a board monitor's connection, `MONITORING` is written first (with a 2.0 s deadline), and after it only that connection's sender task `_send_updates` writes.

### Rules common to all messages (`ultra96/protocol.py`)

- `type` must be one of the eight types (five before the code of 2026-10-18, which added `MONITOR`, `MONITORING` and `MONITOR_UPDATE`), and a port accepts only its own: a `MONITOR` on the ingest port is a wrong type.
- `v` must equal the version of that type: 3 for `SENSOR_BATCH`, `INGEST_ACK` and `GESTURE_RESULT` (with `--sensor-version 4`, since 2026-10-27: 4 for `SENSOR_BATCH` and `INGEST_ACK`, still 3 for `GESTURE_RESULT`, `RESULT_VERSION`); 1 for `SUBSCRIBE` and `SUBSCRIBED`, and for the three monitor messages (`ultra96/protocol.py:31-32`, `:140-142`). Any other value, including 1 or 2 on a data message, is rejected as `unsupported protocol version`. There is no interoperability with versions 1 and 2 (the owner's rule: only the newest version is supported).
- The field set must match the tables below exactly. One extra or one missing field is rejected (`ultra96/protocol.py:143-144`).
- Integers must be real integers. The booleans `true` and `false` do not count as integers.
- `session_id`: a string of 1 to 128 characters, with no control characters below code point 32 and nothing in U+D800 to U+DFFF (`ultra96/protocol.py:119-124`). It must also equal the session ID configured when the service started. Otherwise the code raises `wrong configured session` internally (`ultra96/protocol.py:146-147`).
- Every validation failure is handled the same way: the connection is closed, `rejected` goes up by 1, and no message is sent back. The exception texts (for example `wrong configured session`, `unsupported protocol version`, `values must contain exactly eleven int16 integers`, `gesture must be 1..32 characters from A-Z a-z 0-9 _ -`) are used only inside the process. They are not logged and not sent to the peer. The peer only sees the connection close (`ultra96/server.py:300-301`).

### The `request_id` rules

- The key is always present in `SENSOR_BATCH`, `INGEST_ACK` and `GESTURE_RESULT` (hand-off 6.5, D6).
- `request_id = null`: an ordinary stream sample; and every model result.
- `request_id` is an integer: a command. The range is 1 to 4294967295, and `seq == request_id` is required (`ultra96/protocol.py:154-158`). 0, negative numbers, 2^32 and booleans are rejected.
- The ACK and the command echo carry `request_id` unchanged. A command echo's `result_id` has the `cmd:` prefix.

### De-duplication and replay protection

Since version 3 there is one rule for every sample (`CommsServer._duplicate`, `ultra96/server.py:391-421`). The version-1 rule, which compared only the key and forgot it after 4096 entries, is gone (see "History and removed items").

| Category | Storage | Limit | When full | Counts as a duplicate when | Connection is closed when |
|---|---|---|---|---|---|
| Stream sample (`request_id` null) | `_fingerprints` (ordered dictionary of `(device_id, boot_id, seq)` → fingerprint `(uptime_ms, values)`) and `_high_water` (the highest `seq` per `(device_id, boot_id)`) | 4096 fingerprints; `max_namespaces` = 128 namespaces | Fingerprints evict the oldest entry; high-water marks are never evicted | The key is in the fingerprint table with the same fingerprint | Different fingerprint; `seq` at or below the high-water mark and not in the fingerprint table; the 129th namespace |
| Command (`request_id` set) | `_commands` | `max_commands` = 4096, never evicted | No eviction | The key exists with the same fingerprint | Different fingerprint; the 4097th new command |

- The limits are the constructor arguments `max_namespaces` and `max_commands` (`ultra96/server.py:124`). They must be positive integers, otherwise `ValueError` (`:153-155`). Before version 3 they were called `max_v2_namespaces` and `max_v2_commands`.
- A duplicate input gets `status: "duplicate"`, `duplicates` goes up by 1, and the event is `result_duplicate`. It reaches neither the model nor the phone.
- When the connection is closed, no ACK is sent and `rejected` goes up by 1. The internal exception texts are `conflicting payload for existing identity` (`ultra96/server.py:405`), `stale stream identity outside replay window` (`:414`), `stream identity capacity exhausted; start a new session` (`:416`) and `command identity capacity exhausted; start a new session` (`:409`). These texts are never output.
- Stream samples and commands use separate ledgers. A command does not move the high-water mark.
- After capacity runs out, existing namespaces and existing commands still work normally. A new glove power-up (a new `boot_id`) or a new command is rejected every time until the service restarts.
- All de-duplication state lives only in memory and belongs to this one process. A service restart clears all of it.
- A stream's `seq` must increase within one power-up. Wrap-around is not supported. An earlier sample that arrives out of order makes the service close the connection. Gaps are allowed: a `seq` above the high-water mark is accepted however far above it is (`ultra96/server.py:411-417`). A gated glove's idle pause is not a gap: its `seq` does not advance while it sends nothing.
- State is recorded before the next input is processed (`_duplicate` finishes before any `await`). So even if the ACK was never written, the same identity arriving again is treated as a duplicate or a conflict.
- The high-water marks are also used for the identity check on model results: the result's power-up must be known and its `seq` must not be above the mark. A `seq` inside a gap passes (see "The model interface").

With the current code and firmware it was repeated on 2026-10-16 (3022 samples to the model and 3022 results back, slowest call 0.291 ms; [detail chapter 3](03-laptop-relay-and-tools.md)). Since 2026-10-16 the dummy model also runs on the Ultra96: that day's remote rehearsals got exactly one dummy-model result per acknowledged sample through it (576 synthetic, 563 from the right board). The model counters of the service deployed on 2026-10-16 became visible only when it stopped; the code of 2026-10-18, deployed on the Ultra96 since 2026-10-19, also sends them, except `model_results`, `model_results_rejected` and `model_results_duplicate`, to a board monitor every 0.25 s, and per glove the published and refused model results (see "The board monitor"). Wen Ree's module does not exist yet; the names `start`, `on_sample` and `emit` and the in-process use are provisional until Wen Ree confirms them (hand-off 7.2; 6.5, D9).

**What a model is.** Any object or module with two callables, `start(emit)` and `on_sample(device_id, boot_id, seq, uptime_ms, values)`. The command line loads only modules. An object can be passed only through the Python API (`CommsServer(..., model=...)`), which the tests use.

**Loading** (`load_model`, `ultra96/model.py:53-69`):

- Without `--model`, the built-in `DummyModel` is used.
- With `--model MODULE`, the folder given by `--model-path DIR` (if any) is inserted first on `sys.path`, then `MODULE` is imported (`importlib.import_module`; a dotted name inside a package works).
- `start` and `on_sample` must be callable attributes of the module, and neither may be `async def` (checked with `inspect.iscoroutinefunction`). Otherwise `TypeError`. The service calls both directly on its event loop, where a coroutine would never run (hand-off 6.5, D10).
- The model's name in `model_ready` and `model_failed` is the module's import name (`__name__`), never a global inside the module. An object is named by its `name` attribute or its class name (`model_name`, `:72-76`). The dummy model is `dummy`.

**Order at start-up** (`_run_service`, `ultra96/server.py:560-612`; `CommsServer.start`, `:185-210`):

1. Import the model. This happens before the certificate is loaded. Any exception, or a `SystemExit` raised while importing, prints `model_failed` and ends with a non-zero exit. A `SystemExit` is turned into `ModelStartError`, so even `sys.exit(0)` in the module gives a non-zero exit (`:564-570`).
2. Build `CommsServer`: load the certificate and key (`:571`), check the session and the ingest idle limit. A bad session, certificate or key is reported as itself, with a traceback, not as a model failure (the comment at `:562-563`).
3. Call `start(emit)` once, on the event-loop thread, before any listener exists (`:189-190`). If it raises an exception or `SystemExit`, the result is `ModelStartError("model start(emit) raised <type>")` (`ultra96/model.py:126-138`): no port is opened, `model_failed` is printed, and the exit is non-zero (`ultra96/server.py:576-580`).
4. Open both listeners. Then print `model_ready` and `listening`.

- `model_ready`: `{"event": "model_ready", "model": <name>, "seconds": <duration of start(emit), rounded to 3 decimals>}` (`ultra96/server.py:586-587`). The import time is not included.
- `model_failed`: `{"event": "model_failed", "model": <MODULE, or "dummy">, "error_type": <type name of the original exception>}` (`ultra96/server.py:555-557`). For example `ModuleNotFoundError` for a missing module, `TypeError` for a missing or `async def` function, `RuntimeError` for a `start` that raised it, `SystemExit` for `sys.exit()` in the module or in `start`.

**`on_sample`** (`ModelPort.on_sample`, `ultra96/model.py:150-166`; called at `ultra96/server.py:339-342`):

- Called once for each newly accepted stream sample (`request_id` null). Not for a duplicate, not for a command, not for a rejected frame. With a gated `-glove` build (`COMMS_GLOVE_SEND_ALL=0`; since pull request #31, in local `main` from 2026-10-23, the `-glove` environments set it to 1), only samples sent while the movement detector said MOVING arrive; the default dummy builds send every tick (see "The model interface" under "Cautions and known limitations").
- Called on the event-loop thread, inside `_ingest`, before that sample's ACK is written.
- Arguments: `device_id`, `boot_id`, `seq`, `uptime_ms` as received, and `values`, a tuple of 11 Python floats, each `int16 / SCALES[i]` (`physical_values`, `common/sensor.py:92-98`). Packing keeps 4 decimal places for acceleration and flex and 2 for angular rate and angles; restoring cannot recover more. Any normalisation is Wen Ree's.
- The return value is ignored.
- Any `Exception` or `SystemExit` raised by `on_sample` is caught. `model_errors` goes up by 1, a warning is logged (rate-limited), and ingestion continues on the same connection. The ACK is still `accepted` (hand-off 6.5, D18).
- Every call is timed. A call longer than 5 ms (`SLOW_CALL_SECONDS = 0.005`, `ultra96/model.py:30`) increments `model_slow_calls` and logs a rate-limited warning. `model_max_call_ms` keeps the longest call in milliseconds, rounded to 3 decimals. Nothing is cut short: a slow call still delays the ACKs of both gloves, result sending and new connections, because they all share one event loop.

**`emit(gesture, confidence, device_id, boot_id, seq)`** (`ModelPort.emit`, `ultra96/model.py:168-187`):

- Callable from any thread, including from inside `on_sample`.
- It first checks and converts the arguments synchronously (`normalize_result`, `:84-100`). `gesture` must be a `str` (a subclass such as a numpy string is converted with `str()`) that satisfies the label rule. `confidence` may be any `numbers.Real` that is not a `bool` (numpy floats, `fractions.Fraction`); it is converted with `float()` and must satisfy the confidence rule. `device_id` must be a `numbers.Integral` (not a `bool`) equal to 1 or 2; `boot_id` and `seq` must be `numbers.Integral` from 0 to 4294967295. All three become plain `int`. The confidence is not rounded: a numpy `float32` 0.93 arrives as 0.9300000071525574 (hand-off 6.5, D17).
- It returns `True` when the arguments are valid and the service is running, and `False` when they are invalid or the service has not started or has stopped. `True` does not mean the result was sent: the identity and duplicate checks below, and the subscriber, come afterwards.
- Hand-over: on the event-loop thread the result is handled at once; from any other thread it is passed with `loop.call_soon_threadsafe`. Only the event loop touches the result queue and the subscriber.
- Invalid arguments are counted on the event loop as `model_results_rejected`, with a rate-limited warning. Nothing is sent.

**Checks on the event loop** (`CommsServer._model_result`, `ultra96/server.py:362-389`):

1. Identity: the result is refused unless `(device_id, boot_id)` is a stream namespace this process has accepted and `seq` is at or below its high-water mark. Counted as `model_results_rejected`; event `model_result_refused` with `reason=unknown_identity`; warning.
2. Duplicate: the result is refused when its `result_id` (`device_id:boot_id:seq`) is among the last 4096 model result IDs (`_emitted`, `:161-162`, `:380-382`). Counted as `model_results_duplicate`; event `model_result_refused` with `reason=duplicate`; warning.
3. Otherwise the service builds the 10-key version-3 `GESTURE_RESULT` with `request_id: null` and the configured session, validates it with `validate_message`, counts `model_results`, logs the event `model_result`, and publishes it like any result (`_publish`, `:354-360`): with no subscriber it is dropped at once (`disconnected_results`, event `result_no_subscriber`); otherwise it goes into the subscriber's queue of 32.

**Late emits.** `emit` before the model was started, after the service closed, or when the event loop is closed returns `False` and counts `model_results_late`. A result handed over from another thread that the event loop reaches only after the service stopped is also counted `model_results_late`, although `emit` had returned `True`. This is the only counter updated off the event loop, under a lock (`ultra96/model.py:189-191`).

**Commands bypass the model** (`ultra96/server.py:343-349`; hand-off 6.5, D11). For a newly accepted command the service itself publishes one echo result: version 3, the command's trace fields (so `request_id` equals `seq`), `result_id` `cmd:device_id:boot_id:seq`, a random label from `DUMMY_GESTURES`, confidence 1.0. Command values are transformed dummy rows and their `seq` comes from the command ID space, so they must not reach the model's windows. A repeated command gets `duplicate` and no second echo. Command echoes are not counted in `model_results`.

**The built-in dummy model** (`DummyModel`, `ultra96/model.py:38-50`; hand-off 6.5, D12). For each `on_sample` it calls `emit` at once, on the event-loop thread, for the same sample, with a random `REST`, `FIST`, `OPEN` or `POINT` (system randomness unless a test injects a generator) and confidence 1.0. So with the dummy model every accepted input, stream sample or command, gives exactly one result, and that result is queued before the ACK is written. The one-input-one-result checks (`Phone expected increase` in `demo.py run`, `tools/rehearse_comms.py`, `tools/rehearse_remote_comms.py`, `tools/check_board.py`) hold only while the dummy model runs; `demo.py run` prints a line saying so (`demo.py:248-249`). A real model that emits from another thread may emit after the ACK, or not at all for a given sample.

**Warnings** (`ModelPort.warn`, `ultra96/model.py:143-148`). WARNING lines on standard error, at most one per kind per second (`_WARNING_INTERVAL`, `:31`): `model on_sample raised <type>`, `model on_sample took <ms> ms; it must return immediately`, `model emitted an invalid result; it was not sent`, `model result names a sample this service has not accepted`, `model emitted a second result for one sample`. Repeats within the second are only counted.

**Model threads at exit** (`ultra96/server.py:651-675`; hand-off 6.5, D18). When the command line's event loop has ended (after `stopped`, or after an error such as `model_failed`), it checks for non-daemon threads other than the main thread that are still alive (for example a model's worker). If there are any, it prints `{"event": "exit_with_model_threads", "threads": <n>}` and ends the process with `os._exit`: code 0 after a normal stop (Ctrl+C or SIGTERM); after an error, the traceback first and then code 1 (or the integer code of a `SystemExit`). Without this, the interpreter would wait for those threads, and a process without ports would linger. The threads end abruptly, and interpreter clean-up is skipped.

**Model counters** (always in the metrics, also with the dummy model; `ultra96/model.py:116-119`):

| Key | Meaning |
|---|---|
| `model_samples` | `on_sample` calls (newly accepted stream samples) |
| `model_errors` | `on_sample` calls that raised (`Exception` or `SystemExit`) |
| `model_slow_calls` | Calls longer than 5 ms |
| `model_max_call_ms` | The longest call, in milliseconds, 3 decimals |
| `model_results` | Model results that passed every check and were published (with or without a subscriber) |
| `model_results_rejected` | Invalid arguments, or an identity that fails the high-water check (an unknown power-up, or a `seq` above the highest accepted one) |
| `model_results_duplicate` | A second result for one sample (within the last 4096 model result IDs) |

**The gateway branch** (`CommsServer._gateway`, `ultra96/server.py:423-430`). The gateway reads one first frame with the single 5.0 s deadline. A JSON object whose `type` is `MONITOR` starts a monitor session; any other first frame is validated as `SUBSCRIBE`, as before. A `MONITOR` is validated like every message (exact field set, `v` 1, the configured session): a wrong session, version or field set closes the connection, `rejected` goes up by 1, and no `MONITORING` is sent. `MONITOR` belongs to the gateway only: on the ingest port it is a wrong message type, so that connection is closed and counted in `rejected` too. A service from before 2026-10-18, such as the one deployed on 2026-10-16 (replaced on 2026-10-19), validates every first frame on 9999 as `SUBSCRIBE`, so it refuses a `MONITOR` the same way.

**Messages** (`ultra96/protocol.py:25-37`; checked by `validate_message`, with the update rules in `_monitor_update` and `_monitor_event`, `:56-116`, `:176-177`). All three are version 1, like the subscription envelopes; the version-3 data messages did not change.

| Message | Direction | Content |
|---|---|---|
| `MONITOR` | Laptop to 9999, as the first frame | `{"v":1,"type":"MONITOR","session_id":<configured session ID>}` |
| `MONITORING` | 9999 back to the laptop, once | `{"v":1,"type":"MONITORING","session_id":<configured session ID>}` |
| `MONITOR_UPDATE` | 9999 to the laptop, every 0.25 s | `v`, `type`, `session_id` and the ten fields below, exactly |

`MONITOR_UPDATE` fields (built in `ServiceMonitor._update`, `ultra96/monitor.py:149-176`, from `_monitor_status`, `ultra96/server.py:488-493`):

| Field | Type | Meaning |
|---|---|---|
| `update` | int, 0 or more | 0 for the first update on each connection, then +1 per update |
| `uptime_seconds` | number, 0 or more | Seconds since the service started (`CommsServer.start`, `ultra96/server.py:188`), 3 decimals |
| `model` | string | The model's name as in `model_ready` (`dummy` for the built-in one), 1 to 128 printable characters: a longer name is cut, other characters become `?` (`ultra96/monitor.py:27-30`) |
| `subscriber` | int, 1 or more, or null | The current phone subscriber's ID (the `subscriber_id` of the event log, numbered from 1 since the service started), or null when no phone is subscribed |
| `identities` | int, 0 or more | `(device_id, boot_id)` stream namespaces used by this process |
| `identity_limit` | int, 1 or more | `max_namespaces`, 128 |
| `devices` | object | Exactly the keys `"1"` and `"2"`, each with the seven per-glove counters below |
| `service` | object | Exactly ten values copied from the metrics: `rejected`, `client_limit`, `idle_evicted`, `subscribers`, `replaced`, `model_samples`, `model_errors`, `model_slow_calls`, `model_results_late` (integers) and `model_max_call_ms` (a number). As in the metrics: counts since the service started, and the longest model call so far |
| `events` | list | At most 100 events (`MAX_MONITOR_EVENTS`, `ultra96/protocol.py:16`), oldest first |
| `events_dropped` | int, 0 or more | Events lost on this connection because its buffer was full |

The validator requires exact key sets at every level, integers that are not booleans, finite numbers that are not negative, and in each result, command or refusal event a `device_id` of 1 or 2 and a `boot_id` and `seq` from 0 to 4294967295, with the label and confidence rules on results and command echoes. The laptop's board view checks every update with it.

Per-glove counters (`ServiceMonitor`, `ultra96/monitor.py:42-77`). They are cumulative since the service started and are kept whether or not a monitor is attached: plain integers updated on the event-loop thread, with no I/O, and a `device_id` other than 1 or 2 is ignored.

| Counter | Counts |
|---|---|
| `accepted` | New inputs (stream samples and commands) accepted from this glove: this glove's share of the metric `accepted` |
| `duplicates` | Inputs answered `duplicate` |
| `results` | Model results that passed the identity and duplicate checks and were published, with or without a subscriber: this glove's share of `model_results` |
| `commands` | Command echo results published |
| `refused` | Model results refused by the identity or the duplicate check: the same refusals as the `model_result_refused` events of the event log. Invalid emits never reach these checks and are counted only in `model_results_rejected` |
| `sent` | Results written into the subscriber's connection: the point of `result_write_complete` in the event log (level 4), not a phone receipt |
| `unsent` | Results that were not written: no subscriber (`result_no_subscriber`), dropped as the oldest (`result_drop_oldest`), dropped as stale at dequeue or before the write (`result_drop_stale`), abandoned when their subscriber ended (`result_abandoned`), a failed write (`result_send_failed`) or a cancelled one (`result_send_cancelled`) |

Every published result, model result or command echo, ends in exactly one of `sent` and `unsent`; until then it waits in the queue or is being written. So `results` + `commands` equals `sent` + `unsent` once nothing is waiting. `unsent` does not say which of its causes applied; the event log does. The counts are made by `ResultQueue.count` (`ultra96/server.py:71-74`) and in `_ingest`, `_publish`, `_model_result` and `_send_results`, with or without an observer.

Events (`ultra96/monitor.py:55-71`). Each is a JSON array whose last item `t` is the service uptime in seconds (3 decimals) when it happened:

| Event | Array |
|---|---|
| A model result published | `["result", device_id, boot_id, seq, gesture, confidence, t]` |
| A command echo published | `["command", device_id, boot_id, seq, gesture, confidence, t]` |
| A model result refused | `["refused", device_id, boot_id, seq, "unknown_identity" or "duplicate", t]` |
| A phone subscription | `["subscriber", "claimed", subscriber_id, null, t]` or `["subscriber", "ended", subscriber_id, reason, t]`; `reason` is that of `subscriber_ended` in the event log |

The `gesture` and `confidence` are those of the `GESTURE_RESULT` that is published. Outside the phone, these events are the only place the labels appear: the event log still records none.

**Sending** (`ServiceMonitor.serve` and `_send_updates`, `ultra96/monitor.py:82-147`):

- Events are kept only while a monitor is attached, in a buffer of 4096 (`EVENT_CAPACITY`). When it is full, the oldest event is pushed out and counted in `events_dropped`. Nothing that happened before the monitor attached is kept as an event; the counters cover it.
- After `MONITORING` (written with a 2.0 s deadline), the connection's own sender task writes one `MONITOR_UPDATE` every 0.25 s (`MONITOR_INTERVAL`), the first at once. While events are pending it writes up to 4 updates back to back in one tick (`FRAMES_PER_TICK`). Each update carries at most 100 events, and a frame stays within the frame limit of 16384 bytes: events that would not fit wait, in order, for the next update.
- One monitor at a time. A new `MONITOR` replaces the attached monitor: the old connection is closed and its transport aborted (`:89-95`), and its end is not counted in `rejected`.
- The connection is send-only after `MONITOR`, like a subscriber's: any byte from the laptop, or EOF, ends the session, without counting in `rejected`.
- A slow reader never gets updates queued behind it: while the connection's write buffer holds more than 16384 bytes, the tick is skipped. A drain that takes longer than 2.0 s (`WRITE_TIMEOUT`), or a write buffer that stays above 16384 bytes for longer than 2.0 s, ends the session, and `rejected` goes up by 1. The second rule is needed because `drain()` waits only above the transport's high-water mark of 32768 bytes, so a peer that stopped reading below it would otherwise never time out (`:131-143`).
- A monitor takes one of the 8 client slots and is never evicted to free one: eviction considers only ingest connections that wait for a frame (see "Limits and timeouts"). The service's shutdown ends a monitor session like any connection.

**What it never touches.** A monitor never claims or replaces the phone subscriber (`subscribers` and `replaced` do not change), never reads or writes the result queue, and adds no event and no field to the observer and the event log. The metric keys of the `stopped` line and the service's standard-output lines (`model_ready`, `listening`, `stopped`, `observation_stopped`, `exit_with_model_threads`) are unchanged: the per-glove counters live in `CommsServer.monitor`, not in the metrics. The monitor logs nothing. The phone clients (the Swift app, the C# and the Python receivers) never send `MONITOR`, so they are unaffected.

**Python 3.10, the board's version.** Two details exist for it. The sender loops only while its connection is still the attached one (`ultra96/monitor.py:128`): on Python 3.10 a cancellation that lands in `wait_for` just after the drain finished can be swallowed, so cancellation alone might not stop a replaced monitor's sender. And a replaced monitor's transport is aborted, not only closed (`:93-95`): Python 3.10's TLS close waits for a `close_notify` that a vanished peer never sends, and without the abort the replaced connection would keep its slot.

- The ingest idle limit (since `5d2e52f`). A gated glove sends nothing while the player is still. Under the old single 5.0 s deadline its connection would be closed at every pause longer than 5 s, and the first frames after the pause would be lost as ambiguous during the TLS reconnect (the comment at `ultra96/server.py:34-37`). Now each ingest read waits up to the idle limit for the first byte of the next frame. Once that byte arrives, the rest of the frame must arrive within 5.0 s, as before. After the idle limit the read times out, the connection is closed and `rejected` goes up by 1; nothing is logged. The gateway is not affected: a subscribed phone has no idle timeout, and `SUBSCRIBE` must still arrive within 5.0 s. **Verified on the real Ultra96 on 2026-10-16** (the deployed service, default 600 s; through the tunnel; see "On the real Ultra96 (2026-10-16)"): on one ingest connection, after silences of 7 s, 30 s and 120 s the next sample was `accepted`, so the board no longer closes a quiet connection after 5 s; on another, after 590 s of silence the next sample was `accepted`, and after a further 620 s the next write failed with `ConnectionResetError('Connection lost')` while the tunnel stayed up. So the service closed the quiet connection between 600 and 620 s, as the limit intends.
- Eviction (`_evict_idle_ingest`, `ultra96/server.py:249-263`). Each ingest connection records when it began waiting for its next frame (`_waiting_ingest`, `:142-143`, `:324-328`). When a new connection arrives on either port and all 8 slots are taken, the service picks the ingest connection that has waited longest, provided it has waited at least 5.0 s. It cancels that connection's task, which closes its TLS connection, adds 1 to `idle_evicted`, logs one warning, and waits up to 2.0 s for the slot to free. It then admits the new client if a slot is free; otherwise the new client is closed at once and counted in `client_limit` (`:233-242`). Only ingest connections that are waiting for a frame are candidates. Gateway connections (the phone's, and a board monitor's in the code of 2026-10-18) and connections still in the TLS handshake are never closed this way. Nothing is evicted while the service shuts down. The reason (the comment at `:40-46`): the SSH tunnel's `sshd` can keep the socket of a laptop that vanished for many minutes, and with a 600 s idle limit such sockets could otherwise hold all 8 slots.
- An evicted connection is not counted in `rejected`: its task is cancelled, and cancellation is not one of the expected errors that `_client` counts (`ultra96/server.py:298-301`). No event-log event records an eviction.
- The consequence for a glove that is only still. Its laptop is live, but the service cannot tell it from a vanished one. If its connection is closed (by the idle limit or by eviction), the laptop notices only when it next sends: the frames then in flight get no ACK, the laptop counts them as ambiguous drops, and it reconnects (the comment at `ultra96/server.py:44-45`). This is the same loss the old 5.0 s limit would cause at every pause. Now it happens only after 600 s of silence, or when all 8 slots are full and this connection has waited longest.
- What the 2 s rule covers. It limits how long a result may wait on the board: in the queue (`ResultQueue.get_timed`, `ultra96/server.py:103-112`) plus the write into the phone's connection (`_send_results`, `ultra96/server.py:495-520`, where the write gets only the time that is left). It is not an end-to-end latency bound, and it is not a promise that the phone receives the result: once `write_frame` returns, the bytes are with TCP and TLS and cannot be recalled (the comment at `ultra96/server.py:504-505`). Time spent before the board (the glove, BLE, the laptop's own 2 s freshness, the tunnel, and the model's own processing before it calls `emit`) and after it (SSH, the phone) is not counted here. The phone keeps its own 2 s display window, counted from when it received a result (`ios-visualizer/CommsNative/Sources/CommsCore/DisplayState.swift:104`, `:141`). The phone's result queue for `CommsNextResult` also drops a result 2 s after the phone received it (`DisplayState.swift:29`, `:169`; compiled and tested on Linux and macOS, built for iOS and installed on the owner's iPhone on 2026-10-16, in an export that does not call `CommsNextResult`; a provisional V1 limit, hand-off 7.3). See also hand-off 9.2.
- Every accepted connection gets `TCP_NODELAY` (`ultra96/server.py:243`).
- `SO_REUSEADDR` is set only on POSIX (`ultra96/server.py:196-200`). It lets the same ports restart at once after the service stops.
- With port 0, the system assigns a port. The actual port is read from the `listening` line (`ultra96/server.py:206-207`, `:595-596`). The tests use it this way.
- Temporary listener errors are: a connection aborted by the peer while it was queued, file descriptors exhausted, buffers or memory exhausted (`errno` `ECONNABORTED`, `EMFILE`, `ENFILE`, `ENOBUFS`, `ENOMEM`, or Windows 10024, 10053, 10055). See `ultra96/server.py:222-225`.

### Standard output, logs and metrics

- After start, the service prints two lines on standard output: `{"event": "model_ready", "model": …, "seconds": …}` and then `{"event": "listening", "host": "127.0.0.1", "tls": true, "ingest_port": 8888, "gateway_port": 9999}` (`ultra96/server.py:586-587`, `:595-596`).
- When the model cannot be loaded or its `start(emit)` fails, `{"event": "model_failed", …}` (`ultra96/server.py:555-557`) takes the place of `model_ready` and `listening`, and there is never a `stopped` line. With the event log on, `observation_stopped` follows it (`ultra96/server.py:539-552`). If model threads remain, the last line is `exit_with_model_threads` (`:655-658`).
- On stop it prints one line: `{"event": "stopped", "metrics": {...}}` (`ultra96/server.py:609`). On standard output this is the only place the metrics appear. For a service from before 2026-10-18, such as the one deployed on 2026-10-16 (replaced on 2026-10-19), it is the only place at all: that code cannot be asked for its metrics while it runs. The code of 2026-10-18, deployed on the Ultra96 since 2026-10-19, also sends ten of the metrics, with the per-glove counters, to a board monitor every 0.25 s while it runs (see "The board monitor"); the `stopped` line is unchanged.
- With the event log on, one more line follows: `{"event": "observation_stopped", "state": {...}}` (`ultra96/server.py:552`).
- If non-daemon model threads remain, the very last line is `{"event": "exit_with_model_threads", "threads": n}` (`ultra96/server.py:672-673`).
- Since the code of 2026-10-18 (`2b3be2b`; on the Ultra96 since the redeploy of 2026-10-19) nothing is logged per accepted input. Until then, each new input accepted (stream sample or command) wrote one INFO line to standard error, `accepted session=… device=… boot=… seq=…` (at `bbf1316`, `ultra96/server.py:325-326`; `values` was not printed): a synchronous write before every ACK that nothing parsed, about 100 lines per second while two gloves send at 50 Hz. It was removed for these reasons. The service deployed on 2026-10-16 wrote it into `BOARD_ROOT/evidence/server-co-20261016T050629Z.log`, which therefore grew without bound while the gloves sent, until that service was stopped by the redeploy of 2026-10-19 (a service of code from before 2026-10-18 started with `--start` writes it into its terminal). Since the redeploy, the service log, `BOARD_ROOT/evidence/server-co-20261018T185037Z.log`, no longer grows per sample: it holds the standard-output lines above and the WARNING and ERROR lines below.
- When a listener task dies, one ERROR line goes to standard error: `listener task failed: <exception type name>` (`ultra96/server.py:276`).
- When all 8 client slots are full and an ingest connection is closed to admit a new client, one WARNING line goes to standard error: `client slots full; closing an ingest connection idle for <seconds> s` (`ultra96/server.py:259-260`). It is not rate-limited; there is at most one per new client that finds the slots full.
- Model problems log the rate-limited WARNING lines listed under "The model interface". Duplicates, rejections (including a connection closed after the ingest idle limit) and drops are not logged, and neither is anything of the board monitor.
- Metric keys: `accepted`, `duplicates`, `rejected`, `subscribers`, `replaced`, `disconnected_results`, `result_drops`, `result_stale`, `client_limit`, `idle_evicted` (since `5d2e52f`), `accept_retries`, `accept_failures` (`ultra96/server.py:167-170`), the eight model counters (`model_samples`, `model_errors`, `model_slow_calls`, `model_max_call_ms`, `model_results`, `model_results_rejected`, `model_results_duplicate`, `model_results_late`; `ultra96/model.py:116-119`), and with an observer one more: `observer_errors` (`ultra96/server.py:171-172`). The board monitor of 2026-10-18 adds no key: its per-glove counters are kept apart, in `CommsServer.monitor`.
- `accepted` counts new stream samples and new commands; `model_samples` counts only the stream samples. With the dummy model, `model_results` equals `model_samples` when nothing was refused.
- `client_limit` counts new clients closed at once because all 8 slots were taken and no ingest connection could be closed for them, or the slot of the one closed did not free within 2.0 s, or because the service was shutting down. `idle_evicted` counts ingest connections closed to free a slot (see "Limits and timeouts"). An evicted connection is not also counted in `rejected`.
- `result_drops` and `result_stale` are added to the metrics only when a subscriber ends (`ultra96/server.py:482-483`).
- `rejected` counts more than bad frames on the ingest port. All of the following land in the same `except _EXPECTED_ERRORS` in `_client` (`ultra96/server.py:32-33`, `:300-301`), and each adds 1:
  - a failed handshake, or a handshake longer than 5.0 s (`ultra96/server.py:289-290`);
  - on the ingest port: a bad frame (a `MONITOR` included), mismatched fields, a wrong version, a wrong session, an identity conflict, exhausted capacity, a read timeout (no frame begins within the ingest idle limit, 600 s by default, or a begun frame does not finish within 5.0 s);
  - on the gateway port: a bad frame or a timeout before `SUBSCRIBE`; in the code of 2026-10-18 also a `MONITOR` with a wrong session, version or field set, and on a service from before it, every `MONITOR`;
  - on the gateway port: a failed or timed-out result write. The exception travels from `_send_results` (`ultra96/server.py:513-517`) through `task.result()` and `except Exception: raise` in `_gateway` (`ultra96/server.py:459-460`, `:466-469`) up to `_client`;
  - on the gateway port, in the code of 2026-10-18: a board monitor whose connection fails (a failed write or a reset), whose drain takes longer than 2.0 s, or whose write buffer stays above 16384 bytes for longer than 2.0 s. A monitor that sends a byte, closes, or is replaced by a newer one is not counted.

  So `rejected` above 0 does not necessarily mean that the laptop sent bad data. A gated glove that stays still for longer than the idle limit also adds 1, and so does each run of `python demo.py start` whose board view reaches a service from before 2026-10-18, such as the one deployed on 2026-10-16 (replaced on 2026-10-19): it sends one `MONITOR`, which that service refuses, and then stops asking. Model errors and refused model results never count in `rejected`.

### Event log (`--event-log-dir`)

- Files: while the service runs, `events.partial.jsonl` and `status.json`. After a normal end, `events.partial.jsonl` is renamed to `events.jsonl`, and `status.json` receives `events_sha256` and the counts.
- The folder is created with `mkdir(parents=True, exist_ok=False)` (`ultra96/diagnostics.py:63`). If the folder already exists, this raises `FileExistsError` and the service does not start.
- Each line is one JSON object with these fixed fields: `schema` (`ultra96-observer-event-v1`), `run_id`, `event_seq`, `utc`, `monotonic`, `event`.
- The `schema` of `status.json` is `ultra96-bounded-event-log-status-v1` (`ultra96/diagnostics.py:33`). Its keys include `complete`, `incomplete`, `lost_event_count`, `overflow_count`, `callback_error_count`, `file_cap_reached`, `file_cap_drop_count`, `writer_error_count`, `writer_error_type`, `close_timed_out` and `finalized` (`ultra96/diagnostics.py:244-270`).
- There are 17 event names (`ultra96/diagnostics.py:17-24`): `result_accepted`, `result_duplicate`, `result_no_subscriber`, `result_enqueued`, `result_drop_oldest`, `result_drop_stale`, `result_send_started`, `result_write_complete`, `result_send_failed`, `result_send_cancelled`, `result_abandoned`, `subscriber_claimed`, `subscriber_replaced`, `subscribed_write_complete`, `subscriber_ended`, and since 2026-10-14 `model_result` and `model_result_refused`.
- `result_accepted` means that an input (stream sample or command) was accepted, not that a result exists.
- Ingest connections have no events of their own. Neither close has an event-log event: a close after the ingest idle limit shows only in `rejected`; an eviction shows in `idle_evicted` and in one WARNING line on standard error.
- `model_result` (a model result passed the checks and is being published) and `model_result_refused` (with `reason` `unknown_identity` or `duplicate`) carry `session_id`, `device_id`, `boot_id`, `seq` and `request_id` (null). Invalid and late emits produce no event; they are only counted. A command echo produces no `model_result`.
- There are 14 allowed extra fields (`ultra96/diagnostics.py:25-31`): `device_id`, `boot_id`, `seq`, `subscriber_id`, `previous_subscriber_id`, `queue_size`, `queued_count`, `session_id`, `reason`, `error_type`, `phone_receipt_confirmed`, `ambiguous`, `age_seconds`, `request_id`. The allowlist includes `queued_count`, but the current service code does not emit it.
- The log does not record `values`, `gesture`, `confidence`, the peer address or any credential.
- The board monitor of 2026-10-18 did not change the event log: no new event name, no new field, and still no labels. A monitor connection has no events of its own. The labels reach the laptop only through the monitor's `MONITOR_UPDATE` events (see "The board monitor"; hand-off 6.5, D40).
- Result-queue events carry `subscriber_id` and `queue_size` automatically, and `age_seconds` when the enqueue time is known (`ultra96/server.py:76-87`).
- `result_drop_stale` carries `reason`: `dequeue` when the result is found stale at dequeue, `before_write` when the re-check before the write finds it stale (`ultra96/server.py:110`, `:502`).
- The `reason` of `result_abandoned` equals the reason that subscriber ended (`ultra96/server.py:119`, `:480-481`).
- `result_send_failed` and `result_send_cancelled` carry `ambiguous=true`. The first also carries `error_type` (`ultra96/server.py:511`, `:515-516`).
- `subscribed_write_complete` and `result_write_complete` carry `phone_receipt_confirmed=false`. The log object allows only `false` for this field (`ultra96/diagnostics.py:127-129`).
- `reason` and `error_type` must match `^[A-Za-z][A-Za-z0-9_.-]{0,63}$` (`ultra96/diagnostics.py:32`, `:119-121`).
- Values of `reason` in `subscriber_ended`: `peer_eof`, `unexpected_input`, `sender_stopped`, `replaced`, `server_shutdown`, `cancelled`, `error`, `disconnected` (`ultra96/server.py:439`, `:461-464`, `:467`, `:480`).
- An invalid event name or field is not raised into the service. That event is dropped and `callback_error_count` goes up by 1 (`ultra96/diagnostics.py:161-166`).
- A full queue, exceeding the file cap, a write failure, a rejected field or a close timeout all make the receipt's `complete` `false` (`ultra96/diagnostics.py:306-313`). After the file cap is exceeded, later events are only dropped, never written (`ultra96/diagnostics.py:206-213`).

- Renewal mode neither outputs nor changes the CA private key or the CA certificate. Clients keep trusting the same `ca-cert.pem`, and the CA fingerprint registered in the phone source stays valid.
- Before renewal, the tool checks that `ca-key.pem` and `ca-cert.pem` are the same key pair. If not, it reports `ca-key.pem does not belong to ca-cert.pem` (`tools/generate_comms_pki.py:88-89`). The CA private key must have no passphrase.
- Renewal requires the CA to outlive the new server certificate. If now plus 30 days is past the CA's expiry, the tool reports `the CA expires before a new server certificate would; generate a new PKI` (`tools/generate_comms_pki.py:91-92`).
- Both certificates become valid 5 minutes before the issue time. The signature algorithm is SHA-256. The server certificate is built in `_server_certificate` (`tools/generate_comms_pki.py:38-56`), with the 30 days on line 47. The CA's 365 days and path length 0 are on lines 117 and 118.
- The host name constant is `SERVER_NAME = "ultra96.week7.internal"` (`tools/generate_comms_pki.py:24`), the same as `TLS_SERVER_NAME` at `common/tls.py:4`.
- The output folder must be outside every Git repository (neither the folder nor any parent folder may contain `.git`) and must be empty. It may not exist yet; the tool then creates it. Otherwise the tool reports `PKI output must be outside Git repositories and worktrees` or `PKI output directory must be empty; refusing to overwrite keys` and overwrites nothing (`tools/generate_comms_pki.py:27-35`). Both modes apply these rules.
- Before writing keys, the tool restricts the output folder's permissions. On Windows it gets the current user with `whoami`, then runs `icacls /reset` and `icacls /inheritance:r /grant:r <user>:(OI)(CI)F`, so only the current user has access. On other systems it runs `chmod 700` (`tools/generate_comms_pki.py:12-21`).
- Private keys are created with `O_EXCL` and mode 0600 (`tools/generate_comms_pki.py:64`). Certificates are written in exclusive mode. Existing files are never overwritten.
- Output on success: new-PKI mode prints `Created B07 Communications development PKI in <folder>` and `Copy only ca-cert.pem to clients; copy server-cert.pem/server-key.pem to Ultra96.` (`tools/generate_comms_pki.py:145-146`). Renewal mode prints `Issued a new server certificate from the existing CA in <folder>` and `Clients keep their ca-cert.pem; copy server-cert.pem/server-key.pem to Ultra96.` (`tools/generate_comms_pki.py:141-142`).
- On connect, clients verify the certificate chain and the host name `ultra96.week7.internal` (`TLS_SERVER_NAME`), even though they actually connect to the forwarded port on `127.0.0.1`.
- Server authentication only. There are no client certificates.

## Workflow

### Normal path

1. Prepare the certificates. On first deployment, run `python -m tools.generate_comms_pki --output-dir <empty folder outside Git>` on the laptop to get 4 files. When a CA already exists (as it does now), use `--renew-server-from` to issue only a new server certificate (see "Renewing the server certificate"). The renewed pair of 2026-10-14 is on the board since 2026-10-16, kept by the redeploy of 2026-10-19 (see "Certificates").
2. Inspect read-only first: `python demo.py service`. It prints, from the board, the listener list, this user's processes, and the PID and working directory of each `ultra96.server` process.
3. Deploy: `python -m tools.deploy_service --dry-run`, then `python -m tools.deploy_service --server-cert-dir <renewed folder>` (later with `--model MODULE --model-path DIR`). The owner types both passwords, with the NUS VPN on: without it the jump host offers no password login (see "Failure paths", 33). Done this way on 2026-10-16 (see "Board state (2026-10-16, after the deploy)"), and again on 2026-10-19 without options, so the installed certificate was kept, to bring the board monitor (see "Board state (2026-10-19, after the redeploy)"). The tool uploads the code into a new folder, installs the certificate, replaces a running service of this user or starts the first one, and prints a final record. The steps are in "Deploying with `tools/deploy_service.py`" below. The deployed service runs in the background in its own session and does not depend on any SSH session.
4. Only when nothing runs (for example after the board rebooted) and the code has not changed: `python demo.py service --start`, adding `--session-id <name>` when needed. If a healthy service already runs, reuse it; do not start another one. The session ID is first checked with `validate_session`. If it is invalid, `demo.py` prints `Demo could not complete: …` and returns 2 without contacting SSH (`demo.py:340-342`).
5. After the check passes, `--start` prints four lines (`tools/demo_service.py:119-123`): `Run 'python demo.py service' first. Reuse an existing healthy service.`, `Confirm ESP, board and iPhone versions match this deployment: <folder>`, `Model: <model, or "the built-in dummy model">`, `Session: <session ID> (the capture and the phone must use the same one)`. Then it prompts `Press Enter to start only if absent, or type q to cancel: `. Only an empty line (or one of blanks only) continues. Any other input cancels, returns 130 and does not contact SSH (`tools/demo_service.py:124-125`).
6. The script runs a piece of `sh` on the board over two SSH hops (`tools/demo_service.py:86-113`). It uses `ssh -tt`, strict host key checking on both hops, and the operator types the passwords interactively in the terminal. The `sh` script first runs `set -eu`, enters the folder from `newest_deployment()`, confirms with `command -v ss` that the `ss` command exists, then lists listeners with `ss -ltnH`. When 8888 and 9999 are both free, it runs `exec /usr/bin/python3 -u -m ultra96.server --cert BOARD_ROOT/tls/server-cert.pem --key BOARD_ROOT/tls/server-key.pem --session-id <session ID> --ingest-port 8888 --gateway-port 9999`, plus `--model` and `--model-path` when the record names them (hand-off 6.5, D19). The service runs as the logged-in user and becomes the foreground process of this SSH session. The exit code of `demo.py` is the exit code of `ssh` (`tools/demo_service.py:137`).
7. The service starts. It imports the model, loads the certificate and private key (`ultra96/server.py:571`), calls the model's `start(emit)`, opens the two listeners, prints `model_ready`, registers a SIGTERM handler on platforms that support it, and prints the `listening` line.
8. The phone subscribes. The phone connects to 9999. The TLS handshake must finish within 5.0 s, and `SUBSCRIBE` must arrive within 5.0 s. After validation, the service creates a new empty result queue, registers this connection as the current subscriber, and then sends `SUBSCRIBED`. Registration comes before writing `SUBSCRIBED`, so every result produced from that moment goes into this queue. The phone shows `Subscribed` when `SUBSCRIBED` arrives. That proves only this handshake; whether results flow depends on input arriving on 8888, and on the model producing results, while this connection is still the subscriber.
9. After subscribing, the connection only receives. The service sets no idle timeout, so the phone can stay connected indefinitely. In the code of 2026-10-18, the laptop's board view (`python demo.py start`) connects to 9999 the same way but sends `MONITOR`: it gets `MONITORING` and then a `MONITOR_UPDATE` every 0.25 s, and the phone stays the subscriber (see "The board monitor").
10. The laptop sends samples. Each `SENSOR_BATCH` goes through three steps in order: read the frame, validate the fields, version and session, check for a duplicate. A gated glove sends only while its movement detector says MOVING, so its connection can be quiet for seconds or minutes. The service waits up to the ingest idle limit (600 s by default) for the next frame to begin; once it begins, the rest must arrive within 5.0 s (see "Limits and timeouts").
11. A new input: `accepted` goes up by 1 (in the code of 2026-10-18 also the glove's own `accepted` counter for the board monitor). The service deployed on 2026-10-16 also logged one INFO line per input; the code of 2026-10-18, on the Ultra96 since 2026-10-19, no longer does (see "Standard output, logs and metrics"). A stream sample goes to the model's `on_sample` (`ultra96/server.py:339-342`); with the dummy model, `on_sample` calls `emit` at once and the result passes the identity and duplicate checks. A command gets the service's own echo result (`:343-349`).
12. Each result is published: if there is a subscriber, it goes into the queue; if there is none, it is dropped and counted (`ultra96/server.py:354-360`). Then `INGEST_ACK` (`accepted`) goes back to the laptop (`:350-352`). With the dummy model and for commands the order is enqueue first, ACK write second. A model that emits from another thread delivers its result later, independent of the ACK.
13. The send task takes results from the queue, checks freshness and writes them to the phone. The write timeout equals the remaining freshness (`ultra96/server.py:495-520`). This bounds only the waiting on the board, not end-to-end latency (see "Limits and timeouts").
14. Stop. Press Ctrl+C in the foreground terminal, or send SIGTERM to a verified PID. The service cancels the listener tasks, closes the listeners, cancels all connection tasks, closes the model port (later emits count as late), and prints `stopped` with the metrics (`ultra96/server.py:522-536`, `:603-612`). If non-daemon model threads remain, it then prints `exit_with_model_threads` and exits. In the Linux tests, both signals give exit code 0.

### Failure paths

1. Invalid session ID: `demo.py` prints `Demo could not complete: session_id must be a nonempty string of at most 128 characters`, returns 2 and does not contact SSH. `tools.deploy_service` prints `FAILED: …` and returns 2.
2. The board cannot enter the start folder (missing, or no permission): `cd` fails, the script exits at once because of `set -eu`, and nothing starts.
3. The board has no `ss` command: the script exits at `command -v ss` because of `set -eu`. Nothing starts and no explanation is printed (`tools/demo_service.py:96`).
4. The `ss` query fails: the script prints `Could not inspect service ports. Nothing was started.`, exits with code 2, and starts nothing (`tools/demo_service.py:97-100`).
5. Either 8888 or 9999 is taken: the script prints `Service ports are already in use. Nothing was stopped or started.` and the output of `ss -ltnp`, and exits with code 2 (`tools/demo_service.py:101-111`). The guard matches a listener on any local address that ends in `:8888` or `:9999` (`*:8888|*:9999`), not only `127.0.0.1`. The script never stops or kills an existing process.
6. The model cannot be imported, lacks `start` or `on_sample`, has an `async def` one, or its import or `start(emit)` raises (including `SystemExit`): `model_failed`, a traceback, a non-zero exit, and no port is opened. Under `tools.deploy_service` this is a failed start: it rolls back, or ends in `failed_nothing_running` when nothing ran before.
7. The certificate or private key fails to load: the service raises an exception during start-up, prints a traceback and exits non-zero. There is no `listening` line.
8. The certificate has expired: the service loads it and starts as usual, because the service code does not check its own certificate's validity. Clients enforce validity, so the handshake fails. On the board this shows as `rejected` growing. The laptop gets no ACK. The phone stops, does not retry, and needs the passwords typed again before it can reconnect (hand-off document sections 4.6 and 9.2). `tools.deploy_service` refuses a certificate that expires within an hour, so it does not start a service with an expired one.
9. `--event-log-dir` points to an existing folder: constructing the log object raises `FileExistsError` and the service does not start.
10. A plaintext connection, a failed handshake, or a handshake over 5.0 s: the connection is closed and `rejected` goes up by 1.
11. The 9th concurrent connection, on either port. If an ingest connection has waited at least 5.0 s for its next frame, the one that has waited longest is closed: `idle_evicted` goes up by 1, one WARNING line is logged, and the new connection is admitted once the slot frees (within 2.0 s); if it does not, the new connection is closed and `client_limit` goes up by 1. When no ingest connection has waited that long, the new connection is closed at once and `client_limit` goes up by 1. Connections accepted while the service is shutting down are always closed at once and counted in `client_limit`. A gated glove whose connection was evicted while it was still loses the frames in flight when it next sends (ambiguous drops on the laptop), and the laptop reconnects.
12. An invalid frame, mismatched fields, a wrong version (for example a laptop or a tool from before version 3 sending `v` 2), or a wrong session ID: the connection is closed, `rejected` goes up by 1, no error frame is sent and nothing is logged. The peer must reconnect.
13. An ingest connection receives no frame for longer than the ingest idle limit (600 s by default), or a frame that has begun is not complete within 5.0 s: the read times out, the connection is closed, `rejected` goes up by 1, and nothing is logged. A gated glove that was still for that long loses the frames in flight when it next sends, as in 11. Before `5d2e52f` the limit for a quiet connection was 5.0 s.
14. A duplicate sample: the service answers `duplicate`, `duplicates` goes up by 1, and the sample reaches neither the model nor the phone.
15. A fingerprint conflict, a stale identity, or exhausted capacity: see the "De-duplication and replay protection" table. The connection is closed.
16. `on_sample` raises: `model_errors` goes up by 1, a warning is logged at most once a second, the ACK is still `accepted`, and the connection stays open.
17. `on_sample` is slow: `model_slow_calls` goes up and `model_max_call_ms` shows the worst call. The ACKs of both gloves wait; if they wait past the laptop's 5 s ACK limit, the laptop counts `ack_errors` and `transport_errors` (hand-off 9.2).
18. The model emits an invalid result, a result whose power-up the service has not seen or whose `seq` is above the highest accepted one (a `seq` inside a gap is not detected), or a second result for one sample: nothing is sent; `model_results_rejected` or `model_results_duplicate` goes up, with a warning and (for the last two) a `model_result_refused` event.
19. The model emits after the service stopped: `emit` returns `False` (or the result is dropped on the event loop) and `model_results_late` goes up.
20. No subscriber: the result is dropped at once, `disconnected_results` goes up by 1, and the event is `result_no_subscriber`. The laptop still gets `accepted`. A later phone subscription does not get the result resent.
21. The queue already holds 32 results: the oldest is dropped, with the event `result_drop_oldest`.
22. A result has waited 2.0 s or longer on the board (in the queue, or found stale just before the write): it is dropped, with the event `result_drop_stale`.
23. A result write fails or times out: the event is `result_send_failed` (`ambiguous=true`). This subscriber ends (`reason=error`). What remains in the queue is recorded as `result_abandoned`. `rejected` goes up by 1. The phone must subscribe again.
24. A new `SUBSCRIBE` arrives: the new connection becomes the subscriber. The service closes the old connection. Unsent results in the old queue are recorded as `result_abandoned`, `replaced` goes up by 1, and the event is `subscriber_replaced`.
25. The phone sends any byte after subscribing: the subscription ends with `reason=unexpected_input` and the connection is closed.
26. A phone app from before version 3 (the Week 7 build, installed on the owner's iPhone until 2026-10-16): its `SUBSCRIBE` is still version 1, so it can subscribe if its session matches, but it rejects the first version-3 result with a terminal error (hand-off 8, step 5). That build uses the session `week7-demo`, so against a service on `ltc-comms` it cannot even subscribe. On the owner's iPhone it was replaced at 13:13 (+08:00) on 2026-10-16, seven minutes after the deploy, by the app built from the current source, which subscribed to the service that afternoon.
27. A temporary listener error: `accept_retries` goes up by 1 and the listener retries after a delay.
28. A listener task exits on any other error: `accept_failures` goes up by 1 and standard error shows `listener task failed: <exception type name>`. The service shuts down as usual and prints `stopped`, then exits non-zero with a `RuntimeError: B07 Communications listener failed` traceback (`ultra96/server.py:278-281`, `:601-602`). It never leaves an idle process behind with a dead listener.
29. The observer (event log) raises an exception: only `observer_errors` counts it. ACKs and result forwarding are not affected.
30. Non-daemon model threads remain after the stop: `exit_with_model_threads`, and the process ends with `os._exit`.
31. During renewal, the CA private key and certificate do not match, the CA has less than 30 days left, or the output folder breaks the rules: the tool exits with an error and writes no file.
32. `tools.deploy_service` fails: see the statuses table in "Deploying with `tools/deploy_service.py`". A failure before the old service is stopped leaves it running; a failure after that tries to restart it from the rollback copy.
33. The jump host offers no password login (seen on 2026-10-16 with the laptop on Wi-Fi without the NUS VPN: `stujump.comp.nus.edu.sg:22` answered but offered only `publickey`). `tools.deploy_service` fails at the first hop with `FAILED: BadAuthenticationType: Bad authentication type; allowed types: ['publickey']` and exit code 2; nothing is uploaded or changed. Since 2026-10-16 it then prints `The server does not offer password login. Off the NUS VPN, stujump accepts only public keys: connect the NUS VPN and run this again.` (`tools/deploy_service.py:569-573`). With the VPN connected, stujump offered `password` and both logins worked. So a missing VPN shows up not as an unreachable host but as a refused login method. The OpenSSH commands (`demo.py service`, `demo.py tunnel`, and since 2026-10-18 `demo.py start`) depend on the same password login, so they need the VPN too. The laptop has no SSH key pair and Communications uses none; the route stays laptop to stujump to Ultra96 with passwords, VPN on.
34. A `MONITOR` with a wrong session, version or field set, or a `MONITOR` sent to the ingest port (code of 2026-10-18): the connection is closed, `rejected` goes up by 1, and no `MONITORING` is sent. A service from before 2026-10-18, such as the one deployed on 2026-10-16 (replaced on 2026-10-19), treats every `MONITOR` this way, because it validates every first frame on 9999 as `SUBSCRIBE`; the phone's subscription is not affected. The laptop's board view cannot tell these cases apart: it reports the close as `unsupported` (a service that predates the monitor, or one on another session) and, if it had not connected yet in this run, stops asking, so `python demo.py start` runs without it (`board view off (service predates the monitor)`; [detail chapter 3](03-laptop-relay-and-tools.md)). After an earlier connection in the same run (for example when the service is restarted on another session mid-run), it treats the close as an outage (`lost`) and keeps reconnecting, with a back-off of up to 5 s (`_run`, `laptop/board_monitor.py:102-126`), and each refused `MONITOR` adds 1 to `rejected`.
35. A second `MONITOR` while a monitor is attached: the new one is served, and the old connection is closed and its transport aborted at once. Neither counts in `rejected`, and the phone's subscription is untouched.
36. A board monitor that sends any byte, or closes: the session ends, not counted. One that stops reading: while its write buffer holds more than 16384 bytes no update is queued; after 2.0 s above that, or a drain longer than 2.0 s, the session ends and `rejected` goes up by 1. The events still buffered for it are discarded; the per-glove counters are not affected, and the next monitor reads them as they are.

| Design point | Reason | Alternatives rejected in the past | Design record |
|---|---|---|---|

## Cautions and known limitations

### Certificates

- The server certificate is valid for only 30 days. The renewed one (see "Certificates") expires at 2026-11-13 14:27:35 UTC: it covers the 10-20 session but not the final demo around Week 13, so renew again in early November (hand-off 9.2). It is installed on the board since 2026-10-16 (`tools.deploy_service --server-cert-dir`; see "Board state (2026-10-16, after the deploy)"), and the redeploy of 2026-10-19 kept it.
- The laptop keeps a copy of the server certificate that was deployed to the board in September. That laptop copy expired at 2026-10-06 15:11:29 UTC (also recorded at `docs/archive/reports/week7-continuation-report-2026-09-07.md:733-734`). The 28 September redeploy kept the existing TLS files (`docs/archive/test-evidence/co-live-deployment-2026-09-28.md:12`). The pair on the board until 2026-10-16 was backed up to `BOARD_ROOT/tls/backup-20261016T050629Z/` by that day's deploy, without its dates being read.
- The service code does not check whether its own certificate has expired. With an expired certificate the service starts as usual, and clients fail the handshake because they enforce validity. `tools.deploy_service` does check: it refuses a pair that expires within an hour. So a later deploy without `--server-cert-dir` keeps the installed pair (as the redeploy of 2026-10-19 did) and, from an hour before it expires on 2026-11-13, fails its checks (nothing changes) until a renewed pair is given.
- Running the tool without `--renew-server-from` creates a new CA, and then the fingerprint in the phone source and the laptop's `--ca` must both change.
- The phone app hard-codes the CA's SHA-256 in its source (`ios-visualizer/CommsNative/Sources/CommsBridge/Configuration.swift:19`) and compares against it when the CA is imported (`Configuration.swift:62-63`). Changing the CA means changing this value, rebuilding and reinstalling the app, and updating the laptop's `--ca`.
- The current CA expires on 2027-09-06. From about 2027-08-07, the tool refuses renewal.

### The model interface

- `on_sample` runs on the service's only event loop, before the ACK. A model that does its inference inside `on_sample` holds up the ACKs of both gloves, result sending and new connections. The laptop waits up to 5 s for each frame's ACK (`laptop/bridge.py:608-617`; `io_timeout` defaults to 5.0 at `laptop/bridge.py:42`). Sample freshness is 2 s (`laptop/bridge.py:41`). The ACK window is 32 frames (`laptop/dual_bridge.py:549`), and at 50 Hz 32 frames are only 0.64 s. Slow calls are counted, not stopped. Inference belongs on another thread or in another process.
- The identity check uses the high-water mark: it proves that the sample's power-up is known and that `seq` is not ahead of what arrived. It does not prove that this exact `seq` arrived; a `seq` inside a gap passes.
- `emit` returning `True` does not mean the result was sent. The identity and duplicate checks, the subscriber, the queue of 32 and the 2 s limit come later.
- The board remembers the last 4096 model result IDs. A repeated identity older than that would be sent again (the phone keeps its own last 4096).
- With the dummy model a stream sample's result is queued before its ACK. With a model that emits from another thread, a result can follow the ACK by any amount of time, or never come.
- `--model-path` is ignored by `ultra96.server` without `--model`; the deploy tool refuses that combination. The folder stays first on the import path for the whole process.
- A model's non-daemon threads end abruptly at exit (`exit_with_model_threads`); daemon threads, or threads the model stops itself, avoid this. A model that calls `emit` inside `start(emit)` gets its results refused, because no sample has been accepted yet.
- `model_ready`'s `seconds` counts only `start(emit)`, not the import.
- The model gets no commands and no duplicates. Samples from the two gloves arrive interleaved on one thread, with no pairing and no alignment.
- With the bridge (`ultra96.model_bridge`), samples are dropped, not stored, while no runner is connected or while 1024 lines wait for it; they are counted only in the bridge's log line at disconnect, not in the `stopped` metrics. `model_samples` still counts every call to the bridge. The bridge's Unix-socket tests skip on Windows, which has no `AF_UNIX` in Python's `socket` there; the rest of its tests run everywhere.
- The bridge's socket is mode 0600, so another ordinary user cannot connect; root can. A second service started while one runs fails at `start(emit)` (`model_failed`, `FileExistsError`) instead of taking over the socket.

What the model receives since gating (`5d2e52f`, `e24f8ea`; built; on 2026-10-16 the gating ran on the right board with the gated dummy against a service on the laptop, not yet through the Ultra96 and not yet with Siqiang's detector on a glove; the firmware side is in [detail chapter 2](02-firmware.md)):

- A board built from the `-glove` environments, with Siqiang's sensor module, sends a sample only while his movement detector says MOVING. While it says IDLE, the glove sends nothing, and `on_sample` is not called for that glove. A `-glove` build with `-DCOMMS_GLOVE_SEND_ALL=1` sends IDLE samples too; since pull request #31 (in local `main` from 2026-10-23) both `-glove` environments set it, so the plain `-glove` build does. The default environments, with the built-in dummy glove, send every tick unless built with `COMMS_DUMMY_IDLE_MS` above 0.
- The IDLE/MOVING state itself does not travel. The packet and `on_sample` keep the 11 values; the only sign of IDLE is silence.
- The firmware allocates a `seq` only for a sample it sends. An idle pause therefore shows as a jump in `uptime_ms`, not as a gap in `seq`. A `seq` gap still means a lost sample (see "Behaviour limits").
- The two gloves gate independently. One glove can be silent for any length of time while the other sends.
- The detector judges a 1 s window (50 samples, 20 ms apart) every 200 ms. MOVING needs two above-threshold windows in a row: at the earliest 0.2 to 0.4 s after motion starts, later if the 1 s window needs more motion to cross the threshold. IDLE needs three below-threshold windows: at least 0.4 to 0.6 s after the window falls below the threshold, and because each window covers the last 1 s, up to about 1.6 s after motion stops (`hardware/gloves/integration_files/glove_sensor.cpp:46-50`, `:381-389`, `:412-416`). Samples before the MOVING decision are not sent and cannot be sent later. So the model never sees the first part of a gesture, and it can see up to about 1.6 s of stillness after one. This is a property of Siqiang's detector for Wen Ree to plan around (hand-off 7.2), not something the service can repair.
- The detector restarts from nothing after a failed IMU read, a non-finite sample, or more than 100 ms between two `gloveUpdate` calls. Sending then stops for about 1.2 s (the 1 s window refills, then a second evaluation 200 ms later must agree), even in the middle of a gesture. In the Communications firmware `gloveUpdate` runs every 1 to 2 ms, so only the first call after boot and transient I2C failures trigger this.
- A glove that is still for longer than the ingest idle limit (600 s by default) has its connection closed (verified on the Ultra96 on 2026-10-16 with a test script: closed between 600 and 620 s). The frames in flight when it next sends are lost as ambiguous drops on the laptop (see "Limits and timeouts").

### Behaviour limits

- Any process that can reach `127.0.0.1:9999` on the board and knows the session ID can take over the phone's subscription. During a demo, do not run `laptop.phone_simulator`, `tools.rehearse_remote_comms` or any other subscriber against the board in use. A board monitor (`MONITOR`, the board view of `python demo.py start`, code of 2026-10-18) is not a subscriber: it never claims or replaces the subscription. It does take a client slot, and a second monitor replaces the first.
- The one subscriber receives every result, whatever input caused it. So while a rehearsal checks its results one by one, nothing else may send input to the same service: on 2026-10-16 an idle test that ran at the same time put 2 unexpected results into a remote rehearsal and failed it (see "On the real Ultra96 (2026-10-16)"). Run one rehearsal at a time.
- The limit of 8 connections covers both ports together. When all 8 are taken, a new client on either port is admitted only by closing the ingest connection that has waited longest for its next frame, and only if it has waited at least 5.0 s. Two gloves and one phone use 3 slots, and 4 with the board view of `python demo.py start` (code of 2026-10-18), so the slots fill only with leftover tunnel sockets or extra clients. A board monitor is never closed to free a slot.
- The service closes an ingest connection that stays quiet for longer than the ingest idle limit, 600 s by default (before `5d2e52f`: 5.0 s; verified on the Ultra96 on 2026-10-16, see "Limits and timeouts"). A frame that has begun must still finish within 5.0 s. When a gated glove that was only still next sends after such a close, or after an eviction, the frames then in flight get no ACK, the laptop records them as ambiguous drops, and it reconnects.
- Reconnects can leave gaps in `seq` that the service, and the model, sees. On a BLE disconnect the laptop discards that glove's queued samples (`inbox.deactivate` in `laptop/bridge.py`; reported as `callback_generation_dropped`). On a TLS reconnect, samples already written but not acknowledged count as ambiguous drops and are not resent (`ambiguous_dropped`). While a glove is disconnected it produces no samples and `seq` does not advance, so that time shows only as a jump in `uptime_ms`. The same holds for a gated glove's idle pause. None of these is resent, and nothing on the board fills or reports the gap (hand-off 7.2).
- Stream samples must arrive in increasing `seq` order. Gaps are allowed (`ultra96/server.py:411-417`).
- One process lifetime allows at most 128 `(device_id, boot_id)` pairs and at most 4096 commands. When they are used up, restart the service. Every glove power-up uses one pair, and so does every synthetic rehearsal and test script with its own boot ID. The service deployed on 2026-10-16 had used 5 after that day's tests. The redeploy of 2026-10-19 started a new process, whose count starts again at 0 of 128 (the old process had used some of its 128; see "Board state (2026-10-19, after the redeploy)").
- A service restart clears the de-duplication state. After a restart, an old input that is sent again is accepted again.
- The service deployed on 2026-10-16 printed one INFO line per accepted input, as does any service of code from before 2026-10-18. With two gloves at about 50 Hz each, that is about 100 lines per second while both send (fewer while gated gloves are idle), into the foreground terminal (`--start`) or into `BOARD_ROOT/evidence/server-co-<stamp>.log` (deploy tool), which grows without bound. The code of 2026-10-18 removed that line; since the redeploy of 2026-10-19 the service on the Ultra96 runs it, so its log no longer grows per sample (see "Standard output, logs and metrics").
- The event log is capped at 50 MiB. Once full, it only drops events. Use a new folder each time.

### Blind spots when troubleshooting

- The service records no rejection reasons. Expected errors are caught and only increment `rejected` (`ultra96/server.py:300-301`). A wrong session ID, a wrong version, mismatched fields, a stale identity, exhausted capacity, a quiet connection closed after the ingest idle limit, and a handshake failure caused by an expired certificate all look the same on the board: the connection closes and `rejected` grows. The only problems logged with a reason are model problems (rate-limited warnings), a dead listener, and an eviction when the slots are full.
- On a service from before 2026-10-18, such as the one deployed on 2026-10-16, the metrics become visible only when the service stops and prints `stopped`. With the code of 2026-10-18, on the Ultra96 since the redeploy of 2026-10-19, the board monitor's updates carry, while the service runs, `rejected`, `client_limit`, `idle_evicted`, the model counters except `model_results`, `model_results_rejected` and `model_results_duplicate`, the identities used out of 128, and per glove the inputs, the model results, the refusals, the command echoes and the results sent and not sent (see "The board monitor"); still without any reason. The board view of `python demo.py start` shows and logs only part of this: the identities, the model errors, slow calls and late results (and, in its summary, the slowest call), and per glove the model results, the refused results, the command echoes and the results sent and not sent. It does not show or log `rejected`, `client_limit`, `idle_evicted` or the per-glove inputs (its `Ultra96 acknowledged` step counts the ACKs the laptop received, not the board's `accepted`), so `rejected`, `client_limit` and `idle_evicted` still become visible only in the `stopped` line ([detail chapter 3](03-laptop-relay-and-tools.md)). When troubleshooting, do not expect to find texts such as `wrong configured session` or `stream identity capacity exhausted; start a new session` in the board logs. They are never output. When capacity is exhausted, the operator sees a newly powered glove that never connects, and the laptop's `transport_errors` growing (and, with the board monitor, `identities` at 128 of 128).
- The laptop side does not record reasons either (see [detail chapter 3](03-laptop-relay-and-tools.md)). A TLS connect or handshake failure increments only `transport_errors`. An ACK timeout or a mismatched ACK increments both `ack_errors` and `transport_errors`. So no log on either side records the reason. On the laptop, an expired certificate and an unreachable port show only `transport_errors`; a session mismatch and a protocol version mismatch between the two ends show `ack_errors` as well, because the Ultra96 closes the connection after reading the frame. With version 3, upgrading only one end shows up as such a "silent disconnect". Only the newest version is supported (the owner's rule), so both boards, the laptop, the Ultra96 service and the phone app are upgraded together (hand-off 6.3).
- The only way to find which segment results are lost in is the event log: read `status.json` and `events.jsonl` after a graceful stop. A service started by the deploy tool has one by default; with `--start`, start the service by hand with `--event-log-dir`. The board monitor of the code of 2026-10-18 tells, per glove and while the service runs, how many results were written to the subscriber's connection (`sent`) and how many were not (`unsent`), but not which drop applied to which result; for that the event log remains the only record.

### Technical constraints related to teammate interfaces

The content of the three interfaces (fields, how calls are made, questions for teammates) is maintained only in section 7 of the hand-off document: Siqiang in 7.1, Wen Ree in 7.2, Jie Ling in 7.3. This chapter records only the constraints that come from its own code. The Communications side of 7.2 is built; Wen Ree's side does not exist; the interface shapes are the owner's proposals of 2026-10-14, final when the teammates confirm them, and teammates deliver code by pushing it to the team repo on GitHub, not over Telegram (hand-off 7, 13).

- The model receives each sample's 11 values as physical floats in the agreed order and units. They travel as int16, and the service divides by the scale before calling `on_sample`. Restoring cannot recover precision dropped when packing (acceleration and flex keep 4 decimal places, angular rate and angles 2). Any normalisation is Wen Ree's. The scales are provisional.
- `on_sample` is called once per newly accepted stream sample, from the ingest path at `ultra96/server.py:339-342`: a duplicate (`status: "duplicate"`) and a command produce no call. Samples from the two gloves arrive on two independent connections, with no pairing and no alignment, and can have `seq` gaps (see "Behaviour limits"). A gated glove sends only while its detector says MOVING; each glove pauses on its own, and a pause shows only as an `uptime_ms` jump (see "The model interface" above).
- `on_sample` must return immediately. The board service has only one asyncio event loop, and the ingest connections of both gloves share it; the ACK is written only after `on_sample` returns. The numbers are in "The model interface" under "Cautions and known limitations".
- `emit` may be called from any thread. The result queue is an `asyncio.Queue` (`ultra96/server.py:62`), `ResultQueue.put` is synchronous and has no lock (`ultra96/server.py:89-97`), and the current subscriber `_subscriber` has no lock either. `emit` therefore moves each result onto the event loop with `loop.call_soon_threadsafe`; a model must never call the queue directly.
- Communications passes every valid result through unchanged: it does not merge, split, filter, rename or reinterpret results. Several identical labels in a row (for example several `CHOP`) reach the phone as several results (subject to the board queue of 32 and the 2 s limit); whether they mean one action or several is for Wen Ree and Jie Ling to agree (hand-off 3.1).
- Each result must name a different sample: the board refuses a second result for the same `device_id:boot_id:seq` (within the last 4096), and the phone de-duplicates by `result_id`.
- Only the existing send task may write results to the phone. The frame-writing contract is one writing task per connection (`common/wire.py:87`).
- `GESTURE_RESULT` cannot gain fields freely. All four validators match exactly the 10 keys: on the board `ultra96/protocol.py:143-144`; the Python receiver compares the key set (`phone/receiver.py:100`, with `RESULT_FIELDS` at `:21-22`); the C# reference implementation compares the field count, 10 (`phone/unity/CommsPhoneCore.cs:51`, `:78`); the iPhone requires exactly the result field set (`ios-visualizer/CommsNative/Sources/CommsCore/Protocol.swift:51`, `:108`) and its parser accepts at most 10 fields (`Protocol.swift:202`). All four require `v` 3, `result_id` equal to `device_id:boot_id:seq` (with `cmd:` for commands) and `device_id` 1 or 2. So the correlation that the model hands back can only be the identity of one sample. On the iPhone, a validation failure is a terminal error. Adding a field means changing all four together, and the Swift 10-field cap.
- The service runs as an ordinary user, with `/usr/bin/python3 -u` and the standard library only (`tools/demo_service.py:112`; `tools/deploy_service.py:181`). A model inside this process can import only what loads under this interpreter and this user. `fpga/README_FPGA_PYNQ.md` says the FPGA overlay needs `sudo` and the pynq-venv Python; a model that can only run that way is a separate process (hand-off 7.2).
- The deploy tool does not upload the model; its files must already be on the board, and the model must not open listening sockets in the service process (see "Deployment and operation").

### Locally (without the board)

1. Install the dependencies: `python -m pip install -r requirements-dev.txt`.
2. Generate a temporary set of certificates: `python -m tools.generate_comms_pki --output-dir <empty folder outside Git>`.
3. Start the service: `python -m ultra96.server --cert <folder>/server-cert.pem --key <folder>/server-key.pem`. The `model_ready` line (model `dummy`) and then the `listening` line mean it started. To try a model module, add `--model <module> --model-path <folder holding it>`.
4. Open a second terminal as the subscriber: `python -m laptop.phone_simulator --host 127.0.0.1 --port 9999 --ca <folder>/ca-cert.pem --count 3 --reconnect`. It waits only 5.0 s for each result (`laptop/phone_simulator.py:13-14`, `:26`). Without `--reconnect`, if no input arrives, it exits with `TimeoutError` about 5 s after subscribing (`laptop/phone_simulator.py:57-59`).
5. Open a third terminal to send synthetic input: `python -m laptop.dual_bridge --ca <folder>/ca-cert.pem --port 8888 --mock --duration 10`. `--mock` is explicit two-device synthetic input and does not touch BLE (`laptop/dual_bridge.py:566-567`). `--port 8888` connects it directly to the local service; the default 18888 is the tunnel port (`laptop/dual_bridge.py:545`; the host defaults to `127.0.0.1`, see `laptop/bridge.py:37-38`). The subscriber should receive 3 results and exit.
6. Press Ctrl+C to stop the service. The `stopped` line with the metrics, including the model counters, should appear.
7. A simpler one-shot rehearsal: `python -m tools.rehearse_comms --pki-dir <same folder> --duration 30 --target 100`. It starts the service (with the dummy model), the bridge and the subscriber locally and prints one JSON line. `passed` should be `true`.
8. One flashed board against a service on the laptop: `python -m tools.check_board left|right` (detail chapter 3).
9. The board monitor (code of 2026-10-18): `python -m pytest tests/test_ultra96_monitor.py -q -p no:cacheprovider`. It starts services on local TLS and checks the gateway branch, the counters and events against the result path, that the phone's results do not change, the replacement, the limits and the validator (see "Components and files"). There is no separate command-line client for the monitor; its client is the board view of `python demo.py start` ([detail chapter 3](03-laptop-relay-and-tools.md)).

To run the tests for this chapter:

```
python -m pytest tests/test_transport.py tests/test_transport_cleanup.py tests/test_v3_events.py tests/test_model_interface.py tests/test_protocol_rules.py tests/test_server_diagnostics.py tests/test_server_observation.py tests/test_server_signals.py tests/test_accept_recovery.py tests/test_ack_window_transport.py tests/test_co_contracts.py tests/test_ssh_trust.py tests/test_demo_service.py tests/test_deploy_service.py tests/test_ultra96_monitor.py -q -p no:cacheprovider
```

- Do not run `python -m pytest` without paths from the repository root (rule 4 in `AGENTS.md`). For the full suite, use `python -m pytest tests laptop/tests phone/tests -q -p no:cacheprovider`.
- The two real-signal cases in `test_server_signals.py` run only on Linux. The script cases in `test_demo_service.py` need `sh` on the local machine. Two cases in `test_ssh_trust.py` need `ssh` on the local machine. When a tool is missing, those cases are skipped.
- With `B07_LINUX_DEPLOY_TEST=1`, `test_deploy_service.py` also runs the deploy tool's board program in Linux, or in WSL from Windows. It starts and stops `ultra96.server` processes there and needs the Git history with `5a004c6` (the team main after PR #18, whose service code equals `c42b386`). The test hands bash a copy of the script with LF endings, so a Windows checkout with CRLF endings works. Never run `tests/linux/deploy_remote_test.sh` on the Ultra96 itself.

Neither was run on 2026-10-16; instead the remote rehearsals' TLS handshakes verified the renewed certificate against the CA through the tunnel.
7. End-to-end check: on the laptop side, every sample gets `accepted` (level 3). On the phone side, the increase in `Received` equals the `Phone expected increase` that `demo.py` prints (level 5). These are evidence at different levels. The phone showing `Subscribed` is not evidence that results flow; only the `Received` increase is. `Phone expected increase` is the number of generated samples plus completed commands (`demo.py:245-249`), so it holds only while the board runs the built-in dummy model; `demo.py` prints a line saying so. After a graceful stop, look at `status.json`. Only `complete` equal to `true` and `lost_event_count` equal to 0 make it usable as complete evidence.

Or first verify with `ps -p <PID> -o pid=,uid=,args=` and `readlink -f /proc/<PID>/cwd` that it is the user's own `ultra96.server`, then run `kill -TERM <PID>`. Do not use `pkill` or kill by port.
