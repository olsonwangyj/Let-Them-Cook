# Communications integration handoff

**Status:** proposed sequence and interface requests, 8 October 2026. These are tasks for the communications portion, not agreed dates or commitments from other teammates. Keep the working dummy transport available until the real-data path passes its own tests.

## What exists now

- The communications path has two independently tracked ESP32 **BLE/GATT** streams through the laptop to Ultra96; the phone receives results directly from Ultra96 through its own SSH/TLS connection. The laptop gets `INGEST_ACK`, which proves ingestion rather than phone delivery. See [bridge](../laptop/dual_bridge.py), [server](../ultra96/server.py), and [phone protocol](../ios-visualizer/CommsNative/Sources/CommsCore/Protocol.swift).
- The current dummy BLE packet is exactly **32 bytes**: `<2sBBIII8h>` = `W7`, version, device ID, boot ID, sequence, uptime in milliseconds, and **eight little-endian signed 16-bit values**. Its version 2 network envelope has one device's eight values and a `request_id` key (`null` for ordinary telemetry). For example, this is a valid *dummy-contract illustration*, not a real sensor vector:

  ```json
  {"v":2,"type":"SENSOR_BATCH","session_id":"week7-demo","device_id":1,"boot_id":7,"seq":42,"uptime_ms":4200,"values":[1,2,3,4,5,6,7,8],"request_id":null}
  ```

  See [packet codec](../common/sensor.py), [network schema](../ultra96/protocol.py), and [framing](../common/wire.py). The JSON is carried as four-byte big-endian length plus UTF-8 body over TLS; that TCP framing is separate from BLE notifications.
- Ultra96 currently issues one random dummy result per newly accepted version 2 single-glove input. The accepted labels are `REST`, `FIST`, `OPEN`, `POINT`; confidence must equal `1.0`, including in the iPhone validator. It does **not** assemble paired-glove model windows. See [server](../ultra96/server.py), [result schema](../ultra96/protocol.py), and [Swift validator](../ios-visualizer/CommsNative/Sources/CommsCore/Protocol.swift).
- Team-repository sensor work describes an MPU-6500 and two flex sensors per glove, producing **11 floating-point features** in this order: `ax, ay, az, gx, gy, gz, yaw, pitch, roll, flex1, flex2`, approximately 50 Hz. Acceleration is gravity-compensated in g, gyro is bias-corrected in degrees/s, angles are in degrees, and flex is normalized. The model combines left then right into **50 × 22** input and has six classes: `PICKUPHOLD`, `PLACEDOWN`, `CHOP`, `WASH`, `THROW`, `FIREEXT`. See [glove README](../hardware/gloves/README.md), [live inference](../src/live_inference.py), [preprocessing](../src/preprocess_sensor_data.py), and [class order](../models/class_names.json).
- The team's unmerged `siqiang_29_sept` branch (`c55e95c`) adds `hardware/gloves/29_sept/imu_v7.ino` and recorder v14. That firmware emits 11-value CSV plus a glove label over **Bluetooth Classic SPP**, which Windows exposes as a virtual COM port. It is an acquisition reference, not a drop-in BLE/GATT sender for this path. See [branch firmware](https://github.com/B07-CG4002/Let-Them-Cook/blob/c55e95c0946e4c80559c9ee137ee6f24add65e21/hardware/gloves/29_sept/imu_v7.ino#L85-L102) and [branch recorder](https://github.com/B07-CG4002/Let-Them-Cook/blob/c55e95c0946e4c80559c9ee137ee6f24add65e21/hardware/gloves/29_sept/imu_recording_terminal_v14.py#L74-L85).

**Integration consequence:** the eight-int16 dummy packet, 11-float real sample, 50 × 22 model input, and six-class result are different contracts. Preserve the old message versions and specify a new version or message type with cross-language test vectors before changing producers or validators. The team recorder pairs samples using laptop receive timestamps within 35 ms, while training preprocessing resamples each whole trial to 50 points and live inference slides over the latest 50 raw samples. The real-time pairing and window rules still need agreement.

### Packet decision record to complete together

Publish one versioned interface sheet and literal golden vectors covering: byte offsets and total length; magic/version; left/right device and boot/session identity; per-device sequence; timestamp units and sampling instant; feature order; numeric encoding, byte order, scale, saturation and invalid-value representation; notification versus batch boundaries; maximum rate; ACK/result correlation; and malformed/reboot/gap behavior. Include at least one ordinary vector, signed/scale boundaries, both devices, reboot and malformed-length cases. Firmware, laptop and Ultra96 must decode the **same bytes** to the **same physical values**.

The old 32-byte packet needs ATT MTU **at least 35** because a notification value is limited to `MTU - 3` bytes. As a sizing illustration only, 11 `float32` values plus the present 16-byte header would be **60 bytes**, requiring MTU **at least 63**, before any added fields or batching. At 50 samples/s on each glove that would be 48 kbps of application packet bytes. The existing physical test negotiated MTU 517 and found a clean peak near 66 packets/s per device with **32-byte dummy** packets, about 33.792 kbps combined; it does not certify the larger real format. Recalculate and retest the chosen encoding on two actual gloves. See [MTU policy](../firmware/esp32/include/comms_security.h), [codec](../common/sensor.py), and [28 September physical report](co-live-deployment-2026-09-28.md).

## Acceptance evidence to collect

1. **Contract:** committed schema plus byte-for-byte firmware/Python vectors, valid and invalid cases, and version rejection tests. Include the exact source/model/app revisions used.
2. **Physical streams:** for each glove, source generated/submitted, laptop received, Ultra96 ACKed, duplicate/gap/drop counts, negotiated MTU, actual sample rate and packet goodput over the same timed interval. Compare decoded real values with sensor reference readings.
3. **Pairing and model:** paired-window IDs with left/right boot and sequence ranges, time skew and discard reasons; identical test window producing the agreed reference model result, score and latency on the deployed Ultra96 runtime.
4. **Phone/game:** installed-app evidence that all six supported labels and low-confidence behavior follow the agreed mapping; correlate result IDs to windows. Keep board write completion, aggregate phone count and per-ID phone receipt as distinct evidence levels.
5. **Recovery:** show no cross-boot or stale-window game action after a glove reset, link outage or phone pause; report lost intervals and recovery time. The current live-only result service does not replay results while no phone is subscribed.

**Open blockers before claiming real end-to-end integration:** transport choice for the sensor branch; signed real-data packet contract and test vectors; paired-window timing and inference semantics; deployable Ultra96 model path; six-class visualizer/game mapping and editable app source; owners and test slots for the combined build and physical devices.
